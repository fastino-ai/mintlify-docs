Verwenden Sie einen verifizierbaren Reward, wenn Code eine Antwort prüfen kann,
etwa ein Mathematikergebnis, ein Testergebnis, eine Schema-Bedingung, eine
exakte Extraktion oder ein Tool-Ergebnis.

```text
prompt -> sample a group -> grade -> center rewards -> build datums -> update
```

Sampling, Forward-Backward-Durchläufe, Optimiererschritte und Checkpoints
gehören alle zum selben interaktiven Fastino-Job. Reward-Berechnung und
Anwendungszustand bleiben in Ihrem Code.

## Bevor Sie beginnen

Schließen Sie den [Schnellstart für den benutzerdefinierten Loop](/de/training/quickstart#custom-training-loop)
ab. Die folgenden Ausschnitte verwenden dessen Helfer `call` und `wait`, seinen
`tokenizer` und eine `job_id`. Sie nutzen den eingebauten Loss
`importance_sampling` und konzentrieren sich auf den nutzereigenen Reward-Ablauf.

<Note>
  Dieser Leitfaden ist kein eigenständiger Trainer zum Kopieren und Einfügen.
  Beginnen Sie mit dem Schnellstart-Skript, prüfen Sie, dass seine Datums
  trainieren, und ergänzen Sie dann den folgenden Reward-Ablauf.
</Note>

<Note>
  Der Job führt nur die eingebauten Losses aus: `cross_entropy`,
  `importance_sampling`, `ppo`, `cispo` und `dro`. Eine Loss-Funktion aus Ihrem
  eigenen Code kann nicht auf dem Job laufen. Drücken Sie Ihren Reward als
  Advantages für einen dieser Losses aus.
</Note>

<Warning>
  Führen Sie generierten Code oder Tools nur in einer isolierten Umgebung mit
  begrenzten Ressourcen aus. Fastino führt Ihre Reward-Funktion nicht aus und
  verwaltet ihre Seiteneffekte nicht.
</Warning>

## 1. Einen engen Grader definieren

Trennen Sie Parsing und Bewertung, damit fehlerhafte Ausgaben sichtbar werden:

```python
def get_reward(response: str, expected: str) -> float:
    actual = parse_answer(response)
    if actual is None:
        return 0.0
    return 1.0 if actual == expected else 0.0
```

Halten Sie einen festen Satz von Testfällen mit korrekten, falschen, fehlerhaften
und gleichwertig formatierten Antworten vor. Protokollieren Sie Parsing-Fehler
getrennt von gültigen, aber falschen Antworten.

## 2. Job für das Sampling sichern

Speichern Sie einen Sampler-Checkpoint aus den aktuellen Gewichten und samplen
Sie daraus eine Gruppe:

```python
name = f"rollout-{step:06d}"
saved = call(
    "POST",
    f"/v1/training/jobs/{job_id}/save-weights-for-sampler",
    {"name": name, "ttl_seconds": 24 * 60 * 60},
)
wait(job_id, saved["future_id"])

prompt_tokens = tokenizer.apply_chat_template(
    [{"role": "user", "content": question}],
    add_generation_prompt=True,
    return_dict=False,
)
sampled = call(
    "POST",
    f"/v1/training/jobs/{job_id}/sample",
    {
        "checkpoint": name,
        "prompt_tokens": prompt_tokens,
        "num_samples": group_size,
        "sampling_params": {"max_tokens": 512, "temperature": 1.0},
    },
)
sample_result = wait(job_id, sampled["future_id"])
```

Dadurch entsteht kein weiterer Job. Checkpoint und Samples gehören zum selben
interaktiven Job.

## 3. Rewards in Advantages umwandeln

```python
sequences = sample_result["sequences"]
rewards = [
    get_reward(tokenizer.decode(sequence["tokens"]), expected)
    for sequence in sequences
]

mean_reward = sum(rewards) / len(rewards)
advantages = [reward - mean_reward for reward in rewards]

if all(advantage == 0.0 for advantage in advantages):
    continue
```

Verfolgen Sie Gruppen ohne Reward-Varianz. Sie können darauf hindeuten, dass die
Aufgabe zu leicht, zu schwer oder falsch geparst ist.

## 4. Ausgerichtete Datums erstellen

Der Prompt ist Kontext, daher erhalten Prompt-Positionen einen Advantage von
null. Antwort-Positionen erhalten den gruppenrelativen Advantage der Antwort und
die Log-Wahrscheinlichkeiten des Samplers. Jeder Tensor hat einen Wert pro
Eingabeposition:

```python
def rl_datum(prompt_tokens, sequence, advantage):
    completion = sequence["tokens"]
    tokens = prompt_tokens + completion
    padding = [0.0] * (len(prompt_tokens) - 1)
    logprobs = padding + sequence["logprobs"]
    advantages = padding + [advantage] * len(completion)
    if not (len(tokens) - 1 == len(logprobs) == len(advantages)):
        raise ValueError("training datum arrays are not aligned")
    return {
        "model_input": {"chunks": [{"type": "encoded_text", "tokens": tokens[:-1]}]},
        "loss_fn_inputs": {
            "target_tokens": {"data": tokens[1:], "dtype": "int64"},
            "logprobs": {"data": logprobs, "dtype": "float32"},
            "advantages": {"data": advantages, "dtype": "float32"},
        },
    }


datums = [
    rl_datum(prompt_tokens, sequence, advantage)
    for sequence, advantage in zip(sequences, advantages)
]
```

Verwenden Sie den Tokenizer des `base_model` des Jobs für Prompts und Dekodierung.

## 5. Interaktiven Job aktualisieren

```python
backward = call(
    "POST",
    f"/v1/training/jobs/{job_id}/forward-backward",
    {"datums": datums, "loss_fn": "importance_sampling"},
)
update = call(
    "POST",
    f"/v1/training/jobs/{job_id}/optim-step",
    {"adam_params": {"learning_rate": 1e-5}},
)
train_result = wait(job_id, backward["future_id"])
optim_result = wait(job_id, update["future_id"])
```

Beide Operationen verändern den bestehenden interaktiven Job. Native Clients
reihen dieselbe Arbeit über
[`forward-backward`](/de/api-reference/training-jobs/interactive/forward-backward)
und [`optim-step`](/de/api-reference/training-jobs/interactive/optim-step) ein
und fragen jede `future_id` bis zu einem Endstatus ab. Tinker-Clients lösen
jedes Future auf. Zeichnen Sie jedes Ergebnis auf, bevor Sie den
Anwendungsschritt fortsetzen.

## 6. Wiederherstellungspunkt speichern

```python
state = call(
    "POST",
    f"/v1/training/jobs/{job_id}/save-weights",
    {"name": f"step-{step:06d}"},
)
wait(job_id, state["future_id"])
```

Persistieren Sie den zurückgegebenen `path` zusammen mit:

- Job-ID
- Anwendungsschritt und Dataset-Cursor
- Revisionen von Dataset und Reward-Implementierung
- Basismodell und Trainingskonfiguration
- Evaluierungsmetriken

Mit diesen Metadaten kann ein Controller einen Checkpoint wählen, ohne ihn aus
dem Namen zu erraten.

## Vor dem Skalieren prüfen

- Der Grader unterscheidet bekannte korrekte und falsche Testfälle.
- Fehlerhafte Antworten bringen den Anwendungsloop nicht zum Absturz.
- Mindestens eine Sample-Gruppe hat Reward-Varianz.
- Die Tensoren jedes Datums haben einen Wert pro Eingabeposition.
- Forward-Backward- und Optimiererschritt-Operationen werden auf demselben Job abgeschlossen.
- Ein neuer Job kann aus einem Zustands-Checkpoint mit seinen clienteigenen
  Fortsetzungsmetadaten starten.
- Die Evaluierung auf zurückgehaltenen Daten bleibt vom Reward-Batch des
  Trainings getrennt.

Den umgebenden Lebenszyklus finden Sie unter
[Benutzerdefinierten Trainingsloop erstellen](/de/training/training-loop).
