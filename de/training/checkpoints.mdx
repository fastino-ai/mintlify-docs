---
title: "Checkpoints und Wiederherstellung"
description: "Speichern Sie den Status eines interaktiven Jobs und den Anwendungsfortschritt und stellen Sie ihn wieder her, ohne abgeschlossene Arbeit zu wiederholen."
---

Ein Zustands-Checkpoint schützt den serverseitigen Trainingszustand. Ein
vollständiger Wiederherstellungsdatensatz schützt zusätzlich den
nutzereigenen Zustand, der Ihrem Controller sagt, was als Nächstes zu tun ist.

Die Beispiele verwenden die Helfer `call` und `wait` aus dem
[Schnellstart-Skript](/de/training/quickstart#custom-training-loop).

## Was gespeichert wird

| Datensatz | Enthält | Gespeichert von |
| --- | --- | --- |
| Zustands-Checkpoint | LoRA-Gewichte und Optimiererzustand | Fastino |
| Loop-Datensatz | Quell-Job-ID, Checkpoint-Pfad, Schritt, Dataset-Cursor, Konfiguration und Fortsetzungs-Herkunft | Ihre Anwendung |

## 1. Zustand und Loop-Fortschritt speichern

Speichern Sie den Zustand mit `save-weights`, warten Sie darauf und persistieren Sie
seinen Pfad mit den clienteigenen Feldern, die zum Fortsetzen nötig sind:

```python
import json
from pathlib import Path


state = call(
    "POST",
    f"/v1/training/jobs/{job_id}/save-weights",
    {"name": f"step-{step:06d}"},
)
state_path = wait(job_id, state["future_id"])
record = {
    "source_job_id": job_id,
    "state_path": state_path,
    "model": model_name,
    "dataset_revision": dataset_revision,
    "optimizer": adam_params,
    "step": step,
    "dataset_cursor": dataset_cursor,
    "reward_version": reward_version,
}

with Path(log_path).open("a", encoding="utf-8") as checkpoint_log:
    checkpoint_log.write(json.dumps(record, sort_keys=True) + "\n")
```

Der Pfad in der ersten Speicherantwort ist vorläufig. Der Checkpoint wird erst
nach Abschluss des Speicher-Futures dauerhaft. Bei Fehler oder Abbruch dürfen
Sie diesen Pfad nicht persistieren oder verwenden.

Verwenden Sie eindeutige Checkpoint-Namen, damit jeder Loop-Datensatz einen
eindeutigen Wiederherstellungspunkt bezeichnet. Namen bestehen aus 1–128 Zeichen
aus `A-Z`, `a-z`, `0-9`, `.`, `_` und `-`. Präfixe `__park-` und `__snap-`
sind reserviert.

## 2. Neuesten vollständigen Datensatz lesen

Ein Prozess kann beim Schreiben der letzten Zeile anhalten. Lesen Sie rückwärts
und überspringen Sie ein fehlerhaftes Ende:

```python
def get_last_checkpoint(log_path: str) -> dict[str, object] | None:
    path = Path(log_path)
    if not path.exists():
        return None

    for line in reversed(path.read_text(encoding="utf-8").splitlines()):
        try:
            record = json.loads(line)
        except json.JSONDecodeError:
            continue
        if isinstance(record, dict) and isinstance(record.get("state_path"), str):
            return record
    return None
```

## 3. Vor dem Laden validieren

Vergleichen Sie den Datensatz mit dem Quell-Checkpoint und der angeforderten
Fortsetzung:

- Quell-Job-ID im Checkpoint-Pfad
- Basismodell und LoRA-Konfiguration
- Dataset-Revision und Cursor
- Revision der Reward-Implementierung
- Optimierereinstellungen
- Annahmen zu Tokenizer und Chat-Template

Halten Sie für eine explizite Entscheidung an, wenn diese Felder kollidieren.
Kombinieren Sie einen Checkpoint nicht stillschweigend mit einem anderen
Experiment.

Wählen Sie dann, wie es weitergeht:

| Situation | Aufruf |
| --- | --- |
| Der Quell-Job ist noch aktiv und Sie möchten zurückrollen | `POST /v1/training/jobs/{job_id}/load-weights` mit `{"path": "<name>", "optimizer": true}` |
| Der Quell-Job wurde gestoppt oder freigegeben | `POST /v1/training/jobs/create-model` mit `from_checkpoint` und `load_optimizer` |

So setzen Sie in einem neuen Job fort:

```python
resumed = call(
    "POST",
    "/v1/training/jobs/create-model",
    {"from_checkpoint": resume["state_path"], "load_optimizer": True},
)
wait(resumed["job_id"], resumed["future_id"])
wait(resumed["job_id"], resumed["load_future_id"])
resumed_job_id = resumed["job_id"]
```

Der neue Job übernimmt Basismodell und LoRA-Einstellungen des Checkpoints; senden
Sie daher kein `lora_config`. Seine ID unterscheidet sich von der Quell-Job-ID.
Speichern Sie `source_job_id`, `state_path` und `resumed_job_id` als
anwendungseigene Herkunft.

## 4. Grenze wiederherstellbar machen

Halten Sie diese Reihenfolge ein:

1. Warten Sie, bis die Forward-Backward- und Optimiererschritt-Futures abgeschlossen sind.
2. Speichern Sie den Zustands-Checkpoint und warten Sie auf das Speicher-Future.
3. Persistieren Sie den Loop-Datensatz mit seinem Pfad.
4. Markieren Sie den Anwendungsschritt als abgeschlossen.
5. Beginnen Sie den nächsten Schritt.

Endet der Prozess nach dem Speichern des Checkpoints, aber vor dem Persistieren
des Loop-Datensatzes, behalten Sie den vorherigen vollständigen Datensatz als
vertrauenswürdigen Wiederherstellungspunkt. Markieren Sie einen Schritt erst als
abgeschlossen, wenn sein Datensatz dauerhaft gespeichert ist.

Future-Ergebnisse bleiben eine Stunde abrufbar. Fragen Sie in diesem Fenster
eine bekannte Speicher-`future_id` ab. Bei `410` dürfen Sie nicht blind erneut
speichern; gleichen Sie die Checkpoints des Jobs mit dem dauerhaften
Loop-Datensatz ab. Die langfristige Commit-Grenze ist ein abgeschlossener
Checkpoint mit seinem dauerhaften Anwendungsdatensatz.

## 5. Checkpoint-Arten getrennt halten

```python
name = f"step-{step:06d}"
state = call(
    "POST",
    f"/v1/training/jobs/{job_id}/save-weights",
    {"name": name},
)
sampler = call(
    "POST",
    f"/v1/training/jobs/{job_id}/save-weights-for-sampler",
    {"name": name, "ttl_seconds": 24 * 60 * 60},
)
```

| Gespeichert mit | Checkpoint-ID-Suffix | Vollständiger Pfad | Verwendung |
| --- | --- | --- | --- |
| `save-weights` | `weights/<name>` | `tinker://<job_id>/weights/<name>` | Trainingswiederherstellung: laden oder einen neuen Job daraus starten |
| `save-weights-for-sampler` | `sampler_weights/<name>` | `tinker://<job_id>/sampler_weights/<name>` | Rollouts, Evaluierung und Download als PEFT-LoRA-Dateien |

Verwenden Sie keinen Sampler-Checkpoint als Wiederherstellungspunkt: Er enthält
keinen Optimiererzustand, und ein neuer Job kann nicht daraus starten. Übergeben
Sie den vollständigen `tinker://.../weights/<name>`-Pfad, nicht das ID-Suffix,
als `from_checkpoint`.

`ttl_seconds` ist standardmäßig `null`; ohne TTL bleibt der Checkpoint erhalten,
bis Sie ihn löschen. Aktive Checkpoints zählen zum Checkpoint-Speicher. Für eine
automatische Bereinigung übergeben Sie einen Wert von `3600` bis `315360000`
Sekunden (1 Stunde bis 10 Jahre).

Verwalten Sie Checkpoints mit diesen Routen:

| Aufgabe | Route |
| --- | --- |
| Checkpoints eines Jobs auflisten | [`GET /v1/training/jobs/{job_id}/checkpoints`](/de/api-reference/training-jobs/checkpoints) |
| Einen Checkpoint abrufen | [`GET /v1/training/jobs/{job_id}/checkpoints/{kind}/{name}`](/de/api-reference/training-jobs/interactive/get-checkpoint) |
| Als `.tar`-Archiv herunterladen | [`GET /v1/training/jobs/{job_id}/checkpoints/{checkpoint_id}/download`](/de/api-reference/training-jobs/download-checkpoint) |
| TTL ändern | [`PUT /v1/training/jobs/{job_id}/checkpoints/{kind}/{name}/ttl`](/de/api-reference/training-jobs/interactive/set-checkpoint-ttl) |
| Veröffentlichen oder Veröffentlichung aufheben | [`POST /v1/training/jobs/{job_id}/checkpoints/{kind}/{name}/publish`](/de/api-reference/training-jobs/interactive/publish-checkpoint) |
| Löschen | [`DELETE /v1/training/jobs/{job_id}/checkpoints/{kind}/{name}`](/de/api-reference/training-jobs/interactive/delete-checkpoint) |
| Speichernutzung lesen | [`GET /v1/training/usage`](/de/api-reference/training-jobs/interactive/storage-usage) |

Für Downloads benötigt das Team Zugriff auf den Gewichte-Download.

Nach dem Stoppen eines Jobs werden verändernde Trainingsoperationen abgelehnt.
Seine Checkpoints können weiterhin aufgelistet, geprüft, heruntergeladen,
veröffentlicht, mit einer TTL versehen und gelöscht werden. Sampling aus
Sampler-Checkpoints bleibt ebenfalls möglich.

## 6. Fortsetzung prüfen

Bevor Sie den fortgesetzten Workload skalieren:

1. Starten Sie den neuen Job aus dem gewählten Zustands-Checkpoint.
2. Persistieren Sie seine ID als `resumed_job_id` und bestätigen Sie sie über
   `GET /v1/training/jobs/{resumed_job_id}`.
3. Führen Sie eine kleine Evaluierung auf zurückgehaltenen Daten aus.
4. Senden Sie ein Trainingsupdate.
5. Speichern Sie einen neuen Zustands-Checkpoint unter neuem Namen.
6. Persistieren Sie den nächsten Loop-Datensatz.

## Trainiertes Modell bereitstellen

Stellen Sie einen Sampler-Checkpoint bereit, um ihn als Modell auszuliefern. Das
Deployment ist für unterstützte Basismodelle verfügbar; andere Basismodelle
geben `400` zurück.

```bash
curl -X POST "https://api.fastino.ai/v1/training/jobs/$TRAINING_JOB_ID/checkpoints/sampler_weights/step-000100/deploy" \
  -H "X-API-Key: $FASTINO_API_KEY" \
  -H "Content-Type: application/json" \
  -d '{"model_name": "support-replies-v1"}'
```

Die Antwort enthält die `model_id` des Modells und den `status` `deploying`.
Wiederholen Sie denselben Aufruf, um den Fortschritt zu prüfen: Er gibt dasselbe
Modell zurück, und `status` wird `deployed`, sobald das Modell bereit ist. Rufen
Sie es dann über seine ID auf:

```bash
curl -X POST "https://api.fastino.ai/v1/chat/completions" \
  -H "X-API-Key: $FASTINO_API_KEY" \
  -H "Content-Type: application/json" \
  -d '{
    "model": "MODEL_ID",
    "messages": [{"role": "user", "content": "Summarize this ticket in one sentence."}]
  }'
```

Ersetzen Sie `MODEL_ID` durch die zurückgegebene `model_id`. Felder und Fehler
finden Sie unter
[Checkpoint bereitstellen](/de/api-reference/training-jobs/interactive/deploy-checkpoint).

## Wiederherstellungsfehler diagnostizieren

| Symptom | Prüfung |
| --- | --- |
| Ein Future schlägt fehl | Notieren Sie die Job-ID und den `error` des Futures. Schreiben Sie abhängigen Anwendungszustand nicht fort |
| Ein Trainingsaufruf gibt nach einer Pause `400` zurück | Der Job wurde gestoppt oder nach 30 inaktiven Minuten freigegeben. Veränderndes Training ist nicht verfügbar; Checkpoint-Verwaltung und Sampling bleiben verfügbar. Starten Sie zum Fortsetzen einen neuen Job aus dem letzten Zustands-Checkpoint |
| Ein Checkpoint lässt sich nicht laden | Prüfen Sie Job, Checkpoint-Art und den clienteigenen Wiederherstellungsdatensatz |
| `from_checkpoint` wird abgelehnt | Bestätigen Sie, dass es ein vollständiger `tinker://<job_id>/weights/<name>`-Pfad Ihres Teams ist; Sampler-Checkpoints können keinen Job starten |
| Abruf des fortgesetzten Jobs schlägt fehl | Bestätigen Sie, dass die ID aus der Erstellungsantwort des neuen Jobs stammt und dasselbe Fastino-Team authentifiziert ist |
