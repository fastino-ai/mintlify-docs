---
title: "Checkpoints und Wiederherstellung"
description: "Speichern Sie den Status eines interaktiven Jobs und den Anwendungsfortschritt und stellen Sie ihn wieder her, ohne abgeschlossene Arbeit zu wiederholen."
---

Ein Status-Checkpoint schützt den serverseitigen Trainingsstatus. Ein
vollständiger Wiederherstellungsdatensatz schützt außerdem den benutzereigenen
Status, der Ihrem Controller vorgibt, was als Nächstes zu tun ist.

## Was gespeichert werden muss

| Datensatz | Enthält | Gespeichert von |
| --- | --- | --- |
| Status-Checkpoint | Durch den SDK-Checkpoint repräsentierte Trainingsgewichte und Optimizer-Status | Fastino |
| Loop-Datensatz | Quell-Job-ID, Checkpoint-Pfad, Schritt, Datensatz-Cursor, Konfiguration und Wiederherstellungslinie | Ihre Anwendung |

Der SDK-Trainingsclient repräsentiert einen interaktiven Fastino-Job. Lesen Sie
seine kanonische ID aus
`training_client.get_info().model_id`.

## 1. Status und Loop-Fortschritt speichern

Speichern Sie den Status über das SDK und persistieren Sie anschließend den
zurückgegebenen Checkpoint mit den clientseitigen Feldern, die zum Fortfahren
benötigt werden:

```python
import json
from pathlib import Path


source_job_id = training_client.get_info().model_id
state = training_client.save_state(f"step-{step:06d}").result()
record = {
    "source_job_id": source_job_id,
    "state_path": state.path,
    "model": model_name,
    "dataset_revision": dataset_revision,
    "optimizer": optimizer_config,
    "step": step,
    "dataset_cursor": dataset_cursor,
    "reward_version": reward_version,
}

with Path(log_path).open("a", encoding="utf-8") as checkpoint_log:
    checkpoint_log.write(json.dumps(record, sort_keys=True) + "\n")
```

Verwenden Sie eindeutige Checkpoint-Namen, damit jeder Loop-Datensatz eine
eindeutige Wiederherstellungsgrenze identifiziert. Gehen Sie nicht von einer
undokumentierten Lebensdauer eines Checkpoints aus.

## 2. Neuesten vollständigen Datensatz lesen

Ein Prozess kann beim Schreiben der letzten Zeile beendet werden. Durchsuchen
Sie die Datei rückwärts und überspringen Sie ein fehlerhaftes Ende:

```python
def get_last_checkpoint(log_path: str) -> dict[str, object] | None:
    path = Path(log_path)
    if not path.exists():
        return None

    for line in reversed(path.read_text(encoding="utf-8").splitlines()):
        try:
            record = json.loads(line)
        except json.JSONDecodeError:
            continue
        if isinstance(record, dict) and isinstance(record.get("state_path"), str):
            return record
    return None
```

## 3. Vor dem Laden validieren

Vergleichen Sie den Datensatz mit dem Quell-Checkpoint und der gewünschten Fortsetzung:

- im Checkpoint-Pfad kodierte Quell-Job-ID,
- Basismodell und trainierbare Konfiguration,
- Datensatzrevision und -Cursor,
- Revision der Reward-Implementierung,
- Optimizer-Konfiguration,
- Annahmen zu Renderer und Tokenizer.

Halten Sie an und fordern Sie eine ausdrückliche Entscheidung an, wenn diese
Felder im Konflikt stehen. Kombinieren Sie einen Checkpoint nicht
stillschweigend mit einem anderen Experiment.

Native Clients erstellen einen neuen Job mit `from_checkpoint` oder rufen
[`load checkpoint`](/de/api-reference/training-jobs/interactive/load-checkpoint)
für einen kompatiblen Job auf. Tinker-Clients verwenden den unterstützten
Ablauf zum Laden des Status:

```python
training_client = (
    service_client.create_training_client_from_state_with_optimizer(
        str(resume["state_path"])
    )
)
resumed_job_id = training_client.get_info().model_id
```

Diese Factory erstellt zuerst einen neuen Interactive-Job und lädt dann Gewichte
und Optimizer-Status des Quell-Checkpoints. Die neue Job-ID unterscheidet sich
normalerweise von der Quell-ID. Speichern Sie `source_job_id`, `state_path` und
`resumed_job_id` als anwendungseigene Linie. Lehnen Sie die Fortsetzung nicht
wegen unterschiedlicher IDs ab. Konstruieren Sie keine privaten
Kompatibilitäts-Unterpfade.

## 4. Grenze wiederherstellbar gestalten

Verwenden Sie diese Reihenfolge:

1. Lösen Sie die Forward-/Backward- und Optimizer-Futures auf.
2. Speichern Sie den Status-Checkpoint.
3. Persistieren Sie den Loop-Datensatz mit seiner ID.
4. Markieren Sie den Anwendungsschritt als abgeschlossen.
5. Beginnen Sie den nächsten Schritt.

Wenn der Prozess nach dem Speichern des Checkpoints, aber vor dem Persistieren
des Loop-Datensatzes beendet wird, behalten Sie den vorherigen vollständigen
Datensatz als vertrauenswürdigen Wiederherstellungspunkt. Markieren Sie einen
Schritt nicht als abgeschlossen, bevor sein Datensatz dauerhaft gespeichert ist.

## 5. Checkpoint-Arten getrennt halten

```python
state = training_client.save_state("step-000100").result()
sampler = training_client.save_weights_for_sampler(
    "step-000100",
    ttl_seconds=24 * 60 * 60,
).result()
```

Verwenden Sie einen Status-Checkpoint zur Wiederherstellung des Trainings.
Verwenden Sie einen Sampler-Checkpoint für Rollouts oder Evaluierung. Verwenden
Sie einen Sampler-Checkpoint nicht als Wiederherstellungspunkt für den
Optimizer-Status.

`ttl_seconds` ist standardmäßig `None`; ohne TTL läuft ein Checkpoint nicht
automatisch ab. Aktive Checkpoints zählen zum Checkpoint-Speicher. Für
automatische Bereinigung sind Werte von `3_600` bis `315_360_000` Sekunden
einschließlich zulässig.

Die öffentliche Training API kann interaktive Checkpoints speichern, laden,
sampeln, prüfen, löschen, veröffentlichen, die Veröffentlichung aufheben und
ihre Aufbewahrung festlegen. Die Speicherart `state` entspricht `weights`. Die
Speicherart `sampler` entspricht `sampler_weights`. Sampling aus einem
gespeicherten Sampler-Checkpoint bleibt nach dem Stoppen des Jobs möglich. Die
gemeinsamen Listen- und Downloadrouten gelten für interaktive Checkpoints. Der
Download erfordert weiterhin die Berechtigung zum Herunterladen von Gewichten.
Tinker bietet entsprechende SDK-Methoden. Konstruieren Sie keine privaten
Kompatibilitäts-Unterpfade und nehmen Sie keine undokumentierte
Aufbewahrungsdauer an.

## 6. Fortsetzung prüfen

Vor dem Skalieren des fortgesetzten Workloads:

1. Laden Sie den ausgewählten Status-Checkpoint.
2. Lesen Sie die neue ID aus `training_client.get_info().model_id`, speichern
   Sie sie als `resumed_job_id` und bestätigen Sie sie über
   `GET /v1/training/jobs/{resumed_job_id}`.
3. Führen Sie eine kleine zurückgehaltene Evaluierung aus.
4. Senden Sie ein unterstütztes Trainingsupdate.
5. Speichern Sie einen neuen Status-Checkpoint unter einem neuen Namen.
6. Persistieren Sie den nächsten Loop-Datensatz.

Verwenden Sie für interaktive Modelloperationen entweder native JSON-Routen oder das unterstützte Tinker-SDK.

## Wiederherstellungsfehler diagnostizieren

| Symptom | Prüfung |
| --- | --- |
| Ein Future schlägt fehl | Zeichnen Sie Job-ID und Operationsergebnis auf. Setzen Sie abhängigen Anwendungsstatus nicht fort |
| Ein Checkpoint kann nicht geladen werden | Prüfen Sie Job, Checkpoint-Art und den clientseitigen Wiederherstellungsdatensatz |
| Quell-Checkpoint wird abgelehnt | Prüfen Sie Quell-Job, Checkpoint-Art und `state_path`; verlangen Sie nicht, dass neue und alte Job-ID gleich sind |
| Fortgesetzter Job kann nicht abgerufen werden | Prüfen Sie, ob die ID vom fortgesetzten Client aus `get_info().model_id` stammt und dasselbe Fastino-Team authentifiziert ist |
