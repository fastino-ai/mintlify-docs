---
title: "Checkpoints und Wiederherstellung"
description: "Speichern Sie den Status eines interaktiven Jobs und den Anwendungsfortschritt und stellen Sie ihn wieder her, ohne abgeschlossene Arbeit zu wiederholen."
---

Ein Zustands-Checkpoint schützt den serverseitigen Trainingszustand. Ein
vollständiger Wiederherstellungsdatensatz schützt zusätzlich den
nutzereigenen Zustand, der Ihrem Controller sagt, was als Nächstes zu tun ist.

Die Beispiele verwenden die Helfer `call` und `wait` aus dem
[Schnellstart-Skript](/de/training/quickstart#custom-training-loop).

## Was gespeichert wird

| Datensatz | Enthält | Gespeichert von |
| --- | --- | --- |
| Zustands-Checkpoint | LoRA-Gewichte und Optimiererzustand | Fastino |
| Loop-Datensatz | Quell-Job-ID, Checkpoint-Pfad, Schritt, Dataset-Cursor, Konfiguration und Fortsetzungs-Herkunft | Ihre Anwendung |

## 1. Zustand und Loop-Fortschritt speichern

Speichern Sie den Zustand mit `save-weights`, warten Sie darauf und persistieren Sie
seinen Pfad mit den clienteigenen Feldern, die zum Fortsetzen nötig sind:

```python
import json
from pathlib import Path


state = call(
    "POST",
    f"/v1/training/jobs/{job_id}/save-weights",
    {"name": f"step-{step:06d}"},
)
wait(job_id, state["future_id"])
record = {
    "source_job_id": job_id,
    "state_path": state["path"],
    "model": model_name,
    "dataset_revision": dataset_revision,
    "optimizer": adam_params,
    "step": step,
    "dataset_cursor": dataset_cursor,
    "reward_version": reward_version,
}

with Path(log_path).open("a", encoding="utf-8") as checkpoint_log:
    checkpoint_log.write(json.dumps(record, sort_keys=True) + "\n")
```

Verwenden Sie eindeutige Checkpoint-Namen, damit jeder Loop-Datensatz einen
eindeutigen Wiederherstellungspunkt bezeichnet. Namen bestehen aus 1–128 Zeichen
aus `A-Z`, `a-z`, `0-9`, `.`, `_` und `-`.

## 2. Neuesten vollständigen Datensatz lesen

Ein Prozess kann beim Schreiben der letzten Zeile anhalten. Lesen Sie rückwärts
und überspringen Sie ein fehlerhaftes Ende:

```python
def get_last_checkpoint(log_path: str) -> dict[str, object] | None:
    path = Path(log_path)
    if not path.exists():
        return None

    for line in reversed(path.read_text(encoding="utf-8").splitlines()):
        try:
            record = json.loads(line)
        except json.JSONDecodeError:
            continue
        if isinstance(record, dict) and isinstance(record.get("state_path"), str):
            return record
    return None
```

## 3. Vor dem Laden validieren

Vergleichen Sie den Datensatz mit dem Quell-Checkpoint und der angeforderten
Fortsetzung:

- Quell-Job-ID im Checkpoint-Pfad
- Basismodell und LoRA-Konfiguration
- Dataset-Revision und Cursor
- Revision der Reward-Implementierung
- Optimierereinstellungen
- Annahmen zu Tokenizer und Chat-Template

Halten Sie für eine explizite Entscheidung an, wenn diese Felder kollidieren.
Kombinieren Sie einen Checkpoint nicht stillschweigend mit einem anderen
Experiment.

Native Clients erstellen einen neuen Job mit `from_checkpoint` oder senden
einen Zustandsnamen oder den `tinker://`-Pfad desselben Jobs an
[`load-weights`](/de/api-reference/training-jobs/interactive/load-weights).
Tinker-Clients verwenden den unterstützten Ablauf zum Laden des Status:

```python
resumed = call(
    "POST",
    "/v1/training/jobs/create-model",
    {"from_checkpoint": resume["state_path"], "load_optimizer": True},
)
wait(resumed["job_id"], resumed["future_id"])
wait(resumed["job_id"], resumed["load_future_id"])
resumed_job_id = resumed["job_id"]
```

Diese Factory erstellt zuerst einen neuen Interactive-Job und lädt dann Gewichte
und Optimizer-Status des Quell-Checkpoints. Die neue Job-ID unterscheidet sich
normalerweise von der Quell-ID. Speichern Sie `source_job_id`, `state_path` und
`resumed_job_id` als anwendungseigene Linie. Lehnen Sie die Fortsetzung nicht
wegen unterschiedlicher IDs ab. Konstruieren Sie keine privaten
Kompatibilitäts-Unterpfade.

## 4. Grenze wiederherstellbar machen

Halten Sie diese Reihenfolge ein:

1. Warten Sie, bis die Forward-Backward- und Optimiererschritt-Futures abgeschlossen sind.
2. Speichern Sie den Zustands-Checkpoint und warten Sie auf das Speicher-Future.
3. Persistieren Sie den Loop-Datensatz mit seinem Pfad.
4. Markieren Sie den Anwendungsschritt als abgeschlossen.
5. Beginnen Sie den nächsten Schritt.

Endet der Prozess nach dem Speichern des Checkpoints, aber vor dem Persistieren
des Loop-Datensatzes, behalten Sie den vorherigen vollständigen Datensatz als
vertrauenswürdigen Wiederherstellungspunkt. Markieren Sie einen Schritt erst als
abgeschlossen, wenn sein Datensatz dauerhaft gespeichert ist.

## 5. Checkpoint-Arten getrennt halten

```python
name = f"step-{step:06d}"
state = call(
    "POST",
    f"/v1/training/jobs/{job_id}/save-weights",
    {"name": name},
)
sampler = call(
    "POST",
    f"/v1/training/jobs/{job_id}/save-weights-for-sampler",
    {"name": name, "ttl_seconds": 24 * 60 * 60},
)
```

| Gespeichert mit | Pfad | Verwendung |
| --- | --- | --- |
| `save-weights` | `weights/<name>` | Trainingswiederherstellung: laden oder einen neuen Job daraus starten |
| `save-weights-for-sampler` | `sampler_weights/<name>` | Rollouts, Evaluierung und Download als PEFT-LoRA-Dateien |

Verwenden Sie keinen Sampler-Checkpoint als Wiederherstellungspunkt: Er enthält
keinen Optimiererzustand, und ein neuer Job kann nicht daraus starten.

Die öffentliche Training API speichert den Trainingszustand über
[`save-weights`](/de/api-reference/training-jobs/interactive/save-weights) und
Sampling-Gewichte über
[`save-weights-for-sampler`](/de/api-reference/training-jobs/interactive/save-sampler-weights).
Die direkten Lade- und Sampling-Routen akzeptieren einen Checkpoint-Namen oder
den `tinker://`-Pfad desselben Jobs. Sampling bleibt nach dem Stoppen des Jobs
möglich. Die gemeinsamen Listen- und Downloadrouten gelten für interaktive
Checkpoints. Der Download erfordert weiterhin die Berechtigung zum
Herunterladen von Gewichten. Tinker bietet entsprechende SDK-Methoden.
Konstruieren Sie keine privaten Kompatibilitäts-Unterpfade und nehmen Sie keine
undokumentierte Aufbewahrungsdauer an.

## 6. Fortsetzung prüfen

Bevor Sie den fortgesetzten Workload skalieren:

1. Starten Sie den neuen Job aus dem gewählten Zustands-Checkpoint.
2. Persistieren Sie seine ID als `resumed_job_id` und bestätigen Sie sie über
   `GET /v1/training/jobs/{resumed_job_id}`.
3. Führen Sie eine kleine Evaluierung auf zurückgehaltenen Daten aus.
4. Senden Sie ein Trainingsupdate.
5. Speichern Sie einen neuen Zustands-Checkpoint unter neuem Namen.
6. Persistieren Sie den nächsten Loop-Datensatz.

Verwenden Sie für interaktive Modelloperationen entweder native JSON-Routen oder das unterstützte Tinker-SDK.

## Wiederherstellungsfehler diagnostizieren

| Symptom | Prüfung |
| --- | --- |
| Ein Future schlägt fehl | Zeichnen Sie Job-ID und Operationsergebnis auf. Setzen Sie abhängigen Anwendungsstatus nicht fort |
| Ein Checkpoint kann nicht geladen werden | Prüfen Sie Job, Checkpoint-Art und den clientseitigen Wiederherstellungsdatensatz |
| Quell-Checkpoint wird abgelehnt | Prüfen Sie Quell-Job, Checkpoint-Art und `state_path`; verlangen Sie nicht, dass neue und alte Job-ID gleich sind |
| Fortgesetzter Job kann nicht abgerufen werden | Prüfen Sie, ob die ID vom fortgesetzten Client aus `get_info().model_id` stammt und dasselbe Fastino-Team authentifiziert ist |
