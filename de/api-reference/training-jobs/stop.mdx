`POST /v1/training/jobs/{job_id}/stop`

Stoppt einen laufenden Job und erhält die vor dem Stopp erstellten Checkpoints.

## Request

<ParamField header="X-API-Key" type="string" required>
  Ihr Fastino-API-Schlüssel.
</ParamField>

<ParamField path="job_id" type="string" required>
  UUID eines Config-Jobs oder ID eines interaktiven Jobs.
</ParamField>

### Config-Job

Der JSON-Body ist für einen Config-Job optional.

<ParamField body="reason" type="string">
  Grund für das Stoppen des Jobs.
</ParamField>

<ParamField body="scores" type="object">
  Numerische Metriken, auf denen die Stopp-Entscheidung basierte.
</ParamField>

<ParamField body="checkpoint" type="string">
  Checkpoint-Pfad oder -Schritt, der dem Stopp zugeordnet ist.
</ParamField>

### Interaktiver Job

Senden Sie keinen Request-Body. Die Operation gibt sofort `success`, `job_id`
und `status` zurück. Der Job nimmt keine neuen Trainingsaufrufe mehr an.
Bereits eingereihte Operationen können abgeschlossen werden, bevor Ressourcen
freigegeben werden; bis dahin kann die Nutzung weiterlaufen. Sampler-Checkpoints
bleiben für Sampling und Download verfügbar.

### Request-Beispiel für einen Config-Job

```bash cURL
curl -X POST https://api.fastino.ai/v1/training/jobs/YOUR_TRAINING_JOB_ID/stop \
  -H "X-API-Key: $FASTINO_API_KEY" \
  -H "Content-Type: application/json" \
  -d '{"reason": "Validation loss stopped improving"}'
```

### Request-Beispiel für einen interaktiven Job

```bash cURL
curl -X POST https://api.fastino.ai/v1/training/jobs/SESSION_ID:train:0/stop \
  -H "X-API-Key: $FASTINO_API_KEY"
```

## Response eines Config-Jobs

<ResponseExample>

```json Response
{
  "success": true,
  "message": "Training job stopped",
  "job_id": "YOUR_TRAINING_JOB_ID",
  "status": "stopped"
}
```

```json 202 — Abbruch ausstehend
{
  "success": true,
  "message": "Training job cancellation is still being confirmed.",
  "job_id": "YOUR_TRAINING_JOB_ID",
  "status": "stopping"
}
```

</ResponseExample>

Das Feld `message`, die `202`-Antwort, die Polling-Regel und die
Config-spezifischen Fehler gelten nur für Config-Jobs. Fragen Sie nach einer
Config-Job-Antwort `202` den Endpunkt `GET /v1/training/jobs/{job_id}` ab.
Wiederholen Sie den Stopp-Request nicht, solange der Abbruch aussteht.

## Response eines interaktiven Jobs

Ein interaktiver Stopp gibt sofort `200` zurück. Polling ist nicht nötig.

```json Interactive job
{
  "success": true,
  "job_id": "SESSION_ID:train:0",
  "status": "stopped"
}
```

## Status eines Config-Jobs

| Status | Bedeutung |
| --- | --- |
| `200` | Der Job ist gestoppt und vorhandene Checkpoints bleiben verfügbar. |
| `202` | Die Bestätigung des Anbieterabbruchs steht noch aus. |
| `400` | Die ID oder der Request des Config-Jobs ist ungültig. |
| `409 training_job_already_finished` | Der Job hat vor dem Stopp einen Endzustand erreicht. |
| `422` | Der JSON-Request-Body des Config-Jobs ist ungültig. |
