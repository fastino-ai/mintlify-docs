`GET /v1/training/jobs/{job_id}/futures/{future_id}`

Jeder Aufruf eines interaktiven Jobs, der Arbeit auslöst, gibt eine `future_id`
zurück. Fragen Sie das Future ab, bis sein `status` `completed`, `failed` oder
`cancelled` ist. Mit `wait=true` wartet jede Anfrage höchstens 25 Sekunden; nach
einem Timeout kann trotzdem ein nicht terminales Future zurückgegeben werden.
Ergebnisse werden eine Stunde lang aufbewahrt.

## Anfrage

<ParamField header="X-API-Key" type="string" required>
  Ihr Fastino-API-Schlüssel.
</ParamField>

<ParamField path="job_id" type="string" required>
  ID des interaktiven Jobs.
</ParamField>

<ParamField path="future_id" type="string" required>
  Future-ID, die beim Einreihen der Arbeit zurückgegeben wurde.
</ParamField>

<ParamField query="wait" type="boolean" default="false">
  Wartet vor der Antwort bis zu 25 Sekunden auf ein nicht abgeschlossenes
  Future. Wiederholen Sie die Anfrage, bis es abgeschlossen ist.
</ParamField>

<RequestExample>

```bash cURL
curl "https://api.fastino.ai/v1/training/jobs/$TRAINING_JOB_ID/futures/$FUTURE_ID?wait=true" \
  -H "X-API-Key: $FASTINO_API_KEY"
```

</RequestExample>

## Antwort

<ResponseField name="future_id" type="string">
  Das Future.
</ResponseField>

<ResponseField name="job_id" type="string">
  Der Job.
</ResponseField>

<ResponseField name="type" type="string">
  `create`, `load`, `forward`, `forward_backward`, `optim_step`, `save` oder `sample`.
</ResponseField>

<ResponseField name="status" type="string">
  `pending`, `running`, `completed`, `failed` oder `cancelled`.
</ResponseField>

<ResponseField name="queue_state" type="string | null">
  Solange nicht abgeschlossen: `active` oder `paused_capacity`, während GPU-Kapazität hochgefahren wird.
</ResponseField>

<ResponseField name="queue_state_reason" type="string | null">
  Eine menschenlesbare Erklärung zur Kapazität, solange `queue_state`
  `paused_capacity` ist; andernfalls `null`.
</ResponseField>

<ResponseField name="result" type="any">
  Sobald `completed`:

  - `forward` und `forward_backward`: `loss_fn_outputs` (ein Eintrag mit Tensoren
    pro Datum, etwa `logprobs`) und `metrics`.
  - `sample`: `sequences`, jeweils mit `tokens`, `logprobs` und `stop_reason`,
    sowie `prompt_logprobs`, falls angefordert.
  - `save`: der Checkpoint-Pfad.
  - Andere Typen: eine Bestätigung.
</ResponseField>

<ResponseField name="error" type="object | null">
  Bei `failed` oder `cancelled`: `message` und `category` (`user` bei einem
  Problem mit der Anfrage, `server` bei einem Problem auf Seiten von Fastino).
</ResponseField>

Die Token-Arrays im Beispielergebnis unten sind nur illustrative Platzhalter. Dekodieren Sie echte Ergebnisse mit dem Tokenizer des `base_model` des Jobs.

<ResponseExample>

```json Pending

  "queue_state_reason": null,

```


| Status | Bedeutung |
| --- | --- |
| `404` | Der Job oder das Future existiert nicht, gehört zu einem anderen Team, ist einem anderen Job zugeordnet oder sein Request-Datensatz wurde nach etwa sieben Tagen entfernt. |
| `410` | Prüfen Sie `error.message`. Eine verlorene Operation kann erneut gesendet werden. Ist das Ergebnis nach einer Stunde Aufbewahrung abgelaufen, wurde die Operation möglicherweise bereits ausgeführt; wiederholen Sie keine mutierende Operation, bevor Sie Checkpoints und den dauerhaften Loop-Datensatz abgeglichen haben. Siehe [Trainingsloop](/de/training/training-loop) und [Checkpoints](/de/training/checkpoints). |
