---

Dieses Rezept zeigt, wie Sie einen deterministischen Grader in ein Lernsignal
umwandeln. Verwenden Sie es, wenn eine Antwort durch Code geprüft werden kann,
etwa bei einer mathematischen Antwort, einem Testergebnis, einer
Schemabedingung, einer exakten Extraktion oder dem Ergebnis einer Tool-Nutzung.

Das Muster lautet:

```text
prompt -> sample a group -> grade -> center rewards -> build datums -> update
```

## Was Sie erstellen

Für jedes Problem führt der Loop Folgendes aus:

1. Mehrere mögliche Antworten aus der aktuellen Policy sampeln.
2. Jeder Antwort einen Reward von `0.0` bis `1.0` zuweisen.
3. Rewards innerhalb der Gruppe zentrieren.
4. Mit Antworten trainieren, deren Advantages nicht null sind.

Dies ist ein Update im GRPO-Stil. Es erfordert kein separates, erlerntes
Reward-Modell.

## Mit dem minimalen Rezept beginnen

Installieren Sie das getestete SDK und Cookbook:

```bash
pip install "tinker==0.32.0" "tinker-cookbook[math-rl]"
```

Konfigurieren Sie Fastino:

```bash
export FASTINO_API_KEY="fast_sk_..."
export TINKER_API_KEY="tml-${FASTINO_API_KEY}"
export TINKER_BASE_URL="https://api.fastino.ai/tinker"
```

Führen Sie das unveränderte Rezept einmal aus, bevor Sie es ändern:

```bash
python -m tinker_cookbook.recipes.rl_loop \
  base_url=https://api.fastino.ai/tinker \
  model_name=Qwen/Qwen3.6-35B-A3B \
  batch_size=4 \
  group_size=4 \
  max_steps=2 \
  log_path=./runs/reward-baseline
```

So weisen Sie nach, dass Anmeldedaten, Modellzugriff, Rendering, Sampling,
Training und Checkpointing funktionieren, bevor Ihr Grader Teil des Pfads wird.

## 1. Den Vertrag des Graders definieren

Ein nützlicher deterministischer Grader hat einen eng gefassten Vertrag:

```python
def get_reward(response: str, expected: str) -> float:
    """Return a finite reward where larger means better."""
    actual = parse_answer(response)
    if actual is None:
        return 0.0
    return 1.0 if actual == expected else 0.0
```

Halten Sie Parsing und Bewertung getrennt. Dadurch werden fehlerhafte Ausgaben
beobachtbar, statt sie als Ausnahme im Trainingsloop zu behandeln.

Für eine Aufgabe mit strukturierter Ausgabe:

```python
import json


def parse_label(response: str) -> str | None:
    try:
        value = json.loads(response)
    except json.JSONDecodeError:
        return None

    if not isinstance(value, dict):
        return None
    label = value.get("label")
    return label if isinstance(label, str) else None


def get_reward(response: str, expected: str) -> float:
    label = parse_label(response)
    return 1.0 if label == expected else 0.0
```

<Tip>
  Protokollieren Sie Parsing-Fehler getrennt von falschen, aber gültigen
  Antworten. Sie erfordern unterschiedliche Korrekturen an Prompt oder Reward.
</Tip>

## 2. Eine Gruppe aus der aktuellen Policy sampeln

Erstellen Sie zu Beginn jeder Trainingsiteration einen Sampler aus den aktuellen
Gewichten:

```python
sampling_client = training_client.save_weights_and_get_sampling_client()

future = sampling_client.sample(
    prompt=model_input,
    num_samples=group_size,
    sampling_params=sampling_params,
)
sample_result = future.result()
```

Zeichnen Sie sowohl die generierten Tokens als auch deren
Sampling-Log-Wahrscheinlichkeiten auf. Die Importance-Sampling-Loss-Funktion
benötigt beides.

## 3. Rewards in Advantages umwandeln

Bewerten Sie jede Antwort und ziehen Sie anschließend den Mittelwert der Gruppe
ab:

```python
rewards = [
    get_reward(render_response(sequence.tokens), expected)
    for sequence in sample_result.sequences
]

mean_reward = sum(rewards) / len(rewards)
advantages = [reward - mean_reward for reward in rewards]
```

Überspringen Sie Gruppen, bei denen jeder Advantage null ist:

```python
if all(advantage == 0.0 for advantage in advantages):
    continue
```

Vollständig richtige und vollständig falsche Gruppen tragen kein relatives
Signal. Verfolgen Sie ihre Rate. Eine hohe Rate degenerierter Gruppen bedeutet
in der Regel, dass die Aufgabe zu leicht oder zu schwer ist oder der Reward
nicht zwischen Ausgaben unterscheidet.

## 4. Ein Datum pro Antwort erstellen

Der Prompt ist Kontext, daher ist sein Advantage null. Die generierte Antwort
trägt den gruppenrelativen Advantage:

```python
import tinker
import torch
from tinker import TensorData


def build_datum(
    prompt: tinker.ModelInput,
    tokens: list[int],
    logprobs: list[float],
    advantage: float,
) -> tinker.Datum:
    prompt_loss_length = prompt.length - 1
    model_input = prompt.append(
        tinker.EncodedTextChunk(tokens=tokens[:-1])
    )

    target_tokens = [0] * prompt_loss_length + tokens
    padded_logprobs = [0.0] * prompt_loss_length + logprobs
    padded_advantages = (
        [0.0] * prompt_loss_length
        + [advantage] * (model_input.length - prompt_loss_length)
    )

    if not (
        model_input.length
        == len(target_tokens)
        == len(padded_logprobs)
        == len(padded_advantages)
    ):
        raise ValueError("RL datum arrays are not aligned")

    return tinker.Datum(
        model_input=model_input,
        loss_fn_inputs={
            "target_tokens": TensorData.from_torch(
                torch.tensor(target_tokens)
            ),
            "logprobs": TensorData.from_torch(
                torch.tensor(padded_logprobs)
            ),
            "advantages": TensorData.from_torch(
                torch.tensor(padded_advantages)
            ),
        },
    )
```

Verwenden Sie den Tokenizer und Renderer des ausgewählten Basismodells.
Decodieren Sie nicht mit einem Renderer und erstellen Sie die Eingaben mit
einem anderen neu.

## 5. Das Update anwenden

Fassen Sie die nicht degenerierten Gruppen in einer Datum-Liste zusammen und
übermitteln Sie anschließend das Update:

```python
if datums:
    train_future = training_client.forward_backward(
        datums,
        loss_fn="importance_sampling",
    )
    optim_future = training_client.optim_step(
        tinker.AdamParams(
            learning_rate=4e-5,
            beta1=0.9,
            beta2=0.95,
        )
    )

    train_result = train_future.result()
    optim_result = optim_future.result()
```

Das SDK ordnet diese Operationen für den Trainingsclient. Lösen Sie beide
Futures auf und zeichnen Sie ihre Metriken auf, bevor Sie mit dem nächsten
Anwendungsschritt fortfahren.

## 6. Checkpoints an sinnvollen Grenzen speichern

Speichern Sie den vollständigen Status in einem festen Rhythmus und wenn sich
der Evaluierungs-Reward verbessert:

```python
checkpoint = training_client.save_state(
    f"step-{step:06d}"
).result()
print(checkpoint.path)
```

Speichern Sie den zurückgegebenen `tinker://`-Pfad zusammen mit:

- Anwendungsschritt
- Dataset-Revision
- Revision der Reward-Implementierung
- Basismodell
- LoRA-Rang
- Optimizer-Parametern
- Evaluierungsmetriken

Anhand dieses Datensatzes kann ein Agent entscheiden, von welchem Checkpoint er
fortsetzen soll, ohne anhand von Namen raten zu müssen.

## Prüfungen des Reward-Designs

Testen Sie die Reward-Funktion vor einem langen Lauf mit einer unveränderlichen
Fixture-Sammlung.

| Prüfung | Bedeutung |
| --- | --- |
| Richtige Ausgabe erhält einen höheren Reward | Belegt die Optimierungsrichtung |
| Fehlerhafte Ausgabe bringt den Loop nicht zum Absturz | Verhindert, dass ein Rollout zum Verlust eines Batches führt |
| Gleichwertige gültige Formate werden identisch normalisiert | Verhindert versehentliche Formatierungseffekte beim Training |
| Rewards sind endlich | Verhindert ungültige Advantages |
| Ein Sample-Batch weist Reward-Varianz auf | Belegt, dass ein relatives Lernsignal vorhanden ist |
| Verdeckte Evaluierungsfälle bleiben außerhalb des Trainings | Verhindert, dass Reward-Overfitting als Fortschritt erscheint |

## Das Muster anpassen

### Codegenerierung

Führen Sie generierten Code in einer Sandbox mit begrenzten Ressourcen aus.
Belohnen Sie bestandene Tests und fügen Sie anschließend kleine, begrenzte
Komponenten für partielle Testabdeckung oder Effizienz hinzu. Führen Sie
nicht vertrauenswürdige Modellausgaben niemals im Trainingsprozess aus.

### Tool-Nutzung

Parsen Sie den Tool-Aufruf, validieren Sie sein Schema, führen Sie ihn gegen
eine isolierte Fixture aus und belohnen Sie den resultierenden Status. Bewerten
Sie das Ergebnis, nicht nur die Syntax des Aufrufs.

### Extraktion und strukturierte Ausgabe

Validieren Sie anhand eines Schemas und vergleichen Sie normalisierte Werte.
Verwenden Sie nur dann einen separaten Format-Reward, wenn die Ausgabeform
tatsächlich Teil der Aufgabe ist.

### Mehrstufige Umgebungen

Akkumulieren Sie Übergangs-Rewards zu einem Trajektorien-Reward und berechnen
Sie anschließend Advantages über Trajektorien für dasselbe Ausgangsproblem.
Isolieren Sie Umgebungsstatus und Seiteneffekte zwischen Gruppenmitgliedern.

## Einen Lauf diagnostizieren

| Signal | Interpretation | Nächste Maßnahme |
| --- | --- | --- |
| Fast jede Gruppe besteht nur aus null | Aufgabe ist möglicherweise zu schwer oder der Parser lehnt gültige Antworten ab | Prüfen Sie rohe Samples und die Rate der Parsing-Fehler |
| Fast jede Gruppe besteht nur aus eins | Aufgabe ist möglicherweise zu leicht | Erhöhen Sie die Schwierigkeit oder verwenden Sie einen strengeren Reward |
| Reward steigt, aber zurückgehaltene Qualität nicht | Reward wird ausgenutzt | Fügen Sie verdeckte Prüfungen hinzu und untersuchen Sie Fehler mit hohem Reward |
| Fehler bei Datum-Ausrichtung | Renderer, Token, Log-Wahrscheinlichkeit oder Padding stimmen nicht überein | Geben Sie die Längen für eine Antwort aus und vergleichen Sie sie mit dem Rezept |
| Loss ist instabil | Schrittgröße oder Reward-Skalierung ist möglicherweise zu groß | Senken Sie die Lernrate und begrenzen Sie Rewards |

## Abschlusskriterien

Eine erfolgreiche Anpassung umfasst:

- Mindestens eine nicht degenerierte Gruppe
- Endliche Reward-, Loss- und Optimizer-Metriken
- Eine zurückgehaltene Evaluierung unabhängig vom Trainings-Reward-Batch
- Einen wiederherstellbaren Status-Checkpoint
- Ausreichend protokollierte Metadaten, um den Lauf zu reproduzieren
