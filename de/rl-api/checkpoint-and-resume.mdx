---
title: "Checkpoint speichern und RL-Lauf fortsetzen"
description: "Speichern Sie Modell- und Optimizer-Status sowie den Loop-Fortschritt und setzen Sie RL fort, ohne abgeschlossene Arbeit zu wiederholen."
---

Ein RL-Checkpoint schützt den Modellstatus. Ein vollständiger Datensatz zur
Fortsetzung schützt außerdem den Anwendungsstatus, der Ihrem Loop vorgibt, was
als Nächstes zu tun ist.

Verwenden Sie dieses Muster für lange Jobs, unterbrechbare Orchestratoren und
von Agenten verwaltete Experimente.

## Was gespeichert werden muss

Behandeln Sie einen fortsetzbaren Schritt als zwei koordinierte Datensätze:

| Datensatz | Enthält | Gespeichert von |
| --- | --- | --- |
| Status-Checkpoint | LoRA-Gewichte und Optimizer-Status | RL API |
| Loop-Datensatz | Schritt, Dataset-Cursor, Konfiguration und Checkpoint-Pfad | Ihre Anwendung |

Wenn Sie nur den Modellstatus speichern, können Sie die Policy wiederherstellen,
der Anwendung jedoch nicht mitteilen, welche Beispiele bereits verarbeitet
wurden. Wenn Sie nur eine Schrittnummer speichern, können Sie die Policy, die
sie erzeugt hat, nicht wiederherstellen.

## Bevor Sie beginnen

Schließen Sie zuerst den [Schnellstart](/de/rl-api/quickstart) ab, um
Authentifizierung, Modellzugriff und Sampling zu prüfen. Der Schnellstart
erstellt keinen Trainingslauf. Fahren Sie erst fort, wenn Ihre freigeschaltete
Fastino-Umgebung ein kleines Trainingsupdate abschließen sowie einen
Status-Checkpoint speichern und wiederherstellen kann.

## 1. Status und Loop-Fortschritt speichern

Speichern Sie den serverseitigen Trainingsstatus und schreiben Sie anschließend
den zurückgegebenen Pfad zusammen mit den clientseitigen Feldern, die zur
Rekonstruktion des Laufs erforderlich sind, dauerhaft:

```python
import json
from pathlib import Path


state = training_client.save_state(f"step-{step:06d}").result()
record = {
    "state_path": state.path,
    "model": model_name,
    "rank": lora_rank,
    "dataset_revision": dataset_revision,
    "optimizer": optimizer_config,
    "renderer": renderer_name,
    "tokenizer": tokenizer_name,
    "step": step,
    "dataset_cursor": dataset_cursor,
    "reward_version": reward_version,
}
with Path(log_path).open("a", encoding="utf-8") as checkpoint_log:
    checkpoint_log.write(json.dumps(record, sort_keys=True) + "\n")

print(state.path)
```

Der zurückgegebene Pfad hat diese Form:

```text
tinker://<run-id>/weights/step-000100
```

Das Snippet weist keine Gültigkeitsdauer zu. Legen Sie die Aufbewahrung für
rollierende Wiederherstellungsartefakte explizit über die unterstützten
Operationen zur Checkpoint-Verwaltung fest. Bewahren Sie einen finalen
Checkpoint ohne TTL auf, wenn es sich um ein Artefakt handelt, das Sie behalten
möchten.

<Warning>
  `save_state(...)` fordert kein Überschreiben an. Die Wiederverwendung eines
  Checkpoint-Namens wird abgelehnt. `save_state(..., overwrite=True)` kann einen
  Status-Checkpoint ausdrücklich ersetzen, aber eindeutige Namen sind sicherere
  Wiederherstellungsmarker.
</Warning>

## 2. Den neuesten aufgezeichneten Fortsetzungspunkt finden

Durchsuchen Sie beim Prozessstart die lokalen Datensätze rückwärts nach dem
neuesten lesbaren Datensatz, der einen Statuspfad enthält. Ein Prozess kann
während des Schreibens der letzten JSONL-Zeile beendet werden. Überspringen Sie
daher eine fehlerhafte letzte Zeile, statt den vorherigen
Wiederherstellungspunkt zu verlieren:

```python
def get_last_checkpoint(log_path: str) -> dict[str, object] | None:
    path = Path(log_path)
    if not path.exists():
        return None
    for line in reversed(path.read_text(encoding="utf-8").splitlines()):
        try:
            record = json.loads(line)
        except json.JSONDecodeError:
            continue
        if isinstance(record, dict) and isinstance(record.get("state_path"), str):
            return record
    return None


resume = get_last_checkpoint(log_path)
```

Behandeln Sie beide Pfade explizit:

```python
if resume is None:
    training_client = service_client.create_lora_training_client(
        base_model=model_name,
        rank=lora_rank,
    )
    start_step = 0
    dataset_cursor = 0
else:
    saved_step = resume.get("step")
    saved_cursor = resume.get("dataset_cursor")
    if not isinstance(saved_step, int) or not isinstance(saved_cursor, int):
        raise ValueError("resume record has no valid step or dataset cursor")

    training_client = (
        service_client.create_training_client_from_state_with_optimizer(
            str(resume["state_path"])
        )
    )
    start_step = saved_step + 1
    dataset_cursor = saved_cursor
```

`create_training_client_from_state_with_optimizer(...)` erstellt aus den
gespeicherten Gewichten und dem Optimizer-Status einen neuen geordneten
Trainingslauf.

## 3. Datensatz zur Fortsetzung validieren

Vergleichen Sie den gespeicherten Loop-Datensatz mit dem angeforderten Lauf,
bevor das Training fortgesetzt wird:

```python
if resume is not None and resume.get("reward_version") != reward_version:
    raise ValueError(
        "reward implementation changed; start a new run or approve the change"
    )
```

Validieren Sie mindestens:

- Basismodell
- LoRA-Rang und trainierbares Layout
- Dataset-Revision und -Cursor
- Revision der Reward-Implementierung
- Optimizer-Familie und vorgesehener Zeitplan
- Annahmen zu Renderer und Tokenizer

Ein Agent sollte anhalten und um eine Entscheidung bitten, wenn diese Felder
einander widersprechen. Er sollte einen Checkpoint nicht stillschweigend mit
einem anderen Experiment kombinieren.

## 4. Die Schrittgrenze atomar gestalten

Verwenden Sie diese Reihenfolge:

1. Trainings- und Optimizer-Futures auflösen.
2. Den Status-Checkpoint speichern.
3. Den Loop-Datensatz mit dem zurückgegebenen Pfad dauerhaft speichern.
4. Den Anwendungsschritt als abgeschlossen markieren.
5. Den nächsten Schritt beginnen.

Wenn der Prozess nach Schritt 2, aber vor Schritt 3 beendet wird, kann der
Server einen Checkpoint ohne Referenz enthalten. Dies verschwendet Speicher,
beschädigt aber nicht den vorherigen Fortsetzungspunkt. Bei einer späteren
Bereinigung kann er gelöscht werden.

Markieren Sie einen Schritt nicht als abgeschlossen, bevor der Checkpoint-Pfad
dauerhaft gespeichert ist.

## 5. Sampler-Artefakte getrennt halten

Verwenden Sie einen Status-Checkpoint, um das Training fortzusetzen:

```python
state = training_client.save_state("step-000100").result()
```

Verwenden Sie Sampler-Gewichte für Evaluierung, Rollouts oder SDK-Inferenz:

```python
sampler = training_client.save_weights_for_sampler(
    "step-000100"
).result()
```

Die beiden Pfade haben unterschiedliche Zwecke:

```text
tinker://<run-id>/weights/<name>
tinker://<run-id>/sampler_weights/<name>
```

Wählen Sie keinen Sampler-Checkpoint als Fortsetzungspunkt für den Optimizer.

## 6. Speicher begrenzen

Eine praktische Aufbewahrungsrichtlinie verwendet:

- Kurzlebige rollierende Status-Checkpoints zur Wiederherstellung nach Abstürzen
- Längerlebige regelmäßige Status- und Sampler-Checkpoints für Vergleiche
- Einen dauerhaften finalen Checkpoint

Implementieren Sie die Aufbewahrung in Ihrer Anwendung, indem Sie eindeutige
Checkpoint-Namen vergeben, über unterstützte Checkpoint-Operationen explizite
TTLs festlegen und Artefakte löschen, die nicht mehr in Ihrem
Wiederherstellungs- oder Evaluierungsfenster liegen. Checkpoint-Speicher wird
über die Zeit gemessen.

## Wiederherstellungsentscheidungen für Agenten

| Situation | Maßnahme |
| --- | --- |
| Kein lokaler Datensatz zur Fortsetzung | Einen neuen Lauf starten |
| Datensatz zur Fortsetzung und Checkpoint sind vorhanden | Metadaten validieren und anschließend wiederherstellen |
| Lokaler Datensatz ist vorhanden, aber Checkpoint fehlt | Anhalten und den Benutzer fragen; nicht annehmen, dass ein früherer Datensatz zum beabsichtigten Lauf gehört |
| Checkpoint ist ohne lokalen Datensatz vorhanden | Als nicht klassifiziert behandeln; Dataset-Cursor nicht erraten |
| Reward- oder Dataset-Revision hat sich geändert | Neues Experiment starten, sofern der Benutzer die Fortsetzung nicht genehmigt |
| Live-Lauf meldet nicht wiederherstellbaren Status | Vom neuesten expliziten Status-Checkpoint wiederherstellen |

## Den fortgesetzten Lauf prüfen

Vor einer umfangreichen Fortsetzung:

1. Den Checkpoint wiederherstellen.
2. Eine kleine zurückgehaltene Evaluierung ausführen.
3. Sie mit der beim Speichern aufgezeichneten Metrik vergleichen.
4. Einen Trainingsschritt übermitteln.
5. Einen neuen Checkpoint unter einem neuen Namen speichern.

Exakte Samples können variieren. Das wiederhergestellte Modell sollte die
erwartete Qualität beibehalten, der Optimizer-Schritt sollte abgeschlossen
werden und der neue Checkpoint sollte adressierbar sein.

Schließen Sie den Service-Client immer. Erfassen Sie das Ergebnis korrekt:

```python
service_client.close("success").result()  # completed run
```

Verwenden Sie `errored`, wenn eine Ausnahme weitergegeben wird, und
`interrupted` nach einem Abbruch oder Herunterfahren. Kennzeichnen Sie eine
fehlgeschlagene Wiederherstellung nicht als erfolgreich.

Den vollständigen Lebenszyklus und die administrativen Operationen finden Sie
in der [Referenz zu Laufzeitverhalten und Fehlern](/de/rl-api/runtime).
