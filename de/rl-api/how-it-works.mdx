Die RL API trennt das Lernprogramm vom Modell-Compute. Ihr Prozess entscheidet,
was gesampelt, wie es bewertet und wann es aktualisiert wird. Fastino führt
Sampling, Forward- und Backward-Passes, Optimierungsschritte und
Checkpoint-Operationen aus.

## Der Kontrollloop

<Steps>
  <Step title="Trainingsclient erstellen">
    Wählen Sie ein unterstütztes Basismodell und einen LoRA-Rang. Der Client
    repräsentiert einen geordneten Trainingslauf mit eigenen Gewichten, eigenem
    Optimizer-Status und eigener Operationssequenz.
  </Step>
  <Step title="Snapshot der aktuellen Policy für das Sampling erstellen">
    Rufen Sie `save_weights_and_get_sampling_client()` auf. Rollouts sollten von
    der Policy stammen, die Sie als Nächstes verbessern möchten, nicht von
    unabhängigen oder veralteten Gewichten.
  </Step>
  <Step title="Rollout-Gruppen sammeln">
    Senden Sie denselben Prompt mehrfach oder fordern Sie mehrere Samples in
    einem Aufruf an. Eine Gruppe bietet der Reward-Funktion Alternativen zum
    Vergleich für dasselbe Problem.
  </Step>
  <Step title="Rewards und Advantages berechnen">
    Bewerten Sie jede Antwort. Wandeln Sie anschließend Rewards in Advantages
    um. Subtrahieren Sie in einem Loop im GRPO-Stil den mittleren Reward der
    Gruppe vom Reward jeder Antwort.
  </Step>
  <Step title="Trainings-Datums erstellen">
    Kombinieren Sie Prompt-Tokens, Tokens der gesampelten Antwort,
    Sampling-Log-Wahrscheinlichkeiten und Advantages auf Token-Ebene.
    Prompt-Tokens erhalten normalerweise einen Advantage von null.
  </Step>
  <Step title="Policy aktualisieren">
    Übermitteln Sie die Datums mit `forward_backward(...,
    loss_fn="importance_sampling")` und rufen Sie anschließend
    `optim_step(...)` auf.
  </Step>
  <Step title="Checkpoint speichern und wiederholen">
    Speichern Sie an sinnvollen Grenzen einen dauerhaften Status, erstellen Sie
    aus den aktualisierten Gewichten einen neuen Sampling-Client und beginnen
    Sie die nächste Iteration.
  </Step>
</Steps>

## Client-Objektmodell

| Objekt | Verantwortlichkeit | Typische Lebensdauer |
| --- | --- | --- |
| `ServiceClient` | Öffnet eine Sitzung, meldet Funktionen, erstellt Trainings- und Sampling-Clients und stellt den REST-Client bereit | Ein logischer Anwendungslauf |
| `TrainingClient` | Verwaltet einen geordneten LoRA-Trainingslauf und dessen Optimizer-Status | Eine Policy, die trainiert wird |
| `SamplingClient` | Sampelt oder berechnet Log-Wahrscheinlichkeiten aus einem Basismodell oder gespeicherten Gewichten | Ein Policy-Snapshot oder wiederverwendbarer Checkpoint |
| `RestClient` | Listet Läufe und Checkpoints auf, verwaltet Sichtbarkeit und Aufbewahrung und meldet die Speichernutzung | Administrative Operationen |
| Future | Verfolgt eine übermittelte Operation und gibt ihr Ergebnis zurück | Eine Operation |

Das Schließen eines `ServiceClient` beendet die Sitzung und gibt ihre aktiven
Trainingsläufe frei. Checkpoints werden dadurch nicht gelöscht.

## Warum gruppierte Rewards funktionieren

Angenommen, vier Antworten auf einen Prompt erhalten diese Rewards:

```text
[1.0, 0.0, 1.0, 0.0]
```

Der mittlere Reward ist `0.5`; daraus ergeben sich diese gruppenrelativen
Advantages:

```text
[0.5, -0.5, 0.5, -0.5]
```

Positive Werte verstärken Tokens aus Antworten, deren Bewertung über dem
Gruppendurchschnitt lag. Negative Werte verringern die Wahrscheinlichkeit von
Antworten unter dem Durchschnitt.

Wenn jede Antwort denselben Reward erhält, ist jeder zentrierte Advantage null.
Diese Gruppe trägt kein relatives Lernsignal und kann übersprungen werden.

## Inhalt eines Datums

Für den üblichen Importance-Sampling-Loop enthält jedes Datum:

- Den Prompt, gefolgt von der gesampelten Vervollständigung
- Ziel-Tokens, die am Modelleingang ausgerichtet sind
- Während des Samplings aufgezeichnete Log-Wahrscheinlichkeiten
- Auf die Tokens der Vervollständigung angewendete Advantages

Das Prompt-Präfix ist Kontext und keine von der Policy ausgewählte Aktion.
Setzen Sie seine Advantage-Werte auf null. Wenden Sie den Advantage der Antwort
auf die Positionen der generierten Tokens an.

<Warning>
  Token-Arrays müssen die vom Renderer und SDK erwarteten Längen haben.
  Verwenden Sie den Renderer erneut, der zum ausgewählten Basismodell gehört.
  Ein Formatter eines anderen Modells kann falsche Stoppsequenzen oder eine
  fehlerhafte Token-Ausrichtung erzeugen.
</Warning>

## Geordnete und idempotente Updates

Ein Trainingslauf ist eine geordnete Zustandsmaschine. Das SDK weist
Operationen wie Forward- und Backward-Passes, Optimierungsschritten,
Speicherungen und Ladevorgängen Sequenz-IDs zu.

Wird eine Anfrage mit demselben Lauf, derselben Sequenz-ID und demselben Body
wiederholt, gibt die RL API die ursprüngliche Operation zurück, statt sie
zweimal anzuwenden. Die Wiederverwendung dieser Sequenz-ID mit einem anderen
Body wird abgelehnt. Dies schützt den Optimizer-Status, wenn ein Client nach
einer Netzwerkunterbrechung einen erneuten Versuch unternimmt.

Übermitteln Sie Operationen für einen Trainingsclient nicht aus unabhängigen
Prozessen, sofern diese keinen gemeinsamen Ordnungsmechanismus verwenden.

## Live-Status und dauerhafter Status

Trainingsgewichte, ausstehende Gradienten und Optimizer-Status sind Live-Status.
Die RL API kann versuchen, einen Lauf nach einem Scale-down bei Inaktivität oder
einer Infrastrukturunterbrechung zu rekonstruieren. Die automatische
Wiederherstellung beginnt mit einer Replay-Basis und spielt protokollierte
Mutationen von `forward_backward` und `optim_step` erneut ab. Sie spielt nicht
jede API-Operation erneut ab, und die Wiederherstellung kann fehlschlagen, wenn
das Ergebnis einer Mutation unbekannt ist oder erforderliche Replay-Daten nicht
mehr verfügbar sind.

Ihre expliziten Checkpoints sind die von Ihnen kontrollierte
Wiederherstellungsgrenze:

- `save_state(name)` speichert Trainingsgewichte und Optimizer-Status.
- `save_weights_for_sampler(name)` speichert Gewichte für das Sampling.
- `create_training_client_from_state_with_optimizer(path)` startet einen neuen Lauf mit den gespeicherten Gewichten und dem Optimizer-Status.
- `create_training_client_from_state(path)` startet einen Lauf aus den gespeicherten Gewichten mit einem neuen Optimizer.
- `load_state(path)` stellt einen kompatiblen Checkpoint in einem bestehenden Lauf wieder her.

Speichern Sie den Status vor längeren externen Arbeiten, vor einer riskanten
Codeänderung und an Meilensteinen, die Sie möglicherweise vergleichen oder
fortsetzen möchten.

## Kostengrenzen

Sampling wird anhand von Eingabe-, gecachten Eingabe- und Ausgabe-Tokens
gemessen. Forward- und Forward-Backward-Operationen werden anhand von
Trainings-Tokens gemessen. Checkpoint-Speicher wird über die Zeit gemessen.

Das Erstellen eines Modellclients, die Anwendung eines Optimierungsschritts und
das Speichern oder Laden eines Checkpoints verursachen für sich genommen keine
zusätzliche Token-Nutzung. Die Token-Arbeit und gespeicherten Bytes bestimmen
weiterhin die zugehörige Nutzung.

## Ein zuverlässiges Produktionsmuster

1. Fragen Sie beim Start die Serverfunktionen ab.
2. Pinnen Sie eine von Ihrer Anwendung getestete SDK-Version.
3. Führen Sie die Rollout-Generierung parallel aus, halten Sie Trainingsupdates jedoch geordnet.
4. Zeichnen Sie den Checkpoint-Pfad und den Anwendungsschritt gemeinsam auf.
5. Verwenden Sie begrenzte Wiederholungsversuche beim Abrufen von Future-Ergebnissen.
6. Schließen Sie den Service-Client in einem `finally`-Block.
7. Bewahren Sie nur die benötigten Checkpoints auf.

Eine konkrete Erstellung von Datums und einen deterministischen Grader finden
Sie im [Rezept für verifizierbare Rewards](/de/cookbooks/rl-verifiable-rewards).
