```text
POST https://api.fastino.ai/v1/systemone
```

Il s'agit de l'endpoint d'inférence de **GLiDE**. Envoyez un `state` non vide et une ou plusieurs `questions`
nommées et typées ; lisez les décisions structurées dans `answers`. GLiDE n'utilise pas
`/v1/chat/completions`, `messages` ni un `schema` GLiNER.

## Configurez votre clé d'API

1. **Créez un compte [Fastino](https://agent.fastino.ai/)**
2. **Obtenez votre clé d'API** depuis [Settings](https://agent.fastino.ai/api-keys)

Définissez votre clé comme variable d'environnement afin que les exemples ci-dessous fonctionnent tels quels :

<CodeGroup>

```bash macOS/Linux
export FASTINO_API_KEY="your_api_key_here"
```

```powershell Windows
setx FASTINO_API_KEY "your_api_key_here"
```

</CodeGroup>

## Choisir un type de question

Chaque question n'accepte qu'un seul libellé et renvoie des probabilités. Choisissez la primitive selon la
forme de réponse dont votre code a besoin :

| Primitive | À utiliser lorsque | Forme de `criteria` | Résultat principal |
| --- | --- | --- | --- |
| [Noul](/fr/concepts/glide-noul) | La réponse est oui ou non | `{"true": "...", "false": "..."}` facultatif ; Yes/No par défaut | `noul`, la probabilité de true |
| [Choice](/fr/concepts/glide-choice) | Une seule option non ordonnée doit l'emporter | Objet associant des clés d'option à des descriptions | `choice` plus `probabilities` |
| [Score](/fr/concepts/glide-score) | La réponse se situe sur une échelle ordonnée | Tableau ordonné de descriptions de niveaux | `score`, `expected_level` et `probabilities` |

Il n'existe pas de primitive multi-libellé. Posez plusieurs questions nommées indépendamment dans une même requête
lorsque vous avez besoin de plusieurs jugements sur le même state.

## Requête

<ParamField body="model" type="string" required>
  Utilisez `fastino/GLiDE`. La réponse renvoie le nom du moteur sous la forme `glide`.
</ParamField>

<ParamField body="state" type="string | object | array" required>
  La situation non vide à évaluer. Utilisez une chaîne pour un passage unique, un objet pour des champs
  étiquetés, ou un tableau pour une séquence ordonnée de messages ou d'enregistrements.
</ParamField>

<ParamField body="questions" type="object" required>
  Un objet non vide dont les clés sont des noms que vous choisissez. Chaque valeur doit contenir `type` et
  `instructions` ; Choice et Score exigent également `criteria`. Les mêmes clés apparaissent sous
  `answers` dans la réponse.
</ParamField>

### Requête complète

```bash
curl --max-time 300 -s https://api.fastino.ai/v1/systemone \
  -H "X-API-Key: $FASTINO_API_KEY" \
  -H "Content-Type: application/json" \
  -d '{
    "model": "fastino/GLiDE",
    "state": "Refund request: the receipt is attached, the purchase was 10 days ago, and refunds are allowed within 30 days.",
    "questions": {
      "refund_allowed": {
        "type": "noul",
        "instructions": "Does this request qualify for a refund?",
        "criteria": { "true": "Qualifies", "false": "Does not qualify" }
      }
    }
  }'
```

## Réponse

```json
{
  "model": "glide",
  "answers": {
    "refund_allowed": {
      "type": "noul",
      "noul": 0.99767683794902,
      "confidence": 0.9953536758980399
    }
  },
  "usage": { "input_tokens": 89, "output_tokens": 1 },
  "token_usage": 90
}
```

`answers` utilise les clés de question de votre requête. Pour ce Noul :

- `noul` est la probabilité que le critère `true` soit vérifié. Ce n'est pas un booléen.
- `confidence` est la certitude quant à l'un ou l'autre résultat : `|2 × noul − 1|`.
- Ajustez les seuils d'action sur des données représentatives. Ne supposez pas que `0.5` est le bon seuil
  métier.

`token_usage` est le nombre total de tokens facturés, soit
`usage.input_tokens` plus `usage.output_tokens`.

Choice et Score renvoient des champs différents. Consultez leurs pages de primitive pour les formes de réponse exactes
et des exemples d'intégration.

## Limites et formes non prises en charge

- Chaque prompt de question rendu (`state` plus cette question) doit tenir dans **40 000
  tokens**.
- Choice exige **2 à 255 options** ; une option unique ne peut représenter ni une décision ni un écart de confiance significatif. Score accepte au maximum **255 niveaux**.
- `usage.input_tokens` additionne les passes internes de toutes les questions ; il peut donc dépasser 40 000
  même si chaque prompt rendu individuellement tient dans la limite.
- Une requête évalue un seul `state` partagé ; placez plusieurs questions sous `questions`.
- `/v1/systemone` ne prend pas en charge le streaming et n'accepte pas de lot d'états indépendants.
- GLiDE ne prend pas encore en charge les identifiants de déploiements affinés.

Consultez la [référence GLiDE](/fr/concepts/decision-models) pour des conseils sur les formes de state, les formules
de confiance et une requête mêlant Choice et Score.

## Migrer depuis TypeSafe

Jev de TypeSafe et GLiDE de Fastino utilisent la même structure System One : un `state`, des
`questions` nommées et les `answers` correspondantes. La plupart des requêtes se transposent sans difficulté, mais
l'intégration n'est pas un simple remplacement direct. Suivez cette liste de contrôle pour migrer en toute sécurité :

| TypeSafe ou Jev | Fastino GLiDE |
| --- | --- |
| `https://api.typesafe.ai/v1/systemone` | `https://api.fastino.ai/v1/systemone` |
| `TYPESAFE_API_KEY` | `FASTINO_API_KEY` |
| `Authorization: Bearer $TYPESAFE_API_KEY` | `X-API-Key: $FASTINO_API_KEY` |
| Modèle de requête `jev-latest` | Modèle de requête `fastino/GLiDE` |
| Identifiant de modèle Jev dans la réponse | Modèle de réponse `glide` |
| Client du SDK TypeSafe | Votre client HTTP appelant `/v1/systemone` |
| Nouvelles tentatives sur `429` et `529` | Nouvelles tentatives sur `425`, `429` et `503` avec un backoff borné |

<Steps>
  <Step title="Conserver la structure de requête System One">
    Préservez le `state` non vide, les clés de question et les types de primitive. GLiDE exige que chaque
    valeur `instructions` soit une chaîne non vide ; convertissez donc les instructions omises, nulles, objets ou
    tableaux en texte clair. Conservez les critères Choice sous forme d'objet. Les critères Noul sont
    facultatifs, mais leurs valeurs `true` et `false` doivent être des chaînes. Privilégiez un tableau ordonné
    pour les critères Score.
    N'envoyez que les champs de requête documentés dont votre intégration a besoin. Les champs de premier niveau non pris en charge
    renvoient `422` ; ne copiez donc pas d'options arbitraires du client TypeSafe dans le corps JSON.
  </Step>
  <Step title="Changer l'endpoint, l'identifiant et le modèle">
    Dirigez la requête vers Fastino, lisez `FASTINO_API_KEY`, envoyez-la avec `X-API-Key` et définissez
    `model` sur `fastino/GLiDE`. Fastino accepte aussi l'en-tête Bearer si conserver ce style
    simplifie une migration HTTP directe. Attendez-vous à `model: "glide"` dans la réponse.
  </Step>
  <Step title="Mettre à jour le traitement des réponses Score">
    Le `score` de TypeSafe est un nombre à virgule flottante pondéré par les probabilités. Son équivalent GLiDE est
    `expected_level`. Le `score` de GLiDE est en revanche l'indice entier du niveau le plus probable.
    GLiDE renvoie les descriptions de la légende Score sous forme de chaînes ; mettez donc à jour les consommateurs qui attendent
    des valeurs de légende structurées.
    Pour les requêtes Score, GLiDE accepte aussi des objets de critères avec des clés numériques sous forme de chaîne, comme
    `{"1": "low", "3": "medium", "5": "high"}`. Les clés sont triées puis ignorées, et la
    réponse est réindexée de `0` à `N-1`. Utilisez un tableau ordonné lorsque les valeurs numériques d'origine
    ne doivent pas être confondues avec les indices de niveau renvoyés.
  </Step>
  <Step title="Vérifier les clés de niveau et le comportement des nouvelles tentatives">
    GLiDE renvoie les `probabilities` et la `legend` de Score avec des clés de type chaîne, comme `"0"` et `"1"`.
    La réponse HTTP brute de TypeSafe fait de même, mais son SDK Python peut exposer des clés entières.
    Convertissez les clés uniquement si l'application a besoin de maps à clés entières. Remplacez la gestion des
    nouvelles tentatives sur `529` de TypeSafe par la gestion de `425` et `503` de Fastino, et conservez un backoff borné pour
    `429`. Respectez `Retry-After` lorsqu'il est présent et appliquez le même budget de nouvelles tentatives aux
    défaillances de transport.
  </Step>
  <Step title="Revalider les seuils de décision">
    Gardez les actions métier existantes intactes pendant le portage, puis testez GLiDE sur des cas
    représentatifs avant le déploiement. Ne supposez pas que des seuils calibrés pour Jev se transposent tels quels
    à un modèle différent.
  </Step>
</Steps>

<Warning>
  Ne faites pas correspondre le `score` à virgule flottante de TypeSafe au `score` de GLiDE. Lisez
  `answers.&lt;key&gt;.expected_level` lorsque le code existant attend un score pondéré. Lisez
  `answers.&lt;key&gt;.score` uniquement lorsque le code a besoin de l'indice du seul niveau gagnant.
</Warning>

### Remplacer l'utilisation du SDK TypeSafe

Si le projet utilise un SDK TypeSafe :

1. Recherchez `typesafe-sdk`, `@typesafe-ai/sdk`, `TypeSafeClient`, `AsyncTypeSafeClient` et les
   constructeurs de questions TypeSafe dans les manifestes, les imports, le code applicatif et les tests.
2. Remplacez les constructeurs du SDK et l'accès typé aux réponses par le client HTTP du projet et le
   JSON décodé.
3. Supprimez les packages et imports TypeSafe uniquement lorsqu'il ne reste plus aucune référence.

Les règles d'endpoint, de validation, de nouvelles tentatives et de Score ci-dessus s'appliquent toujours.

## Erreurs

Une première requête vers un modèle à froid peut renvoyer `425 model_warming` pendant son préchauffage ; réessayez
après environ 60 secondes.

| Statut | Cause probable | Action |
| --- | --- | --- |
| `400` | Le prompt dépasse la fenêtre de contexte ou une autre entrée d'inférence est invalide | Raccourcissez le state ou corrigez la question |
| `401` | Clé d'API manquante, mal formée ou invalide | Exportez une clé `fast_sk_...` valide |
| `402` | Crédits insuffisants, financement requis ou plafond de dépense quotidien/mensuel défini par le propriétaire | Ajoutez des crédits ou ajustez le plafond de dépense |
| `403` | Refus lié au moyen de paiement, à la vérification de la carte, au plafond de crédit ou à la politique du compte | Résolvez l'exigence de facturation ou de compte |
| `404` | Modèle inconnu ou modèle ne prenant en charge que les chat completions | Utilisez `fastino/GLiDE` |
| `422` | Un champ obligatoire est manquant, une valeur a une forme incorrecte ou un champ supplémentaire a été envoyé | Lisez et corrigez les détails de validation au niveau du champ |
| `425` | Le déploiement est en cours de préchauffage | Retentez après le délai indiqué |
| `429` | Limite de débit ou de capacité | Respectez `Retry-After` et retentez avec un backoff |
| `503` | Défaillance temporaire du fournisseur ou du service | Retentez avant de considérer l'erreur comme définitive |

Utilisez un délai de lecture d'au moins 300 secondes et un backoff borné pour `425`, `429` et `503`.
Ne retentez pas `401`, `402`, `403`, `404` ou `422` sans corriger le problème sous-jacent.
