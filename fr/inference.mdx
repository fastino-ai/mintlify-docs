Fastino propose deux interfaces d'inférence synchrones. Choisissez celle qui correspond à vos
besoins :

| Fonctionnalité | [`/v1/chat/completions`](/fr/inference/chat-completions) | [`/v1/systemone`](/fr/inference/systemone) |
| --- | --- | --- |
| Modèle | Sélectionnez un modèle de base compatible avec l'inférence ou l'UUID d'une tâche d'entraînement terminée | Utilise toujours `fastino/glide` |
| Requête | `model` et `messages` compatibles OpenAI, plus le `schema` de premier niveau de Fastino | `state` natif plus une ou plusieurs `questions` typées |
| Réponse | Enveloppe chat-completion OpenAI ; analysez `choices[0].message.content` en tant que JSON | Corps natif `{ "answers": ..., "usage": ... }` |
| Entrée par lots | Une conversation par requête | Un `state` par requête, avec plusieurs `questions` évaluées ensemble |
| Idéal pour | Extraction, classification, extraction structurée et relations, sur les modèles de base et affinés | Décisions de classification, de routage et de scoring avec des probabilités calibrées |

<Tip>
  Utilisez [`/v1/chat/completions`](/fr/inference/chat-completions) pour l'extraction, la
  classification, l'extraction structurée ou les relations. Utilisez
  [`/v1/systemone`](/fr/inference/systemone) pour les décisions structurées (classification,
  routage, scoring) plutôt que pour l'extraction.
</Tip>

Cette page couvre ce qui est commun aux deux interfaces. Consultez
[`/v1/chat/completions`](/fr/inference/chat-completions) pour le contrat de requête et de réponse
GLiNER et les instructions de migration depuis l'API héritée, ou
[`/v1/systemone`](/fr/inference/systemone) pour le contrat HTTP de GLiDE ; les formes complètes
de requête et de réponse Noul, Choice et Score sont décrites dans
[Modèles de décision](/fr/concepts/decision-models). L'utilisation du SDK, l'entraînement des
modèles, l'évaluation, l'historique d'inférence et le feedback sortent du cadre de cette page.

## Authentification

Envoyez une clé d'API Fastino avec chaque requête, quelle que soit l'interface :

```bash
export FASTINO_API_KEY="fast_sk_..."
```

```http
Authorization: Bearer $FASTINO_API_KEY
Content-Type: application/json
```

## Démarrages à froid et nouvelles tentatives

Un modèle inactif ou récemment déployé peut subir un démarrage à froid, quelle que soit
l'interface. Utilisez un délai de lecture d'au moins 300 secondes et retentez les réponses
`425`, `429` et `503`. Respectez l'en-tête de réponse `Retry-After` lorsqu'il est présent.

Une requête expirée peut tout de même réchauffer le déploiement, permettant à la requête
suivante d'aboutir. Ne retentez pas les erreurs d'authentification, de facturation, de
validation ou de modèle inconnu sans corriger le problème sous-jacent.

```bash
curl --max-time 300 -X POST "https://api.fastino.ai/v1/chat/completions" \
  -H "Authorization: Bearer $FASTINO_API_KEY" \
  -H "Content-Type: application/json" \
  -d @request.json
```

Le même schéma de délai et de nouvelles tentatives s'applique à `/v1/systemone`.

## Erreurs

Les deux interfaces partagent les mêmes codes de statut pour l'authentification, la
facturation, la validation, la limitation de débit et les démarrages à froid. Quelques codes
diffèrent légèrement selon l'interface : par exemple, `/v1/systemone` ne prend pas encore en
charge les déploiements affinés, donc son cas `409` ne s'applique pas. Consultez le tableau
exact sur la page de chaque endpoint : [erreurs de
`/v1/chat/completions`](/fr/inference/chat-completions#erreurs) ou [erreurs de
`/v1/systemone`](/fr/inference/systemone#erreurs).
