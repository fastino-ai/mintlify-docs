---
title: "Migrer depuis Tinker"
description: "Migrez un workload compatible utilisant le SDK Tinker vers les jobs d'entraînement interactifs Fastino."
---

Fastino prend en charge un sous-ensemble défini du SDK `tinker` comme interface
client pour les jobs d'entraînement interactifs. Un client d'entraînement migré
est un job Fastino dans `/v1/training/jobs` ; son ID de modèle SDK et son ID de
job Fastino canonique sont identiques.

Deux options s'offrent à vous :

- **Conserver le SDK.** Pointez `tinker` vers l'URL de base de compatibilité de
  Fastino et authentifiez-vous avec une clé API Fastino. Suivez les étapes 1 à 4.
- **Passer aux routes natives.** Appelez les routes REST de Fastino en JSON avec
  la même clé API. Consultez [Passer aux routes natives](#switch-to-the-native-routes).

Considérez votre programme existant comme le test d'acceptation. Modifiez la
connexion, vérifiez chaque opération et exécutez un petit test de fumée avant de
rétablir les tailles de workload de production.

## 1. Épingler le paquet testé

<CodeGroup>

```bash uv
uv add "tinker==0.32.0"
```

```bash pip
pip install "tinker==0.32.0"
```

</CodeGroup>

## 2. Remplacer le point de terminaison et l'authentification

<CodeGroup>

```bash macOS/Linux
export FASTINO_API_KEY="fast_sk_..."
export TINKER_BASE_URL="https://api.fastino.ai/v1/training/compat/tinker"
export TINKER_CREDENTIAL_CMD='printf "%s\n" "$FASTINO_API_KEY"'
```

```powershell Windows
$env:FASTINO_API_KEY = "fast_sk_..."
$env:TINKER_BASE_URL = "https://api.fastino.ai/v1/training/compat/tinker"
$env:TINKER_CREDENTIAL_CMD = 'powershell -NoProfile -Command "[Console]::Out.WriteLine($env:FASTINO_API_KEY)"'
```

</CodeGroup>

`TINKER_CREDENTIAL_CMD` est exécuté à chaque demande de token et doit afficher
un identifiant non vide. Utilisez une clé Fastino `fast_sk_` normale ; les
identifiants `tml-` sont rejetés. Ne définissez pas `TINKER_API_KEY`.

Vérifiez la connexion avant de modifier quoi que ce soit d'autre :

```python
import tinker

service_client = tinker.ServiceClient()
print(service_client.get_server_capabilities())
```

## 3. Vérifier le workload

1. Interrogez `ServiceClient.get_server_capabilities()` et choisissez un modèle
   de base disponible. Conservez le nom de paramètre SDK `base_model`.
2. Comparez chaque méthode de votre code avec le
   [comportement du client pris en charge](#supported-client-behavior).
3. Supprimez les dépendances à la récupération par lots des futures, à
   l'exportation de poids externes ou aux URL de poids externes.
4. Conservez dans votre application le rendu des prompts, la logique de
   récompense, la mise en lots, l'évaluation et les critères d'arrêt.

Capabilities liste uniquement les modèles activés et leurs longueurs de
contexte. Il n'énumère pas les rangs LoRA, optimiseurs, pertes, méthodes
facultatives ou limites d'opération. Fastino accepte actuellement les rangs LoRA
de 1 à 32, utilise `adamw` à la création et prend en charge `cross_entropy`,
`importance_sampling`, `ppo`, `cispo` et `dro`. Le service actif valide ces
réglages lors de leur soumission.

## 4. Exécuter un test de fumée

Utilisez les plus petits datums valides et les paramètres d'optimisation de
votre workload existant pour un test peu coûteux qui :

- Crée un client avec `create_lora_training_client(base_model=...)`
- Lit `training_client.get_info().model_id`
- Enregistre les poids d'échantillonneur et effectue un échantillonnage
- Exécute une opération avant/arrière prise en charge et une étape d'optimisation
- Enregistre et recharge un checkpoint d'état
- Récupère l'ID de chaque client via `GET /v1/training/jobs/{job_id}` ; une
  reprise par la fabrique crée un nouvel ID à partir du checkpoint source

Utilisez le SDK Tinker pour les workloads du SDK. Pour un client HTTP direct,
utilisez les [routes natives](#switch-to-the-native-routes).

## Comportement du client pris en charge

Fastino prend en charge les appels `tinker==0.32.0` suivants sur un job
interactif.

### Entraînement et échantillonnage

| Méthode ou opération du SDK | Comportement Fastino |
| --- | --- |
| `create_lora_training_client` | Crée un job interactif |
| `copy_weights` | Démarre un job interactif à partir d'un checkpoint |
| `TrainingClient.get_info` | Renvoie le job interactif |
| `forward` | Exécute une opération avant uniquement |
| `forward_backward` | Exécute une opération avant et arrière |
| Opération avant/arrière personnalisée | Exécute une opération à fonction de perte personnalisée prise en charge |
| `optim_step` | Applique une mise à jour de l'optimiseur |
| `save_state` | Enregistre l'état d'entraînement |
| `save_weights_for_sampler` | Enregistre les poids de l'échantillonneur |
| Charger l'état d'entraînement | Restaure un checkpoint d'état |
| Créer ou obtenir un client d'échantillonnage | Résout les poids de l'échantillonneur |
| `SamplingClient.sample` | Échantillonne via le checkpoint sélectionné |

Conservez le paramètre SDK `base_model` inchangé. Choisissez le modèle avec
capabilities ; utilisez les limites documentées pour le rang et la perte, puis
gérez les erreurs de validation du service actif.

### Futures et administration

| Méthode ou opération du SDK | Comportement Fastino |
| --- | --- |
| Résultat/obtention d'une future | Récupère un résultat asynchrone |
| Annulation d'une future | Annule une future d'échantillonnage `sample` non terminée. Les futures des opérations d'entraînement ne sont pas annulées |
| `list_training_runs` ou `get_training_run` | Lit uniquement les exécutions interactives |
| Lister les checkpoints | Lit les checkpoints qui appartiennent au job |
| Télécharger l'archive d'un checkpoint | Télécharge un checkpoint interactif |
| Supprimer un checkpoint | Supprime un checkpoint via le SDK |
| Publier ou dépublier un checkpoint | Modifie la publication du checkpoint via le SDK |
| Définir ou effacer le TTL d'un checkpoint | Modifie la rétention du checkpoint via le SDK |
| Utilisation du stockage des checkpoints | Lit le stockage actuel des checkpoints via le SDK |
| Utilisation facturée | Lit les événements d'utilisation horaires via le SDK |

Le SDK gère automatiquement l'échange de tokens à l'aide de la clé affichée par
`TINKER_CREDENTIAL_CMD`. Ces méthodes ont aussi des
[routes natives](#switch-to-the-native-routes).

### Appels non pris en charge

Fastino ne prend pas en charge :

- La récupération par lots des futures via `retrieve_futures`
- `save_weights_external`
- `external_weights_urls`
- Export de traces de session
- Entrées du journal d'audit

Ne déduisez pas la prise en charge d'une méthode uniquement parce qu'elle
existe dans le paquet installé. Le tableau définit le sous-ensemble pris en
charge ; capabilities ne rapporte que les modèles activés et longueurs de contexte.

## Résoudre les problèmes de connexion

| Symptôme | Vérification |
| --- | --- |
| Échec de l'authentification | Vérifiez que `TINKER_CREDENTIAL_CMD` affiche une seule clé `fast_sk_` actuelle sans sortie supplémentaire |
| Le client ne parvient pas à se connecter | Vérifiez que `TINKER_BASE_URL` correspond exactement à `https://api.fastino.ai/v1/training/compat/tinker` |
| Un modèle est rejeté | Interrogez de nouveau capabilities et choisissez un modèle activé |
| Un rang, une perte ou une opération est rejeté | Comparez l'appel aux limites documentées et au tableau de prise en charge |
| La recherche du job canonique échoue | Vérifiez que l'ID provient de `get_info().model_id` et que la même équipe Fastino est authentifiée |

## Checklist de migration

- [ ] Épingler `tinker==0.32.0`.
- [ ] Définir l'URL de base de l'adaptateur Fastino.
- [ ] Fournir une clé `fast_sk_` via `TINKER_CREDENTIAL_CMD`.
- [ ] Vérifier chaque méthode SDK par rapport au comportement du client pris en charge.
- [ ] Sélectionner un modèle activé à partir des capacités et valider le rang, la
      perte et les opérations à l'aide de ce guide.
- [ ] Effectuer un échantillonnage et une mise à jour d'entraînement.
- [ ] Enregistrer et recharger un checkpoint d'état.
- [ ] Vérifier l'ID de modèle SDK via le point de terminaison canonique du job.
- [ ] Augmenter la taille du workload uniquement après la réussite du test de fumée.

## Passer aux routes natives

Chaque appel du SDK ci-dessus a une route REST native sous
`/v1/training/jobs`. Envoyez du JSON avec la même clé `fast_sk_` en `X-API-Key`
ou `Authorization: Bearer`. Vous n'avez besoin ni de sessions, ni de numéros de
séquence, ni de heartbeats : Fastino ordonne les opérations de chaque job à leur
réception et maintient le job actif tant que vous l'appelez. Un job interactif
sans appel pendant 30 minutes est libéré ; ses checkpoints sont conservés.

Chaque route qui effectue un travail renvoie un `future_id`. Lisez son
résultat avec `GET /v1/training/jobs/{job_id}/futures/{future_id}?wait=true` ;
cela remplace `future.result()`.

| Appel Tinker | Route native |
| --- | --- |
| `create_lora_training_client(base_model=..., rank=...)` | `POST /v1/training/jobs/create-model` avec `base_model` et `lora_config` |
| `create_training_client_from_state(path)` | `POST /v1/training/jobs/create-model` avec `from_checkpoint` et `"load_optimizer": true` |
| `TrainingClient.get_info()` | `GET /v1/training/jobs/{job_id}` |
| `forward(datums, loss_fn)` | `POST /v1/training/jobs/{job_id}/forward` |
| `forward_backward(datums, loss_fn)` | `POST /v1/training/jobs/{job_id}/forward-backward` |
| `optim_step(AdamParams(...))` | `POST /v1/training/jobs/{job_id}/optim-step` avec `adam_params` |
| `save_state(name)` | `POST /v1/training/jobs/{job_id}/save-weights` |
| `save_weights_for_sampler(name, ttl_seconds=...)` | `POST /v1/training/jobs/{job_id}/save-weights-for-sampler` avec `ttl_seconds` |
| `load_state(path)` / `load_state_with_optimizer(path)` | `POST /v1/training/jobs/{job_id}/load-weights` avec `path` et `optimizer` pour l'état du même job ; pour l'état d'un autre job, créez un job avec `from_checkpoint` |
| `SamplingClient.sample(prompt, ...)` | `POST /v1/training/jobs/{job_id}/sample` avec `checkpoint` et `prompt_tokens` |
| `result()` d'un future | `GET /v1/training/jobs/{job_id}/futures/{future_id}` |
| `cancel()` d'un future d'échantillonnage | `POST /v1/training/jobs/{job_id}/futures/{future_id}/cancel` |
| `RestClient` : lister ou obtenir des exécutions | `GET /v1/training/jobs?type=interactive`, `GET /v1/training/jobs/{job_id}` |
| Lister les checkpoints | `GET /v1/training/jobs/{job_id}/checkpoints` |
| Télécharger l'archive d'un checkpoint | `GET /v1/training/jobs/{job_id}/checkpoints/{checkpoint_id}/download` |
| Supprimer un checkpoint | `DELETE /v1/training/jobs/{job_id}/checkpoints/{kind}/{name}` |
| Publier ou dépublier un checkpoint | `POST` ou `DELETE /v1/training/jobs/{job_id}/checkpoints/{kind}/{name}/publish` |
| Définir ou retirer le TTL d'un checkpoint | `PUT /v1/training/jobs/{job_id}/checkpoints/{kind}/{name}/ttl` |
| Usage du stockage des checkpoints | `GET /v1/training/usage` |
| `ServiceClient.close()` / décharger le modèle | `POST /v1/training/jobs/{job_id}/stop` |

Les datums gardent la forme du SDK en JSON : `model_input.chunks[].tokens`
plus des tenseurs `loss_fn_inputs` comme `{"data": [...], "dtype": "int64"}`.
Tokenisez avec le tokenizer Hugging Face du modèle (`transformers.AutoTokenizer`).
Le [démarrage rapide](/fr/training/quickstart#custom-training-loop) contient un script complet.
