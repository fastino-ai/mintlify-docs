Utilisez une récompense vérifiable lorsque du code peut contrôler une réponse :
résultat mathématique, résultat de test, contrainte de schéma, extraction exacte
ou résultat d'outil.

```text
prompt -> sample a group -> grade -> center rewards -> build datums -> update
```

L'échantillonnage, les passes forward-backward, les étapes d'optimiseur et les
checkpoints appartiennent au même job interactif Fastino. Le calcul des
récompenses et l'état de l'application restent dans votre code.

## Prérequis

Commencez avec une
[boucle d'entraînement personnalisée](/fr/training/quickstart#custom-training-loop)
fonctionnelle et vérifiez qu'un datum de référence s'entraîne correctement. Ce
guide réutilise ses helpers `call` et `wait`, le `tokenizer` et le `job_id`.

Votre application échantillonne les réponses, les évalue et convertit les
récompenses en avantages par token. Fastino applique ces avantages avec une
perte prise en charge : `importance_sampling`, `ppo`, `cispo` ou `dro`. Les
fonctions de perte personnalisées ne s'exécutent pas dans le job d'entraînement.

## 1. Définir un évaluateur restreint

Séparez l'analyse de la notation pour que les sorties mal formées restent
visibles :

<Warning>
  N'exécutez du code ou des outils générés que dans un environnement isolé et
  aux ressources limitées. Fastino n'exécute pas votre fonction de récompense et
  ne gère pas ses effets de bord.
</Warning>

```python
def get_reward(response: str, expected: str) -> float:
    actual = parse_answer(response)
    if actual is None:
        return 0.0
    return 1.0 if actual == expected else 0.0
```

Conservez un jeu de cas figé comprenant des réponses correctes, incorrectes, mal
formées et formatées de manière équivalente. Journalisez les échecs d'analyse
séparément des réponses valides mais incorrectes.

## 2. Capturer le job pour l'échantillonnage

Enregistrez un checkpoint sampler à partir des poids actuels, puis
échantillonnez un groupe depuis celui-ci :

```python
name = f"rollout-{step:06d}"
saved = call(
    "POST",
    f"/v1/training/jobs/{job_id}/save-weights-for-sampler",
    {"name": name, "ttl_seconds": 24 * 60 * 60},
)
wait(job_id, saved["future_id"])

prompt_tokens = tokenizer.apply_chat_template(
    [{"role": "user", "content": question}],
    add_generation_prompt=True,
    return_dict=False,
)
sampled = call(
    "POST",
    f"/v1/training/jobs/{job_id}/sample",
    {
        "checkpoint": name,
        "prompt_tokens": prompt_tokens,
        "num_samples": group_size,
        "sampling_params": {"max_tokens": 512, "temperature": 1.0},
    },
)
sample_result = wait(job_id, sampled["future_id"])
```

Cela ne crée pas d'autre job. Le checkpoint et les échantillons appartiennent au
même job interactif.

## 3. Convertir les récompenses en avantages

```python
sequences = sample_result["sequences"]
rewards = [
    get_reward(tokenizer.decode(sequence["tokens"]), expected)
    for sequence in sequences
]

mean_reward = sum(rewards) / len(rewards)
advantages = [reward - mean_reward for reward in rewards]

if all(advantage == 0.0 for advantage in advantages):
    continue
```

Suivez les groupes sans variance de récompense. Ils peuvent indiquer que la
tâche est trop facile, trop difficile ou mal analysée.

## 4. Construire des datums alignés

Le prompt sert de contexte : ses positions reçoivent un avantage nul. Les
positions de la complétion reçoivent l'avantage relatif au groupe et les
log-probabilités du sampler. Chaque tenseur a une valeur par position d'entrée :

```python
def rl_datum(prompt_tokens, sequence, advantage):
    completion = sequence["tokens"]
    tokens = prompt_tokens + completion
    padding = [0.0] * (len(prompt_tokens) - 1)
    logprobs = padding + sequence["logprobs"]
    advantages = padding + [advantage] * len(completion)
    if not (len(tokens) - 1 == len(logprobs) == len(advantages)):
        raise ValueError("training datum arrays are not aligned")
    return {
        "model_input": {"chunks": [{"type": "encoded_text", "tokens": tokens[:-1]}]},
        "loss_fn_inputs": {
            "target_tokens": {"data": tokens[1:], "dtype": "int64"},
            "logprobs": {"data": logprobs, "dtype": "float32"},
            "advantages": {"data": advantages, "dtype": "float32"},
        },
    }


datums = [
    rl_datum(prompt_tokens, sequence, advantage)
    for sequence, advantage in zip(sequences, advantages)
]
```

Utilisez le tokenizer du `base_model` du job pour les prompts comme pour le
décodage.

## 5. Mettre à jour le job interactif

```python
backward = call(
    "POST",
    f"/v1/training/jobs/{job_id}/forward-backward",
    {"datums": datums, "loss_fn": "importance_sampling"},
)
train_result = wait(job_id, backward["future_id"])
update = call(
    "POST",
    f"/v1/training/jobs/{job_id}/optim-step",
    {"adam_params": {"learning_rate": 1e-5}},
)
optim_result = wait(job_id, update["future_id"])
```

Attendez la réussite de forward-backward avant d'envoyer l'étape d'optimiseur.
Attendez et enregistrez le résultat de l'optimiseur avant de faire avancer
l'étape de l'application.

Champs et valeurs par défaut pris en charge dans `loss_fn_config` :

| S'applique à | Champs et valeurs par défaut |
| --- | --- |
| `ppo` | `clip_low_threshold: 0.8`, `clip_high_threshold: 1.2` |
| `cispo` | `clip_low_threshold: 0.0`, `clip_high_threshold: 4.0` |
| `dro` | `beta: 0.05` |
| Pertes de récompense | `tis_cap: 2`, `icepop_low: 0.5`, `icepop_high: 5` |

Les protections de la dernière ligne sont activées par défaut. Les champs de
configuration inconnus sont rejetés.

## 6. Enregistrer un point de reprise

```python
state = call(
    "POST",
    f"/v1/training/jobs/{job_id}/save-weights",
    {"name": f"step-{step:06d}"},
)
wait(job_id, state["future_id"])
```

Conservez le `path` renvoyé avec :

- l'ID du job ;
- l'étape de l'application et le curseur du dataset ;
- les révisions du dataset et de l'implémentation des récompenses ;
- le modèle de base et la configuration d'entraînement ;
- les métriques d'évaluation.

Ces métadonnées permettent à un contrôleur de choisir un checkpoint sans le
deviner d'après son nom.

## Vérifier avant de monter en charge

- L'évaluateur distingue des cas connus corrects et incorrects.
- Les réponses mal formées ne font pas planter la boucle de l'application.
- Au moins un groupe d'échantillons présente une variance de récompense.
- Les tenseurs de chaque datum ont une valeur par position d'entrée.
- Les opérations forward-backward et d'étape d'optimiseur se terminent sur le même job.
- Un nouveau job peut démarrer depuis un checkpoint d'état avec ses métadonnées
  de reprise côté client.
- L'évaluation sur données réservées reste séparée du lot de récompenses
  d'entraînement.

Pour le cycle de vie complet, lisez
[Construire une boucle d'entraînement personnalisée](/fr/training/training-loop).
