---
title: "Checkpoints et récupération"
description: "Enregistrez l'état d'un job interactif et la progression de l'application, puis récupérez-les sans rejouer le travail terminé."
---

Un checkpoint d'état protège l'état d'entraînement côté serveur. Un
enregistrement de récupération complet protège également l'état contrôlé par
l'utilisateur qui indique à votre contrôleur ce qu'il doit faire ensuite.

## Éléments à enregistrer

| Enregistrement | Contenu | Stocké par |
| --- | --- | --- |
| Checkpoint d'état | Poids d'entraînement et état de l'optimiseur représentés par le checkpoint du SDK | Fastino |
| Enregistrement de la boucle | ID du job source, chemin du checkpoint, étape, curseur du dataset, configuration et lignée de reprise | Votre application |

Le client d'entraînement du SDK représente un job interactif Fastino. Lisez son
ID canonique dans `training_client.get_info().model_id`.

## 1. Enregistrer l'état et la progression de la boucle

Enregistrez l'état via le SDK, puis conservez le checkpoint renvoyé avec les
champs contrôlés par le client nécessaires à la poursuite :

```python
import json
from pathlib import Path


source_job_id = training_client.get_info().model_id
state = training_client.save_state(f"step-{step:06d}").result()
record = {
    "source_job_id": source_job_id,
    "state_path": state.path,
    "model": model_name,
    "dataset_revision": dataset_revision,
    "optimizer": optimizer_config,
    "step": step,
    "dataset_cursor": dataset_cursor,
    "reward_version": reward_version,
}

with Path(log_path).open("a", encoding="utf-8") as checkpoint_log:
    checkpoint_log.write(json.dumps(record, sort_keys=True) + "\n")
```

Utilisez des noms de checkpoint uniques afin que chaque enregistrement de
boucle identifie une limite de récupération sans ambiguïté. Ne supposez pas une
durée de vie de checkpoint non documentée.

## 2. Lire l'enregistrement complet le plus récent

Un processus peut s'arrêter pendant l'écriture de la dernière ligne. Parcourez
les lignes à rebours et ignorez une fin mal formée :

```python
def get_last_checkpoint(log_path: str) -> dict[str, object] | None:
    path = Path(log_path)
    if not path.exists():
        return None

    for line in reversed(path.read_text(encoding="utf-8").splitlines()):
        try:
            record = json.loads(line)
        except json.JSONDecodeError:
            continue
        if isinstance(record, dict) and isinstance(record.get("state_path"), str):
            return record
    return None
```

## 3. Valider avant le chargement

Comparez l'enregistrement avec le checkpoint source et la poursuite demandée :

- ID du job source encodé dans le chemin du checkpoint
- Modèle de base et configuration entraînable
- Révision et curseur du dataset
- Révision de l'implémentation de la récompense
- Configuration de l'optimiseur
- Hypothèses du renderer et du tokenizer

Arrêtez-vous pour obtenir une décision explicite si ces champs sont
incompatibles. Ne combinez pas silencieusement un checkpoint avec une
expérience différente.

Utilisez ensuite le flux de chargement d'état pris en charge par le SDK :

```python
training_client = (
    service_client.create_training_client_from_state_with_optimizer(
        str(resume["state_path"])
    )
)
resumed_job_id = training_client.get_info().model_id
```

Cette fabrique crée un nouveau job interactive, puis charge les poids et l'état
de l'optimiseur du checkpoint source. L'ID repris diffère normalement de l'ID
source. Enregistrez `source_job_id`, `state_path` et `resumed_job_id` comme
lignée gérée par l'application. Ne refusez pas la reprise parce que les ID
diffèrent et ne construisez pas la requête vers l'adaptateur.

## 4. Rendre la limite récupérable

Respectez cet ordre :

1. Résolvez les futures de passe avant/arrière et d'optimisation.
2. Enregistrez le checkpoint d'état.
3. Conservez l'enregistrement de boucle contenant son identifiant.
4. Marquez l'étape de l'application comme terminée.
5. Commencez l'étape suivante.

Si le processus s'arrête après l'enregistrement du checkpoint, mais avant la
persistance de l'enregistrement de boucle, conservez l'enregistrement complet
précédent comme point de récupération fiable. Ne marquez pas une étape comme
terminée avant que son enregistrement ne soit durable.

## 5. Séparer les types de checkpoints

```python
state = training_client.save_state("step-000100").result()
sampler = training_client.save_weights_for_sampler(
    "step-000100",
    ttl_seconds=24 * 60 * 60,
).result()
```

Utilisez un checkpoint d'état pour la récupération de l'entraînement. Utilisez
un checkpoint d'échantillonneur pour les rollouts ou l'évaluation. N'utilisez
pas un checkpoint d'échantillonneur comme point de récupération de l'état de
l'optimiseur.

`ttl_seconds` vaut `None` par défaut ; sans TTL, le checkpoint n'expire pas
automatiquement. Les checkpoints actifs comptent dans le stockage. Pour un
nettoyage automatique, utilisez une valeur comprise entre `3_600` et
`315_360_000` secondes, bornes incluses.

L'API d'entraînement publique permet de lister les checkpoints. Elle permet de
télécharger un checkpoint interactif lorsque l'équipe dispose à la fois de
l'accès à l'entraînement interactif et de l'autorisation de télécharger les
poids. Le SDK prend aussi en charge des méthodes
de suppression, de publication, de rétention et d'utilisation du stockage des
checkpoints. Ce sont des opérations SDK, et non des routes publiques de l'API
d'entraînement. Ne construisez pas
de requêtes vers l'adaptateur et ne supposez pas une durée de rétention non
documentée.

## 6. Vérifier la poursuite

Avant d'augmenter la taille du workload repris :

1. Chargez le checkpoint d'état sélectionné.
2. Lisez le nouvel ID dans `training_client.get_info().model_id`, enregistrez-le
   comme `resumed_job_id` et confirmez-le via
   `GET /v1/training/jobs/{resumed_job_id}`.
3. Exécutez une petite évaluation sur un ensemble de validation.
4. Soumettez une mise à jour d'entraînement prise en charge.
5. Enregistrez un nouveau checkpoint d'état sous un nouveau nom.
6. Conservez l'enregistrement de boucle suivant.

Utilisez le SDK pour toutes les opérations interactives sur le modèle.

## Diagnostiquer les erreurs de récupération

| Symptôme | Vérification |
| --- | --- |
| Une future échoue | Enregistrez l'ID du job et le résultat de l'opération. Ne faites pas avancer l'état dépendant de l'application |
| Un checkpoint ne peut pas être chargé | Vérifiez son job, son type de checkpoint et l'enregistrement de récupération contrôlé par le client |
| Le checkpoint source est refusé | Vérifiez le job source, le type de checkpoint et `state_path` ; n'exigez pas que le nouvel ID égale l'ID source |
| La recherche du job repris échoue | Vérifiez que l'ID provient de `get_info().model_id` du client repris et que la même équipe Fastino est authentifiée |
