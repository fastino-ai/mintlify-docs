---
title: "Checkpoints et récupération"
description: "Enregistrez l'état d'un job interactif et la progression de l'application, puis récupérez-les sans rejouer le travail terminé."
---

Un checkpoint d'état protège l'état d'entraînement côté serveur. Un
enregistrement de reprise complet protège aussi l'état propre à l'utilisateur
qui indique à votre contrôleur quoi faire ensuite.

Les exemples utilisent les helpers `call` et `wait` du
[script du démarrage rapide](/fr/training/decoder-quickstart).

## Que sauvegarder

| Enregistrement | Contenu | Stocké par |
| --- | --- | --- |
| Checkpoint d'état | Poids LoRA et état de l'optimiseur | Fastino |
| Enregistrement de boucle | ID du job source, chemin du checkpoint, étape, curseur du dataset, configuration et lignée de reprise | Votre application |

## 1. Enregistrer l'état et la progression de la boucle

Enregistrez l'état avec `save-weights`, attendez la fin du future, puis
conservez son chemin avec les champs côté client nécessaires pour continuer :

```python
import json
from pathlib import Path


state = call(
    "POST",
    f"/v1/training/jobs/{job_id}/save-weights",
    {"name": f"step-{step:06d}"},
)
state_path = wait(job_id, state["future_id"])["path"]
record = {
    "source_job_id": job_id,
    "state_path": state_path,
    "model": model_name,
    "dataset_revision": dataset_revision,
    "optimizer": adam_params,
    "step": step,
    "dataset_cursor": dataset_cursor,
    "reward_version": reward_version,
}

with Path(log_path).open("a", encoding="utf-8") as checkpoint_log:
    checkpoint_log.write(json.dumps(record, sort_keys=True) + "\n")
```

Le chemin renvoyé dans la réponse initiale de l'enregistrement est provisoire.
Le checkpoint ne devient durable qu'une fois le future d'enregistrement terminé ;
si le future échoue ou est annulé, ne conservez pas ce chemin et ne l'utilisez
pas.

Utilisez des noms de checkpoint uniques afin que chaque enregistrement
identifie un point de reprise sans ambiguïté. Les noms comptent 1 à
128 caractères parmi `A-Z`, `a-z`, `0-9`, `.`, `_` et `-`. Les noms
commençant par `__park-` ou `__snap-` sont réservés.

## 2. Lire l'enregistrement complet le plus récent

Un processus peut s'arrêter pendant l'écriture de la dernière ligne. Parcourez
le fichier à rebours et ignorez une fin mal formée :

```python
def get_last_checkpoint(log_path: str) -> dict[str, object] | None:
    path = Path(log_path)
    if not path.exists():
        return None

    for line in reversed(path.read_text(encoding="utf-8").splitlines()):
        try:
            record = json.loads(line)
        except json.JSONDecodeError:
            continue
        if isinstance(record, dict) and isinstance(record.get("state_path"), str):
            return record
    return None
```

## 3. Valider avant de charger

Comparez l'enregistrement avec le checkpoint source et la reprise demandée :

- ID du job source dans le chemin du checkpoint
- Modèle de base et configuration LoRA
- Révision et curseur du dataset
- Révision de l'implémentation des récompenses
- Réglages de l'optimiseur
- Hypothèses sur le tokenizer et le modèle de chat

Arrêtez-vous pour une décision explicite si ces champs se contredisent. Ne
combinez pas silencieusement un checkpoint avec une autre expérience.

Choisissez ensuite comment continuer :

| Situation | Appel |
| --- | --- |
| Le job source est encore actif et vous voulez revenir en arrière | `POST /v1/training/jobs/{job_id}/load-weights` avec `{"path": "<name>", "optimizer": true}` |
| Le job source a été arrêté ou libéré | `POST /v1/training/jobs/create-model` avec `from_checkpoint` et `load_optimizer` |

Pour continuer dans un nouveau job :

```python
resume = get_last_checkpoint(log_path)
if resume is None:
    raise RuntimeError("no durable checkpoint record found")

resumed = call(
    "POST",
    "/v1/training/jobs/create-model",
    {"from_checkpoint": resume["state_path"], "load_optimizer": True},
)
wait(resumed["job_id"], resumed["future_id"])
wait(resumed["job_id"], resumed["load_future_id"])
resumed_job_id = resumed["job_id"]
```

Le nouveau job reprend le modèle de base et les paramètres LoRA du checkpoint :
n'envoyez donc pas `lora_config`. Son ID diffère de celui du job source.
Enregistrez `source_job_id`, `state_path` et `resumed_job_id` comme lignée gérée
par l'application.

## 4. Rendre la frontière récupérable

Suivez cet ordre :

1. Attendez la fin des futures forward-backward et d'étape d'optimiseur.
2. Enregistrez le checkpoint d'état et attendez le future d'enregistrement.
3. Conservez l'enregistrement de boucle contenant son chemin.
4. Marquez l'étape de l'application comme terminée.
5. Commencez l'étape suivante.

Si le processus s'arrête après l'enregistrement du checkpoint mais avant la
sauvegarde de l'enregistrement de boucle, gardez l'enregistrement complet
précédent comme point de reprise fiable. Ne marquez pas une étape comme terminée
avant que son enregistrement soit durable.

Les résultats des futures restent récupérables pendant une heure. Pendant cette
fenêtre, interrogez le `future_id` d'enregistrement connu avant de conclure sur
ce qui s'est passé. S'il renvoie `410`, ne relancez pas l'enregistrement à
l'aveugle : rapprochez les checkpoints du job de votre enregistrement de boucle
durable. La frontière de validation à long terme est un checkpoint terminé
accompagné de son enregistrement applicatif durable, et non le future lui-même.

## 5. Séparer les types de checkpoints

```python
name = f"step-{step:06d}"
state = call(
    "POST",
    f"/v1/training/jobs/{job_id}/save-weights",
    {"name": name},
)
sampler = call(
    "POST",
    f"/v1/training/jobs/{job_id}/save-weights-for-sampler",
    {"name": name, "ttl_seconds": 24 * 60 * 60},
)
```

| Enregistré avec | Suffixe de l'ID du checkpoint | Chemin complet | Usage |
| --- | --- | --- | --- |
| `save-weights` | `weights/<name>` | `tinker://<job_id>/weights/<name>` | Reprise de l'entraînement : le charger ou démarrer un nouveau job depuis celui-ci |
| `save-weights-for-sampler` | `sampler_weights/<name>` | `tinker://<job_id>/sampler_weights/<name>` | Rollouts, évaluation, déploiement et téléchargement de l’adaptateur |

N'utilisez pas un checkpoint sampler comme point de reprise : il ne contient pas
l'état de l'optimiseur et aucun nouveau job ne peut démarrer depuis celui-ci.
Passez le chemin complet `tinker://.../weights/<name>`, et non le suffixe de
l'ID du checkpoint, comme `from_checkpoint`.

`ttl_seconds` vaut `null` par défaut : sans TTL, le checkpoint est conservé
jusqu'à sa suppression. Les checkpoints actifs comptent dans le stockage des
checkpoints. Pour activer le nettoyage automatique, passez une valeur de `3600`
à `315360000` secondes (1 heure à 10 ans).

Gérez les checkpoints avec ces routes :

| Tâche | Route |
| --- | --- |
| Lister les checkpoints d'un job | [`GET /v1/training/jobs/{job_id}/checkpoints`](/fr/api-reference/training-jobs/checkpoints) |
| Obtenir un checkpoint | [`GET /v1/training/jobs/{job_id}/checkpoints/{kind}/{name}`](/fr/api-reference/training-jobs/interactive/get-checkpoint) |
| Télécharger une archive `.tar` | [`GET /v1/training/jobs/{job_id}/checkpoints/{checkpoint_id}/download`](/fr/api-reference/training-jobs/download-checkpoint) |
| Modifier son TTL | [`PUT /v1/training/jobs/{job_id}/checkpoints/{kind}/{name}/ttl`](/fr/api-reference/training-jobs/interactive/set-checkpoint-ttl) |
| Publier ou dépublier | [`POST /v1/training/jobs/{job_id}/checkpoints/{kind}/{name}/publish`](/fr/api-reference/training-jobs/interactive/publish-checkpoint) |
| Supprimer | [`DELETE /v1/training/jobs/{job_id}/checkpoints/{kind}/{name}`](/fr/api-reference/training-jobs/interactive/delete-checkpoint) |
| Lire l'usage du stockage | [`GET /v1/training/usage`](/fr/api-reference/training-jobs/interactive/storage-usage) |

Le téléchargement des checkpoints est activé par défaut. Le checkpoint sampler d’un décodeur se télécharge sous forme d’adaptateur PEFT Hugging Face standard pour le modèle de base public ; consultez [Télécharger un checkpoint](/fr/api-reference/training-jobs/download-checkpoint).

Après l'arrêt d'un job, les opérations d'entraînement qui modifient son état
sont refusées, mais vous pouvez toujours lister, inspecter, télécharger et
publier ses checkpoints, modifier leur TTL et les supprimer. Vous pouvez aussi
échantillonner à partir de ses checkpoints sampler.

## 6. Vérifier la reprise

Avant de faire monter en charge la reprise :

1. Démarrez le nouveau job depuis le checkpoint d'état choisi.
2. Conservez son ID comme `resumed_job_id` et confirmez-le avec
   `GET /v1/training/jobs/{resumed_job_id}`.
3. Lancez une petite évaluation sur des données réservées.
4. Envoyez une mise à jour d'entraînement.
5. Enregistrez un nouveau checkpoint d'état sous un nouveau nom.
6. Conservez l'enregistrement de boucle suivant.

## Déployer votre modèle entraîné

Déployez un checkpoint sampler pour le servir comme modèle. La disponibilité du déploiement est contrôlée par modèle et par environnement. Nemotron 3.5 Lightning et Qwen3.6-35B-A3B sont actuellement activés. Nemotron 3 Super bénéficie d’une implémentation de serving, mais n’est pas actuellement activé ; le déploiement renvoie donc `400`.

```bash
curl -X POST "https://api.fastino.ai/v1/training/jobs/$TRAINING_JOB_ID/checkpoints/sampler_weights/step-000100/deploy" \
  -H "X-API-Key: $FASTINO_API_KEY" \
  -H "Content-Type: application/json" \
  -d '{"model_name": "support-replies-v1"}'
```

La réponse contient le `model_id` du modèle et un `status` `deploying`. Répétez
le même appel pour suivre la progression : il renvoie le même modèle, et `status`
passe à `deployed` lorsque le modèle est prêt. Appelez-le ensuite par son ID :

```bash
curl -X POST "https://api.fastino.ai/v1/chat/completions" \
  -H "X-API-Key: $FASTINO_API_KEY" \
  -H "Content-Type: application/json" \
  -d '{
    "model": "MODEL_ID",
    "messages": [{"role": "user", "content": "Summarize this ticket in one sentence."}],
    "reasoning": {"enabled": false}
  }'
```

Remplacez `MODEL_ID` par le `model_id` renvoyé. La première requête d’inférence peut renvoyer `425 model_warming` ; attendez l’intervalle indiqué par `Retry-After`, puis réessayez. Pour demander une réponse directe sans préambule de raisonnement, envoyez `"reasoning": {"enabled": false}` comme ci-dessus. Consultez
[Déployer un checkpoint](/fr/api-reference/training-jobs/interactive/deploy-checkpoint)
pour les champs et les erreurs.

## Diagnostiquer les erreurs de reprise

| Symptôme | Vérification |
| --- | --- |
| Un future échoue | Notez l'ID du job et l'`error` du future. Ne faites pas avancer l'état dépendant de l'application |
| Un appel d'entraînement renvoie `400` après une pause | Le job a été arrêté ou libéré après 30 minutes d'inactivité. Les opérations d'entraînement qui modifient l'état sont indisponibles ; la gestion des checkpoints et l'échantillonnage depuis les checkpoints sampler restent disponibles. Démarrez un nouveau job depuis le dernier checkpoint d'état pour continuer |
| Un checkpoint ne peut pas être chargé | Vérifiez son job, son type et l'enregistrement de reprise côté client |
| `from_checkpoint` est refusé | Confirmez qu'il s'agit d'un chemin complet `tinker://<job_id>/weights/<name>` de votre équipe ; les checkpoints sampler ne peuvent pas démarrer un job |
| La recherche du job repris échoue | Confirmez que l'ID provient de la réponse de création du nouveau job et que vous êtes authentifié dans la même équipe Fastino |
