Use a verifiable reward when code can check a response, such as a math answer,
test result, schema constraint, exact extraction, or tool outcome.

```text
prompt -> sample a group -> grade -> center rewards -> build datums -> update
```

Sampling, forward-backward passes, optimizer steps, and checkpoints all belong
to the same interactive Fastino job. Reward execution and application state
remain in your code.

## Before you start

Complete the [custom-loop Quickstart](/training/quickstart#custom-training-loop).
The snippets below reuse its `call` and `wait` helpers, its `tokenizer`, and a
`job_id`. They use the built-in `importance_sampling` loss and focus on the
user-owned reward flow.

<Note>
  This guide is not a standalone copy-and-paste trainer. Start from the
  Quickstart script, confirm that its datums train, then add the reward flow
  below.
</Note>

<Note>
  The job runs only the built-in losses: `cross_entropy`,
  `importance_sampling`, `ppo`, `cispo`, and `dro`. A loss function written in
  your own code can't run on the job. Express your reward as advantages for one
  of these losses.
</Note>

<Warning>
  Run generated code or tools only in an isolated, resource-limited
  environment. Fastino doesn't execute your reward function or manage its side
  effects.
</Warning>

## 1. Define a narrow grader

Separate parsing from scoring so malformed output is observable:

```python
def get_reward(response: str, expected: str) -> float:
    actual = parse_answer(response)
    if actual is None:
        return 0.0
    return 1.0 if actual == expected else 0.0
```

Keep a frozen fixture set that includes correct, incorrect, malformed, and
equivalently formatted answers. Log parse failures separately from valid but
incorrect responses.

## 2. Snapshot the job for sampling

Save a sampler checkpoint from the current weights, then sample a group from
it:

```python
name = f"rollout-{step:06d}"
saved = call(
    "POST",
    f"/v1/training/jobs/{job_id}/save-weights-for-sampler",
    {"name": name, "ttl_seconds": 24 * 60 * 60},
)
wait(job_id, saved["future_id"])

prompt_tokens = tokenizer.apply_chat_template(
    [{"role": "user", "content": question}],
    add_generation_prompt=True,
    return_dict=False,
)
sampled = call(
    "POST",
    f"/v1/training/jobs/{job_id}/sample",
    {
        "checkpoint": name,
        "prompt_tokens": prompt_tokens,
        "num_samples": group_size,
        "sampling_params": {"max_tokens": 512, "temperature": 1.0},
    },
)
sample_result = wait(job_id, sampled["future_id"])
```

This doesn't create another job. The checkpoint and the samples belong to the
same interactive job.

## 3. Convert rewards to advantages

```python
sequences = sample_result["sequences"]
rewards = [
    get_reward(tokenizer.decode(sequence["tokens"]), expected)
    for sequence in sequences
]

mean_reward = sum(rewards) / len(rewards)
advantages = [reward - mean_reward for reward in rewards]

if all(advantage == 0.0 for advantage in advantages):
    continue
```

Track groups with no reward variance. They may indicate that the task is too
easy, too hard, or parsed incorrectly.

## 4. Build aligned datums

The prompt is context, so prompt positions receive zero advantage. Completion
positions receive the response's group-relative advantage and the sampler's log
probabilities. Every tensor has one value per input position:

```python
def rl_datum(prompt_tokens, sequence, advantage):
    completion = sequence["tokens"]
    tokens = prompt_tokens + completion
    padding = [0.0] * (len(prompt_tokens) - 1)
    logprobs = padding + sequence["logprobs"]
    advantages = padding + [advantage] * len(completion)
    if not (len(tokens) - 1 == len(logprobs) == len(advantages)):
        raise ValueError("training datum arrays are not aligned")
    return {
        "model_input": {"chunks": [{"type": "encoded_text", "tokens": tokens[:-1]}]},
        "loss_fn_inputs": {
            "target_tokens": {"data": tokens[1:], "dtype": "int64"},
            "logprobs": {"data": logprobs, "dtype": "float32"},
            "advantages": {"data": advantages, "dtype": "float32"},
        },
    }


datums = [
    rl_datum(prompt_tokens, sequence, advantage)
    for sequence, advantage in zip(sequences, advantages)
]
```

Use the tokenizer of the job's `base_model` for both prompts and decoding.

## 5. Update the interactive job

```python
backward = call(
    "POST",
    f"/v1/training/jobs/{job_id}/forward-backward",
    {"datums": datums, "loss_fn": "importance_sampling"},
)
update = call(
    "POST",
    f"/v1/training/jobs/{job_id}/optim-step",
    {"adam_params": {"learning_rate": 1e-5}},
)
train_result = wait(job_id, backward["future_id"])
optim_result = wait(job_id, update["future_id"])
```

Both calls update the same job, in the order they were sent. Wait for and
record each result before advancing the application step. For clipped
objectives, use `ppo` or `cispo` with `loss_fn_config` thresholds.

## 6. Save a recovery boundary

```python
state = call(
    "POST",
    f"/v1/training/jobs/{job_id}/save-weights",
    {"name": f"step-{step:06d}"},
)
wait(job_id, state["future_id"])
```

Persist the returned `path` with:

- Job ID
- Application step and dataset cursor
- Dataset and reward implementation revisions
- Base model and training configuration
- Evaluation metrics

This metadata lets a controller choose a checkpoint without guessing from its
name.

## Verify before scaling

- The grader distinguishes known correct and incorrect fixtures.
- Malformed responses don't crash the application loop.
- At least one sample group has reward variance.
- Every datum's tensors have one value per input position.
- Forward-backward passes and optimizer steps complete on the same job.
- A new job can start from a state checkpoint with its client-owned resume
  metadata.
- Held-out evaluation remains separate from the training reward batch.
