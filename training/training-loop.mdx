Your application decides what to sample, how to score it, and when to update.
Fastino runs each model call on one interactive job. Every step is a
JSON request to a route under `/v1/training/jobs/{job_id}`.

## The control loop

<Steps>
  <Step title="Create the interactive job">
    Call `POST /v1/training/jobs/create-model` with a `base_model` and optional
    `lora_config`. Save the returned `job_id`, and wait for the `create`
    future to complete.
  </Step>
  <Step title="Checkpoint weights for sampling">
    Call `POST /v1/training/jobs/{job_id}/save-weights-for-sampler` with a
    name. Sample from that checkpoint so each rollout is tied to an
    explicit artifact of the same job.
  </Step>
  <Step title="Collect rollout groups">
    Sample several candidate responses for each prompt with
    `POST /v1/training/jobs/{job_id}/sample`, naming that checkpoint.
    Your application owns prompt construction, tokenization, and grouping.
  </Step>
  <Step title="Compute rewards and advantages">
    Score each response, then turn rewards into the advantages your loss
    function needs.
  </Step>
  <Step title="Build training datums">
    Combine prompt and response tokens with per-position targets, weights, log
    probabilities, or advantages.
  </Step>
  <Step title="Update the same job">
    Send `POST /v1/training/jobs/{job_id}/forward-backward`, then
    `POST /v1/training/jobs/{job_id}/optim-step`.
  </Step>
  <Step title="Save a recovery boundary">
    Save the state with `POST /v1/training/jobs/{job_id}/save-weights`, and
    persist its path with the application step and dataset cursor before you
    begin the next iteration.
  </Step>
</Steps>

## Routes

| Step | Route |
| --- | --- |
| Create a job | [`POST /v1/training/jobs/create-model`](/api-reference/interactive-jobs/create) |
| Compute loss and gradients | [`POST /v1/training/jobs/{job_id}/forward-backward`](/api-reference/interactive-jobs/forward-backward) |
| Compute loss only | [`POST /v1/training/jobs/{job_id}/forward`](/api-reference/interactive-jobs/forward) |
| Apply gradients | [`POST /v1/training/jobs/{job_id}/optim-step`](/api-reference/interactive-jobs/optim-step) |
| Read a result | [`GET /v1/training/jobs/{job_id}/futures/{future_id}`](/api-reference/interactive-jobs/get-future) |
| Save the training state | [`POST /v1/training/jobs/{job_id}/save-weights`](/api-reference/interactive-jobs/save-weights) |
| Save weights for sampling | [`POST /v1/training/jobs/{job_id}/save-weights-for-sampler`](/api-reference/interactive-jobs/save-weights-for-sampler) |
| Sample | [`POST /v1/training/jobs/{job_id}/sample`](/api-reference/interactive-jobs/sample) |
| Stop the job | [`POST /v1/training/jobs/{job_id}/stop`](/api-reference/training-jobs/stop) |

To turn deterministic grading into group-relative advantages, follow
[Train with verifiable rewards](/training/verifiable-rewards).

## Build aligned datums

A datum holds N input tokens and N-value tensors in `loss_fn_inputs`. Tokenize
with the base model's Hugging Face tokenizer
(`transformers.AutoTokenizer.from_pretrained(base_model)`), and use the same
tokenizer to decode samples.

| Loss function | Required inputs |
| --- | --- |
| `cross_entropy` | `target_tokens`; optional `weights` (default `1` everywhere) |
| `importance_sampling`, `ppo`, `cispo`, `dro` | `target_tokens`, `logprobs`, and `advantages` |

For a prompt followed by a completion:

- `model_input` is every token except the last.
- `target_tokens` is every token except the first.
- `weights` is `0` on prompt positions and `1` on completion positions.
- `logprobs` are the sampler's log probabilities of the completion tokens, and
  `0` on prompt positions.
- `advantages` hold the completion's advantage on completion positions, and `0`
  on prompt positions.

<Warning>
  Prompt rendering, tokenization, datum construction, and reward execution run
  in your code. Check tensor lengths before you send a batch. Validate a small
  batch before a larger workload. A datum longer than the model's context
  length fails the call.
</Warning>

Only the built-in loss functions above are supported. A loss written in your
own code can't run on the job.

## Keep dependent work ordered

The job runs calls in the order it receives them, so you can queue an
optimizer step right after a forward-backward pass. Read the forward-backward
result before you treat that step as complete. Wait for the optimizer step to
complete before you save the updated state.

Don't let independent controllers send updates to the same job without
coordinating. To cancel an unfinished sample, call
`POST /v1/training/jobs/{job_id}/futures/{future_id}/cancel`. Training
calls can't be cancelled.

An interactive job with no calls for 30 minutes is released, and later
training calls fail. Its checkpoints are kept, so you can start a new job from
the latest state checkpoint.

## Recover the loop

Persist the job ID, the application step, the dataset cursor, and the latest
checkpoint path. A restarted controller can then tell which work completed
without replaying an update.

For the recovery sequence and checkpoint kinds, follow
[Checkpoints and recovery](/training/checkpoints).

To continue from a saved state in a new job, pass the checkpoint's
`path` as `from_checkpoint` to `POST /v1/training/jobs/create-model`.
The new job has a new ID; persist both job IDs as application-owned lineage.
