Your application decides what to sample, how to score it, and when to update.
Fastino executes the interactive model operations. A `TrainingClient`
represents one interactive Fastino job throughout the loop.

## The control loop

<Steps>
  <Step title="Create the interactive job">
    Choose an enabled `base_model` from the capability response, then call
    `create_lora_training_client(...)` with documented settings. Capabilities
    do not report ranks, losses, or operation limits. Read the canonical job ID
    from `training_client.get_info().model_id`.
  </Step>
  <Step title="Checkpoint weights for sampling">
    Call `save_weights_for_sampler(name, ttl_seconds=24 * 60 * 60)`, then create a sampling client from
    the returned checkpoint path. This ties the rollout policy to an explicit
    artifact of the same job.
  </Step>
  <Step title="Collect rollout groups">
    Sample several candidate responses for each prompt. Your application owns
    prompt construction, response rendering, and grouping.
  </Step>
  <Step title="Compute rewards and advantages">
    Score each response, then transform rewards into the advantages required by
    your selected documented training operation.
  </Step>
  <Step title="Build training datums">
    Combine model inputs, sampled response tokens, sampling metadata, and
    token-level training signals in the SDK's expected shape for the selected
    documented training operation.
  </Step>
  <Step title="Update the same job">
    Submit supported forward/backward work, then an optimizer step, through the
    existing `TrainingClient`.
  </Step>
  <Step title="Save a recovery boundary">
    Save a state checkpoint and persist its identifier with the application
    step and dataset cursor before beginning the next iteration.
  </Step>
</Steps>

## Object model

| Object | Role |
| --- | --- |
| `ServiceClient` | Queries capabilities and creates SDK clients |
| `TrainingClient` | Represents one interactive Fastino job and submits its model operations |
| `SamplingClient` | Samples from a resolved checkpoint |
| `RestClient` | Lists or gets interactive runs and uses supported SDK methods to administer their checkpoints; use `/v1/training/jobs` to read both job types |
| Future | Tracks one operation submitted to the job |

The SDK model ID is the canonical Fastino job ID. Futures and sampling clients
do not create independent runs.

To turn deterministic grading into group-relative advantages, follow
[Train with verifiable rewards](/training/verifiable-rewards).

## Build aligned datums

For an importance-sampling-style loop, the prompt is context and the sampled
completion is the action. Keep token arrays aligned with the SDK and renderer
used by the selected model:

- Model input containing prompt and completion tokens
- Target tokens aligned to the model input
- Sampling log probabilities aligned to generated tokens
- Advantages applied to completion positions

<Warning>
  Prompt rendering, tokenization, datum construction, and reward execution are
  client-owned. Validate their shapes against the [tested SDK](/training/migrate-from-tinker) and the
  documented operation contract before a larger workload. The capability
  response only lists enabled models and advertised context lengths.
</Warning>

## Keep dependent work ordered

Resolve a forward/backward future before treating that stage as complete, and
resolve the optimizer future before checkpointing the updated state. Do not let
independent controllers mutate the same job without application-level
coordination.

The SDK performs these interactive operations. Do not reproduce them as direct
HTTP calls.

Track each future returned by a supported call. Resolve futures individually.
Only sampling futures can be cancelled. Batch retrieval through
`retrieve_futures` is not supported.

## Recover the loop

Persist the canonical job ID, the application step, the dataset cursor, and
the relevant future or checkpoint identifiers. A restarted controller can then
determine which work completed without replaying an update.

For the recovery sequence and checkpoint kinds, follow
[Checkpoints and recovery](/training/checkpoints).

One `TrainingClient` updates one job during its lifetime. Creating a client from
a saved state starts a new interactive job seeded from the source checkpoint;
persist both job IDs as application-owned lineage.
