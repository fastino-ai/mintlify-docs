---
title: "Checkpoints and recovery"
description: "Save interactive-job state and application progress, then recover without replaying completed work."
---

A state checkpoint protects server-side training state. A complete recovery
record also protects the user-owned state that tells your controller what to do
next. Native JSON clients use the public checkpoint operations. Tinker clients
use the matching SDK methods.

## What to save

| Record | Contains | Stored by |
| --- | --- | --- |
| State checkpoint | Training weights and optimizer state represented by the SDK checkpoint | Fastino |
| Loop record | Source job ID, checkpoint path, step, dataset cursor, configuration, and resume lineage | Your application |

The SDK training client represents one interactive Fastino job. Read its
canonical ID from `training_client.get_info().model_id`.

## 1. Save state and loop progress

Save state through the SDK, then persist the returned checkpoint with the
client-owned fields needed to continue:

```python
import json
from pathlib import Path


source_job_id = training_client.get_info().model_id
state = training_client.save_state(f"step-{step:06d}").result()
record = {
    "source_job_id": source_job_id,
    "state_path": state.path,
    "model": model_name,
    "dataset_revision": dataset_revision,
    "optimizer": optimizer_config,
    "step": step,
    "dataset_cursor": dataset_cursor,
    "reward_version": reward_version,
}

with Path(log_path).open("a", encoding="utf-8") as checkpoint_log:
    checkpoint_log.write(json.dumps(record, sort_keys=True) + "\n")
```

Use unique checkpoint names so each loop record identifies an unambiguous
recovery boundary.

## 2. Read the newest complete record

A process can stop while writing the final line. Scan backward and skip a
malformed tail:

```python
def get_last_checkpoint(log_path: str) -> dict[str, object] | None:
    path = Path(log_path)
    if not path.exists():
        return None

    for line in reversed(path.read_text(encoding="utf-8").splitlines()):
        try:
            record = json.loads(line)
        except json.JSONDecodeError:
            continue
        if isinstance(record, dict) and isinstance(record.get("state_path"), str):
            return record
    return None
```

## 3. Validate before loading

Compare the record with the source checkpoint and requested continuation:

- Source job ID encoded by the checkpoint path
- Base model and trainable configuration
- Dataset revision and cursor
- Reward implementation revision
- Optimizer configuration
- Renderer and tokenizer assumptions

Stop for an explicit decision if these fields conflict. Do not silently combine
a checkpoint with a different experiment.

Native clients create a new job with `from_checkpoint`, or send a state name or
the same job's `tinker://` path to
[`load-weights`](/api-reference/training-jobs/interactive/load-weights).
Tinker clients use the supported state-load flow:

```python
training_client = (
    service_client.create_training_client_from_state_with_optimizer(
        str(resume["state_path"])
    )
)
resumed_job_id = training_client.get_info().model_id
```

This factory creates a new interactive job, then loads the source checkpoint's
weights and optimizer state into it. The resumed job ID normally differs from
the source job ID. Record `source_job_id`, `state_path`, and `resumed_job_id` as
application-owned lineage. Do not reject a continuation because the two job IDs
differ. Do not construct private compatibility child routes.

## 4. Make the boundary recoverable

Use this order:

1. Resolve the forward/backward and optimizer futures.
2. Save the state checkpoint.
3. Persist the loop record containing its identifier.
4. Mark the application step complete.
5. Begin the next step.

If the process exits after saving the checkpoint but before persisting the loop
record, keep the previous complete record as the trusted recovery point. Do not
mark a step complete before its record is durable.

## 5. Keep checkpoint kinds separate

```python
state = training_client.save_state("step-000100").result()
sampler = training_client.save_weights_for_sampler(
    "step-000100",
    ttl_seconds=24 * 60 * 60,
).result()
```

Use a state checkpoint for training recovery. Use a sampler checkpoint for
rollouts or evaluation. Do not use a sampler checkpoint as an optimizer-state
recovery point.

`ttl_seconds` defaults to `None`, so an omitted TTL creates a checkpoint with no
automatic expiration. Live checkpoints count toward checkpoint storage. To
enable automatic cleanup, pass an inclusive value from `3_600` to
`315_360_000` seconds (1 hour to 10 years).

The public Training API saves training state through
[`save-weights`](/api-reference/training-jobs/interactive/save-weights) and
sampling weights through
[`save-weights-for-sampler`](/api-reference/training-jobs/interactive/save-sampler-weights).
The direct load and sample routes accept a checkpoint name or the same job's
`tinker://` path. Sampling remains available after the job is stopped. The
shared list and download routes cover interactive checkpoints, and download
still requires weight-download access. Tinker provides matching SDK methods.
Do not construct private compatibility child routes or assume an undocumented
retention period.

## 6. Verify the continuation

Before scaling the resumed workload:

1. Load the selected state checkpoint.
2. Read the new ID from `training_client.get_info().model_id`, persist it as
   `resumed_job_id`, and confirm it through
   `GET /v1/training/jobs/{resumed_job_id}`.
3. Run a small held-out evaluation.
4. Submit one supported training update.
5. Save a new state checkpoint under a new name.
6. Persist the next loop record.

Use either the native JSON operations or the supported Tinker SDK for
interactive model operations.

## Diagnose recovery errors

| Symptom | Check |
| --- | --- |
| A future fails | Record the job ID and future result. Do not advance dependent application state |
| A checkpoint cannot be loaded | Verify its job, checkpoint kind, and client-owned recovery record |
| Source checkpoint is rejected | Confirm its source job, checkpoint kind, and persisted `state_path`; do not require the new job ID to equal the source ID |
| Resumed job lookup fails | Confirm that the ID came from the resumed client's `get_info().model_id` and that the same Fastino team is authenticated |
