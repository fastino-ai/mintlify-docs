Evaluate GLiNER 2.5 Decide on labeled examples from your application before using its classifications to trigger production actions.

## Understand threshold behavior

`cls_threshold` applies only to tasks with `multi_label: true`:

```json
{
  "task": "topics",
  "labels": ["billing", "technical", "account", "security"],
  "multi_label": true,
  "cls_threshold": 0.5
}
```

- Raise the threshold to return fewer labels and generally favor precision.
- Lower the threshold to return more labels and generally favor recall.
- Single-label tasks always return the highest-scoring label; `cls_threshold` does not change their selection.
- `cls_threshold` is an inference setting. It does not affect training.

## Build an evaluation set

Use examples that represent production traffic, including:

- Common inputs for every label
- Rare but important labels
- Ambiguous inputs near category boundaries
- Inputs that should receive several labels
- Inputs that should receive no multi-label result at the selected threshold
- Out-of-domain or malformed inputs your application may encounter

Keep evaluation data separate from fine-tuning data.

## Measure the behavior your application needs

For single-label tasks, review overall accuracy and per-label errors. A confusion matrix helps expose labels the model frequently swaps.

For multi-label tasks, measure precision, recall, and F1 both overall and per label. Also inspect:

- False positives that trigger incorrect actions
- False negatives that skip required actions
- The number of labels selected per input
- The frequency of empty selections
- Results close to your threshold

## Select a threshold

1. Run the evaluation set and retain each selected label and confidence.
2. Test several candidate thresholds.
3. Compare precision, recall, and business impact.
4. Choose a threshold per task when tasks have different error costs.
5. Re-run evaluation after changing labels, data, or the model.

Do not assume `0.5` is universally appropriate. For high-impact actions, use conservative automation thresholds and preserve a review or fallback path.

## Fine-tune for your domain

Start with runtime-defined labels and evaluate the base model first. Fine-tune when representative evaluation shows that schema changes and threshold tuning do not meet the quality required for your domain.

### 1. Confirm the training target

Query the [base-model catalog](/api-reference/training/base-models) and confirm that the selected classification model supports the training type you intend to use.

### 2. Prepare classification data

Store one JSON object per line. Use `label` for single-label examples:

```jsonl
{"text":"The setup was straightforward.","label":"positive"}
{"text":"The application crashes during sign in.","label":"negative"}
```

Use `labels` for multi-label examples:

```jsonl
{"text":"The app crashes on login and I need help urgently.","labels":["technical_issue","login_problem","urgent"]}
```

Use stable label names that match the taxonomy your inference schema will use. Include representative examples for every label and preserve a separate evaluation split.

### 4. Evaluate the trained result

Compare the trained model with the base model on the same held-out set:

- Overall and per-label accuracy for single-label tasks
- Precision, recall, and F1 for multi-label tasks
- Errors on rare and high-impact labels
- Behavior near production thresholds
- Latency and operational requirements

Do not select a checkpoint from training loss alone. Evaluate the classification behavior your application will use.

### 5. Use the trained model

After the selected checkpoint is deployable, use its model identifier with the supported inference endpoint and keep the same classification schema expected by your application. Revalidate thresholds because confidence behavior can change after fine-tuning.
