`POST /v1/training/jobs/{job_id}/stop`

<Warning>
  The renamed `/v1/training/jobs` surface is verified in development, not production. Production may return `404`.
</Warning>

Stops a running job and preserves checkpoints created before the stop. For an
interactive job, the request returns immediately and rejects new calls. Already
queued operations may finish before resources are released, and usage may
continue until that release.

## Request

<ParamField header="X-API-Key" type="string" required>
  Your Fastino API key.
</ParamField>

<ParamField path="job_id" type="string" required>
  Config-job UUID or interactive job ID.
</ParamField>

### Config job

The JSON body is optional for a config job.

<ParamField body="reason" type="string">
  Why the job was stopped.
</ParamField>

<ParamField body="scores" type="object">
  Numeric metrics used to make the stop decision.
</ParamField>

<ParamField body="checkpoint" type="string">
  Checkpoint path or step associated with the stop.
</ParamField>

### Interactive job

Send no request body. The response includes the verified common fields
`success`, `job_id`, and `status`.

### Config-job request example

<RequestExample>

```bash cURL
curl -X POST https://api.fastino.ai/v1/training/jobs/YOUR_TRAINING_JOB_ID/stop \
  -H "X-API-Key: $FASTINO_API_KEY" \
  -H "Content-Type: application/json" \
  -d '{"reason": "Validation loss stopped improving"}'
```

</RequestExample>

### Interactive-job request example


<RequestExample>

```bash cURL
curl -X POST https://api.fastino.ai/v1/training/jobs/YOUR_INTERACTIVE_JOB_ID/stop \
  -H "X-API-Key: $FASTINO_API_KEY"
```

</RequestExample>

## Config-job response

<ResponseExample>

```json Response
{
  "success": true,
  "message": "Training job stopped successfully. Checkpoints preserved.",
  "job_id": "YOUR_TRAINING_JOB_ID",
  "status": "stopped"
}
```

```json 202 — cancellation pending
{
  "success": true,
  "message": "Cancellation in progress. The job moves to 'stopped' once the provider confirms; checkpoints are preserved.",
  "job_id": "YOUR_TRAINING_JOB_ID",
  "status": "stopping"
}
```

</ResponseExample>

The `message` field, `202` response, and polling rule apply only to config jobs.
Poll `GET /v1/training/jobs/{job_id}` after a config-job `202`; do not repeat
the stop request while cancellation is pending.

## Interactive-job response

An interactive job uses the same operation without a body. It returns the
common fields `success`, `job_id`, and `status`. Do not require the config-only
`message` field from an interactive response.

```json Response
{
  "success": true,
  "job_id": "YOUR_INTERACTIVE_JOB_ID",
  "status": "stopped"
}
```

## Config-job statuses

The following statuses and error details apply only to config jobs.

| Status | Meaning |
| --- | --- |
| `200` | The job is stopped and existing checkpoints remain available. |
| `202` | Cancellation is in progress while the provider confirms it. |
| `400` | The config-job ID or request is invalid. |
| `409 training_job_already_finished` | The job reached a terminal state before the stop. |
| `409 cancellation_unconfirmed` | Provider cancellation was not confirmed. Read the job state, then retry when appropriate. |
| `422` | The config-job JSON request body is invalid. |

## Config-job authorization

For config jobs, this operation requires the Owner, Admin, or Editor team role. Other roles receive `403 Forbidden`. The native interactive handler uses the interactive runtime's caller authorization; do not infer config-job RBAC from this shared path.
