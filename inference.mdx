Run inference with Fastino models through one of two API contracts. Each contract has its
own request and response shape, and their fields are not interchangeable.

  <Card title="Run GLiNER" icon="braces" href="/inference/chat-completions">

| If you need to… | Model family | Endpoint | Request shape | Read the result from |
| --- | --- | --- | --- | --- |
| Decide yes/no, route to one option, or score on an ordered scale | GLiDE | [`POST /v1/systemone`](/inference/systemone) | `model`, `state`, `questions` | `answers.<question_key>` |
| Extract spans, classify text, build records, or extract relations | GLiNER | [`POST /v1/chat/completions`](/inference/chat-completions) | `model`, `messages`, `schema` | JSON parsed from `choices[0].message.content` |

For GLiDE concepts and primitive selection, start with [Decision Models](/concepts/glide).
The [GLiDE inference guide](/inference/systemone) covers the HTTP integration.

## Confirm routing and retention

Successful calls to `POST /v1/systemone`, `/v1/chat/completions`,
`/v1/responses`, `/v1/messages`, and `/v1/gliner-2` return two diagnostic
headers:

- `X-Fastino-Data-Retention` is `zero` for team Zero Data Retention,
  `not-stored` when the request opted out of inference history, or `stored`
  otherwise.
- `X-Fastino-Served-Model` is the canonical model that handled the call. It is
  the fine-tuned model ID when a fine-tune served the request and the base-model
  ID otherwise.

Inspect them when verifying an integration:

```bash
curl -sS -D - -o response.json https://api.fastino.ai/v1/systemone \
  -H "X-API-Key: $FASTINO_API_KEY" \
  -H "Content-Type: application/json" \
  --data @request.json
```

The headers are absent on error responses and streams that fail before provider
dispatch. A stream that fails after dispatch retains them and reports its error
in-band.

## Cold starts and retries

An idle or newly deployed model may cold-start. Use a read timeout of at least 300 seconds
and bounded backoff for `425`, `429`, and `503` responses. Respect `Retry-After` when
present.

A timed-out request can still warm the deployment, allowing the next request to succeed. Do
not retry authentication, billing, validation, or unknown-model errors without correcting the
underlying problem.
