---
title: "Checkpoint and resume an RL run"
description: "Save model and optimizer state, persist loop progress, and resume RL without replaying completed work."
---

An RL checkpoint protects model state. A complete resume record also protects
the application state that tells your loop what to do next.

Use this pattern for long jobs, preemptible orchestrators, and agent-managed
experiments.

## What must be saved

Treat a resumable step as two coordinated records:

| Record | Contains | Stored by |
| --- | --- | --- |
| State checkpoint | LoRA weights and optimizer state | RL API |
| Loop record | Step, dataset cursor, configuration, and checkpoint path | Your application |

Saving only model state can restore the policy but cannot tell the application
which examples were already processed. Saving only a step number cannot restore
the policy that produced it.

## Before you start

Complete the [Quickstart](/rl-api/quickstart) first to verify authentication,
model access, and sampling. The Quickstart does not create a training run.
Continue only after your enabled Fastino environment can complete one small
training update and save and restore a state checkpoint.

## 1. Save state and loop progress

Save server-side training state, then persist the returned path with the
client-owned fields required to reconstruct the run:

```python
import json
from pathlib import Path


state = training_client.save_state(f"step-{step:06d}").result()
record = {
    "state_path": state.path,
    "model": model_name,
    "rank": lora_rank,
    "dataset_revision": dataset_revision,
    "optimizer": optimizer_config,
    "renderer": renderer_name,
    "tokenizer": tokenizer_name,
    "step": step,
    "dataset_cursor": dataset_cursor,
    "reward_version": reward_version,
}
with Path(log_path).open("a", encoding="utf-8") as checkpoint_log:
    checkpoint_log.write(json.dumps(record, sort_keys=True) + "\n")

print(state.path)
```

The returned path has this shape:

```text
tinker://<run-id>/weights/step-000100
```

The snippet does not assign a time-to-live. Set retention explicitly through
supported checkpoint administration operations for rolling recovery artifacts.
Keep a final checkpoint without a TTL when it is an artifact you intend to
retain.

<Warning>
  `save_state(...)` does not request overwrite. Reusing a checkpoint name is
  rejected. `save_state(..., overwrite=True)` can replace a state checkpoint
  explicitly, but unique names are safer recovery markers.
</Warning>

## 2. Find the newest recorded resume point

At process startup, scan backward for the newest parseable local record that
contains a state path. A process can stop while writing the final JSONL line, so
skip a malformed tail instead of losing the previous recovery point:

```python
def get_last_checkpoint(log_path: str) -> dict[str, object] | None:
    path = Path(log_path)
    if not path.exists():
        return None
    for line in reversed(path.read_text(encoding="utf-8").splitlines()):
        try:
            record = json.loads(line)
        except json.JSONDecodeError:
            continue
        if isinstance(record, dict) and isinstance(record.get("state_path"), str):
            return record
    return None


resume = get_last_checkpoint(log_path)
```

Handle both paths explicitly:

```python
if resume is None:
    training_client = service_client.create_lora_training_client(
        base_model=model_name,
        rank=lora_rank,
    )
    start_step = 0
    dataset_cursor = 0
else:
    saved_step = resume.get("step")
    saved_cursor = resume.get("dataset_cursor")
    if not isinstance(saved_step, int) or not isinstance(saved_cursor, int):
        raise ValueError("resume record has no valid step or dataset cursor")

    training_client = (
        service_client.create_training_client_from_state_with_optimizer(
            str(resume["state_path"])
        )
    )
    start_step = saved_step + 1
    dataset_cursor = saved_cursor
```

`create_training_client_from_state_with_optimizer(...)` creates a new ordered
training run from the saved weights and optimizer state.

## 3. Validate the resume record

Before training continues, compare the stored loop record with the requested
run:

```python
if resume is not None and resume.get("reward_version") != reward_version:
    raise ValueError(
        "reward implementation changed; start a new run or approve the change"
    )
```

Validate at least:

- Base model
- LoRA rank and trainable layout
- Dataset revision and cursor
- Reward implementation revision
- Optimizer family and intended schedule
- Renderer and tokenizer assumptions

An agent should stop and ask for a decision when these fields conflict. It
should not silently combine a checkpoint with a different experiment.

## 4. Make the step boundary atomic

Use this order:

1. Resolve the training and optimizer futures.
2. Save the state checkpoint.
3. Persist the loop record containing the returned path.
4. Mark the application step complete.
5. Start the next step.

If the process exits after step 2 but before step 3, the server may hold an
unreferenced checkpoint. That wastes storage but does not corrupt the previous
resume point. A later cleanup can delete it.

Do not mark a step complete before the checkpoint path is durable.

## 5. Keep sampler artifacts separate

Use a state checkpoint to resume training:

```python
state = training_client.save_state("step-000100").result()
```

Use sampler weights for evaluation, rollouts, or SDK inference:

```python
sampler = training_client.save_weights_for_sampler(
    "step-000100"
).result()
```

The two paths have different purposes:

```text
tinker://<run-id>/weights/<name>
tinker://<run-id>/sampler_weights/<name>
```

Do not select a sampler checkpoint as the optimizer resume point.

## 6. Bound storage

A practical retention policy uses:

- Short-lived rolling state checkpoints for crash recovery
- Longer-lived periodic state and sampler checkpoints for comparison
- One permanent final checkpoint

Implement retention in your application by assigning unique checkpoint names,
setting explicit TTLs through supported checkpoint operations, and deleting
artifacts that leave your recovery or evaluation window. Checkpoint storage is
metered over time.

## Recovery decisions for agents

| Situation | Action |
| --- | --- |
| No local resume record | Start a new run |
| Resume record and checkpoint both exist | Validate metadata, then restore |
| Local record exists but checkpoint is gone | Stop and ask the user; do not assume an earlier record belongs to the intended run |
| Checkpoint exists without a local record | Treat it as unclassified; do not guess its dataset cursor |
| Reward or dataset revision changed | Start a new experiment unless the user approves continuation |
| Live run reports unrecoverable state | Restore from the latest explicit state checkpoint |

## Verify the resumed run

Before a large continuation:

1. Restore the checkpoint.
2. Run a small held-out evaluation.
3. Compare it with the metric recorded at save time.
4. Submit one training step.
5. Save a new checkpoint under a new name.

Exact samples can vary. The restored model should retain the expected quality,
the optimizer step should complete, and the new checkpoint should be
addressable.

Always close the service client. Record the outcome accurately:

```python
service_client.close("success").result()  # completed run
```

Use `errored` when an exception escapes and `interrupted` after cancellation or
shutdown. Do not label a failed recovery as successful.

For the complete lifecycle and administrative operations, see the
[runtime behavior and errors reference](/rl-api/runtime).
