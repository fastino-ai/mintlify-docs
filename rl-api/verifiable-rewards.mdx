title: "Train with verifiable rewards"

This guide shows how to turn a deterministic grader into a learning signal.
Use it when a response can be checked by code, such as a math answer, test
result, schema constraint, exact extraction, or tool-use outcome.

The pattern is:

```text
prompt -> sample a group -> grade -> center rewards -> build datums -> update
```

## What you will build

For every problem, the loop:

1. Samples several candidate responses from the current policy.
2. Assigns each response a reward from `0.0` to `1.0`.
3. Centers rewards within the group.
4. Trains on responses with nonzero advantages.

This is a GRPO-style update. It does not require a separate learned reward
model.

## Before you start

Complete the [Quickstart](/rl-api/quickstart) first. Keep its working
environment, supported model, renderer, and client configuration. Start this
guide only after the two-step baseline run succeeds.

## 1. Define the grader contract

A useful deterministic grader has a narrow contract:

```python
def get_reward(response: str, expected: str) -> float:
    """Return a finite reward where larger means better."""
    actual = parse_answer(response)
    if actual is None:
        return 0.0
    return 1.0 if actual == expected else 0.0
```

Keep parsing separate from scoring. This makes malformed output observable
instead of treating it as an exception in the training loop.

For a structured-output task:

```python
import json


def parse_label(response: str) -> str | None:
    try:
        value = json.loads(response)
    except json.JSONDecodeError:
        return None

    if not isinstance(value, dict):
        return None
    label = value.get("label")
    return label if isinstance(label, str) else None


def get_reward(response: str, expected: str) -> float:
    label = parse_label(response)
    return 1.0 if label == expected else 0.0
```

<Tip>
  Log parse failures separately from incorrect valid answers. They need
  different prompt or reward fixes.
</Tip>

## 2. Sample a group from the current policy

At the start of each training iteration, create a sampler from the current
weights:

```python
sampling_client = training_client.save_weights_and_get_sampling_client()

future = sampling_client.sample(
    prompt=model_input,
    num_samples=group_size,
    sampling_params=sampling_params,
)
sample_result = future.result()
```

Record both the generated tokens and their sampling log probabilities. The
importance-sampling loss needs both.

## 3. Convert rewards to advantages

Grade each response, then subtract the group mean:

```python
rewards = [
    get_reward(render_response(sequence.tokens), expected)
    for sequence in sample_result.sequences
]

mean_reward = sum(rewards) / len(rewards)
advantages = [reward - mean_reward for reward in rewards]
```

Skip groups where every advantage is zero:

```python
if all(advantage == 0.0 for advantage in advantages):
    continue
```

All-correct and all-incorrect groups carry no relative signal. Track their rate.
A high degenerate-group rate usually means the task is too easy, too hard, or
the reward is not discriminating between outputs.

## 4. Build one datum per response

The prompt is context, so its advantage is zero. The generated response carries
the group-relative advantage:

```python
import tinker
import torch
from tinker import TensorData


def build_datum(
    prompt: tinker.ModelInput,
    tokens: list[int],
    logprobs: list[float],
    advantage: float,
) -> tinker.Datum:
    prompt_loss_length = prompt.length - 1
    model_input = prompt.append(
        tinker.EncodedTextChunk(tokens=tokens[:-1])
    )

    target_tokens = [0] * prompt_loss_length + tokens
    padded_logprobs = [0.0] * prompt_loss_length + logprobs
    padded_advantages = (
        [0.0] * prompt_loss_length
        + [advantage] * (model_input.length - prompt_loss_length)
    )

    if not (
        model_input.length
        == len(target_tokens)
        == len(padded_logprobs)
        == len(padded_advantages)
    ):
        raise ValueError("RL datum arrays are not aligned")

    return tinker.Datum(
        model_input=model_input,
        loss_fn_inputs={
            "target_tokens": TensorData.from_torch(
                torch.tensor(target_tokens)
            ),
            "logprobs": TensorData.from_torch(
                torch.tensor(padded_logprobs)
            ),
            "advantages": TensorData.from_torch(
                torch.tensor(padded_advantages)
            ),
        },
    )
```

Use the tokenizer and renderer associated with the selected base model. Do not
decode with one renderer and rebuild inputs with another.

## 5. Apply the update

Flatten the non-degenerate groups into one datum list, then submit the update:

```python
if datums:
    train_future = training_client.forward_backward(
        datums,
        loss_fn="importance_sampling",
    )
    optim_future = training_client.optim_step(
        tinker.AdamParams(
            learning_rate=4e-5,
            beta1=0.9,
            beta2=0.95,
        )
    )

    train_result = train_future.result()
    optim_result = optim_future.result()
```

The SDK orders these operations for the training client. Resolve both futures
and record their metrics before advancing your application step.

## 6. Checkpoint useful boundaries

Save full state on a fixed cadence and when the evaluation reward improves:

```python
checkpoint = training_client.save_state(
    f"step-{step:06d}"
).result()
print(checkpoint.path)
```

Store the returned `tinker://` path with:

- Application step
- Dataset revision
- Reward implementation revision
- Base model
- LoRA rank
- Optimizer parameters
- Evaluation metrics

That record lets an agent decide which checkpoint to resume without guessing
from names alone.

## Reward design checks

Before a long run, test the reward function against a frozen fixture set.

| Check | Why it matters |
| --- | --- |
| Correct output receives a higher reward | Proves the optimization direction |
| Malformed output does not crash the loop | Keeps one rollout from losing a batch |
| Equivalent valid formats normalize equally | Avoids training formatting accidents |
| Rewards are finite | Prevents invalid advantages |
| A sample batch has reward variance | Proves a relative learning signal exists |
| Hidden evaluation cases stay outside training | Prevents reward overfitting from masquerading as progress |

## Adapt the pattern

### Code generation

Run generated code in a resource-limited sandbox. Reward passed tests, then add
small bounded components for partial test coverage or efficiency. Never execute
untrusted model output in the training process.

### Tool use

Parse the tool call, validate its schema, execute against an isolated fixture,
and reward the resulting state. Grade the outcome, not only the syntax of the
call.

### Extraction and structured output

Validate against a schema and compare normalized values. Keep a separate format
reward only when output shape is genuinely part of the task.

### Multi-step environments

Accumulate transition rewards into a trajectory reward, then compute advantages
across trajectories for the same initial problem. Keep environment state and
side effects isolated between group members.

## Diagnose a run

| Signal | Interpretation | Next action |
| --- | --- | --- |
| Nearly every group is all zero | Task may be too hard or parser rejects valid responses | Inspect raw samples and parse-failure rate |
| Nearly every group is all one | Task may be too easy | Increase difficulty or use a stricter reward |
| Reward rises but held-out quality does not | Reward is being exploited | Add hidden checks and inspect high-reward failures |
| Datum alignment error | Renderer, token, log-probability, or padding mismatch | Print lengths for one response and compare with the recipe |
| Loss is unstable | Step size or reward scale may be too large | Lower learning rate and bound rewards |

## Completion criteria

A successful adaptation has:

- At least one non-degenerate group
- Finite reward, loss, and optimizer metrics
- A held-out evaluation independent of the training reward batch
- A restorable state checkpoint
- Enough logged metadata to reproduce the run
