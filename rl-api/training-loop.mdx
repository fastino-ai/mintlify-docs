The RL API separates the learning program from the model compute. Your process
decides what to sample, how to score it, and when to update. Fastino executes
sampling, forward and backward passes, optimizer steps, and checkpoint
operations.

## The control loop

<Steps>
  <Step title="Create a training client">
    Choose a supported base model and LoRA rank. The client represents one
    ordered training run with its own weights, optimizer state, and operation
    sequence.
  </Step>
  <Step title="Snapshot the current policy for sampling">
    For immediate same-run rollouts, call
    `save_weights_and_get_sampling_client()`. Its weights are ephemeral and can
    disappear when the run ends, parks, moves, rebuilds, or scales down. For a
    retryable boundary, call `save_weights_for_sampler(name)` and create a
    sampling client from the returned path. Rollouts should come from the policy
    you are about to improve, not from unrelated or stale weights.
  </Step>
  <Step title="Collect rollout groups">
    Send one prompt several times or request several samples in one call. A
    group gives the reward function alternatives to compare for the same
    problem.
  </Step>
  <Step title="Compute rewards and advantages">
    Score every response. Then transform rewards into advantages. In a
    GRPO-style loop, subtract the group's mean reward from each response's
    reward.
  </Step>
  <Step title="Build training datums">
    Combine prompt tokens, sampled response tokens, sampling log probabilities,
    and token-level advantages. Prompt tokens normally receive zero advantage.
  </Step>
  <Step title="Update the policy">
    Submit the datums with `forward_backward(...,
    loss_fn="importance_sampling")`, then call `optim_step(...)`.
  </Step>
  <Step title="Checkpoint and repeat">
    Save durable state at useful boundaries, create a fresh sampling client from
    the updated weights, and start the next iteration.
  </Step>
</Steps>

## Client object model

| Object | Responsibility | Typical lifetime |
| --- | --- | --- |
| `ServiceClient` | Opens a session, reports capabilities, creates training and sampling clients, and exposes the REST client | One logical application run |
| `TrainingClient` | Owns an ordered LoRA training run and its optimizer state | One policy being trained |
| `SamplingClient` | Samples or computes log probabilities from a base model or saved weights | One policy snapshot or reusable checkpoint |
| `RestClient` | Lists runs and checkpoints, manages checkpoint metadata and retention, and reports storage usage | Administrative operations |
| Future | Tracks one submitted operation and returns its result | One operation |

Closing a `ServiceClient` ends the session and releases its active training
runs. It does not delete checkpoints.

## Why grouped rewards work

Suppose four responses to one prompt receive these rewards:

```text
[1.0, 0.0, 1.0, 0.0]
```

The mean reward is `0.5`, so the group-relative advantages are:

```text
[0.5, -0.5, 0.5, -0.5]
```

Positive values reinforce tokens from responses that scored above the group
average. Negative values reduce the probability of below-average responses.

If every response receives the same reward, every centered advantage is zero.
That group carries no relative learning signal and can be skipped.

## What belongs in a datum

For the common importance-sampling loop, each datum contains:

- The prompt followed by the sampled completion
- Target tokens aligned with the model input
- Log probabilities recorded during sampling
- Advantages applied to completion tokens

The prompt prefix is context, not an action selected by the policy. Set its
advantage values to zero. Apply the response advantage to the generated token
positions.

<Warning>
  Token arrays must have the lengths expected by the renderer and SDK. Reuse
  the renderer that corresponds to the selected base model. A formatter from a
  different model can produce incorrect stop sequences or token alignment.
</Warning>

## Keep updates sequential

The SDK can submit multiple sampling futures, but qualify concurrency and
throughput against your enabled Fastino environment before depending on them.
Updates to one `TrainingClient` must remain sequential. Resolve
`forward_backward(...)` and `optim_step(...)` in order, and do not mutate one
training client from independent processes.

## Choose the right checkpoint

`save_state(name)` stores training weights and optimizer state for training
resume. `save_weights_for_sampler(name)` stores weights for evaluation or more
rollouts. A sampler checkpoint cannot restore optimizer state.

To build a complete recovery boundary, store the state-checkpoint path with
your application step and dataset position. Follow
[Checkpoint and resume](/rl-api/checkpoint-and-resume) for the full pattern.

To implement the loop with a deterministic grader, follow
[Train with verifiable rewards](/rl-api/verifiable-rewards).
