The RL API separates the learning program from the model compute. Your process
decides what to sample, how to score it, and when to update. Fastino executes
sampling, forward and backward passes, optimizer steps, and checkpoint
operations.

## The control loop

<Steps>
  <Step title="Create a training client">
    Choose a supported base model and LoRA rank. The client represents one
    ordered training run with its own weights, optimizer state, and operation
    sequence.
  </Step>
  <Step title="Snapshot the current policy for sampling">
    Call `save_weights_and_get_sampling_client()`. Rollouts should come from the
    policy you are about to improve, not from unrelated or stale weights.
  </Step>
  <Step title="Collect rollout groups">
    Send one prompt several times or request several samples in one call. A
    group gives the reward function alternatives to compare for the same
    problem.
  </Step>
  <Step title="Compute rewards and advantages">
    Score every response. Then transform rewards into advantages. In a
    GRPO-style loop, subtract the group's mean reward from each response's
    reward.
  </Step>
  <Step title="Build training datums">
    Combine prompt tokens, sampled response tokens, sampling log probabilities,
    and token-level advantages. Prompt tokens normally receive zero advantage.
  </Step>
  <Step title="Update the policy">
    Submit the datums with `forward_backward(...,
    loss_fn="importance_sampling")`, then call `optim_step(...)`.
  </Step>
  <Step title="Checkpoint and repeat">
    Save durable state at useful boundaries, create a fresh sampling client from
    the updated weights, and start the next iteration.
  </Step>
</Steps>

## Client object model

| Object | Responsibility | Typical lifetime |
| --- | --- | --- |
| `ServiceClient` | Opens a session, reports capabilities, creates training and sampling clients, and exposes the REST client | One logical application run |
| `TrainingClient` | Owns an ordered LoRA training run and its optimizer state | One policy being trained |
| `SamplingClient` | Samples or computes log probabilities from a base model or saved weights | One policy snapshot or reusable checkpoint |
| `RestClient` | Lists runs and checkpoints, manages visibility and retention, and reports storage usage | Administrative operations |
| Future | Tracks one submitted operation and returns its result | One operation |

Closing a `ServiceClient` ends the session and releases its active training
runs. It does not delete checkpoints.

## Why grouped rewards work

Suppose four responses to one prompt receive these rewards:

```text
[1.0, 0.0, 1.0, 0.0]
```

The mean reward is `0.5`, so the group-relative advantages are:

```text
[0.5, -0.5, 0.5, -0.5]
```

Positive values reinforce tokens from responses that scored above the group
average. Negative values reduce the probability of below-average responses.

If every response receives the same reward, every centered advantage is zero.
That group carries no relative learning signal and can be skipped.

## What belongs in a datum

For the common importance-sampling loop, each datum contains:

- The prompt followed by the sampled completion
- Target tokens aligned with the model input
- Log probabilities recorded during sampling
- Advantages applied to completion tokens

The prompt prefix is context, not an action selected by the policy. Set its
advantage values to zero. Apply the response advantage to the generated token
positions.

<Warning>
  Token arrays must have the lengths expected by the renderer and SDK. Reuse
  the renderer that corresponds to the selected base model. A formatter from a
  different model can produce incorrect stop sequences or token alignment.
</Warning>

## Ordered and idempotent updates

A training run is an ordered state machine. The SDK assigns sequence IDs to
operations such as forward and backward passes, optimizer steps, saves, and
loads.

If a request is retried with the same run, sequence ID, and body, the RL API
returns the original operation instead of applying it twice. Reusing that
sequence ID with a different body is rejected. This protects optimizer state
when a client retries after a network interruption.

Do not submit operations for one training client from independent processes
unless they share a single ordering mechanism.

## Live state and durable state

Training weights, pending gradients, and optimizer state are live state. The RL
API can attempt to reconstruct a run after idle scale-down or an infrastructure
interruption. Automatic recovery starts from a replay base and replays logged
`forward_backward` and `optim_step` mutations. It does not replay every API
operation, and recovery can fail when the outcome of a mutation is unknown or
required replay data is no longer available.

Your explicit checkpoints are the recovery boundary you control:

- `save_state(name)` stores training weights and optimizer state.
- `save_weights_for_sampler(name)` stores weights for sampling.
- `create_training_client_from_state_with_optimizer(path)` starts a new run with
  saved weights and optimizer state.
- `create_training_client_from_state(path)` starts from saved weights with a
  fresh optimizer.
- `load_state(path)` restores a compatible checkpoint into an existing run.

Save state before long external work, before a risky code change, and at
milestones you may want to compare or resume.

## Cost boundaries

Sampling is metered by input, cached input, and output tokens. Forward and
forward-backward operations are metered by training tokens. Checkpoint storage
is metered over time.

Creating a model client, applying an optimizer step, and saving or loading a
checkpoint do not add token usage by themselves. The token work and stored
bytes still determine the associated usage.

## A reliable production pattern

1. Query server capabilities at startup.
2. Pin an SDK version your application has tested.
3. Keep rollout generation concurrent, but keep training updates ordered.
4. Record the checkpoint path and application step together.
5. Use bounded retries around future result retrieval.
6. Close the service client in a `finally` block.
7. Retain only the checkpoints you need.

For concrete datum construction and a deterministic grader, continue to the
[verifiable rewards cookbook](/cookbooks/rl-verifiable-rewards).
