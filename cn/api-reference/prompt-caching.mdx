这是一份简短指南，介绍如何在任意客户端或智能体框架（Pi、Claude Code、自定义 curl、SDK 等）中稳定地命中提示缓存。

## 你需要知道的一件事

**对于 Claude / Anthropic 风格的模型，缓存在 API 层面需要主动启用，因此是否发生缓存取决于你的客户端。** Fastino 会原样转发你的请求，绝不会替你添加缓存标记。如果请求中不包含 `cache_control` 标记，稳定前缀就**不会**被缓存，你每一轮都要支付完整的输入价格。有些客户端会替你启用——例如 Claude Code 使用 Anthropic 的端点（这些端点要求 `cache_control`），因此会自动发送标记。而只发送纯字符串提示的简单自定义客户端则不会，因此无法获得缓存。

自动缓存的模型（OpenAI/GPT 系列）会透明地完成缓存，并且会**拒绝**显式标记——对于这些模型，你无需做任何操作，也不应添加 `cache_control`。

| 模型 | 你需要做什么 |
| --- | --- |
| Claude / Anthropic 风格 | 添加 `cache_control` 标记（见下文） |
| OpenAI / GPT 系列（自动缓存） | 无需操作——缓存是自动的 |
| 其他模型 | 如不确定，请添加标记；在支持的地方会被采纳，在模型自动缓存的地方会被忽略 |

你能够可靠控制的手段是 Claude 模型上的 `cache_control`。本指南的其余部分介绍如何正确使用它。

## 如何标记可缓存的前缀

将提示中稳定的部分作为带有 `cache_control` 标记的内容块发送。**直到并包括**被标记块在内的所有内容都会成为缓存前缀，并在之后共享完全相同前缀的请求中被复用。

所有基于消息的端点都会采纳标记，并以相同方式进行规范化：

- `POST /v1/chat/completions`（兼容 OpenAI）——标记 `system`/`user` 消息的内容块。
- `POST /v1/messages`（兼容 Anthropic）——标记 `system` 块、消息块或 tools 块。
- `POST /v1/responses`（OpenAI Responses）——标记输入消息上的内容块。稳定前缀通过 `system`/`developer` 输入消息块进行标记（纯 `instructions` 字符串无处放置标记）。

### 示例（`/v1/chat/completions`）

```bash
curl https://api.fastino.ai/v1/chat/completions \
  -H "Content-Type: application/json" \
  -H "X-API-Key: $FASTINO_API_KEY" \
  -d '{
    "model": "claude-opus-5",
    "messages": [
      {
        "role": "system",
        "content": [
          {
            "type": "text",
            "text": "Large stable system prompt or reusable context goes here.",
            "cache_control": { "type": "ephemeral" }
          }
        ]
      },
      { "role": "user", "content": "Answer in one sentence: what is prompt caching?" }
    ],
    "max_tokens": 512
  }'
```

system 内容必须是一个**内容块数组**（而不是纯字符串），这样标记才有可附加的块。纯字符串形式的系统提示无法携带标记，也不会被缓存。

## 标记应放在哪里

每个请求最多可以标记 **4 个断点**。请按前缀顺序，将它们放在每一轮之间保持不变的部分上：

1. **系统提示**——你的稳定指令/可复用上下文。
2. **工具定义**——如果你发送的是庞大且固定的工具集，请标记 tools 块。
3. **消息边界**——标记稳定对话前缀中的最后一条消息，以便在多轮会话中缓存到该点为止的历史记录。

每一轮都会变化的内容（最新的用户问题）应放在最后一个标记**之后**，这样缓存前缀才能保持一致并持续命中。

可选的 `ttl`（例如 `{ "type": "ephemeral", "ttl": "1h" }`）用于控制缓存的生命周期；省略时将使用提供商默认的临时缓存窗口。

## 最小可缓存大小

只有当可缓存前缀足够大时，缓存才会生效——大约为 **~1K–4K tokens，具体取决于模型**。较短的系统提示可能低于该阈值，此时即使标记正确也不会创建缓存条目。如果你预期会有缓存却没有看到缓存 token，请检查被标记的前缀是否确实足够大。

## 配置智能体框架

大多数框架都能生成这种结构，但需要明确告知它们对 Fastino 的 Claude 模型使用 Anthropic 风格的缓存控制。在配置自定义 Fastino 提供商时，请确保客户端设置为：

- 将系统提示作为**带有 `cache_control` 的内容块**发送（而不是裸字符串），并且
- 将稳定指令保留在 `role: "system"` 上。

如果你的框架提供了针对缓存控制格式的提供商兼容性选项，请将其设置为 Anthropic 风格。如果它只发送不带 `cache_control` 的纯字符串提示，那么即使同一框架在自动缓存模型上缓存正常，你在 Claude 模型上也无法获得缓存。

## 验证是否生效

检查响应中的 `usage` 块。字段名称因端点而异：

- **`/v1/chat/completions`**——在 `usage.prompt_tokens_details.cached_tokens` 下报告缓存读取。
- **`/v1/messages`**——报告 `cache_read_input_tokens` 和 `cache_creation_input_tokens`。

预期结果：

- 使用新前缀的**首次请求**：缓存写入/创建计数不为零。
- 复用该前缀的**后续请求**：缓存读取计数不为零，且未缓存的输入计数大幅降低。
- **全部为零**表示缺少标记、前缀低于最小大小、前缀在轮次之间发生了变化，或者模型是自动缓存的（节省依然有效，但不会以缓存 token 的形式报告）。

<Note>
  有些框架会将这些数据规范化为它们自己的字段（例如日志中的 `cacheRead` / `cacheWrite`）——数值相同，只是名称不同。
</Note>

## 如何读取结果

每个响应中的 token 用量都会按缓存状态拆分输入 token：

| 字段 | 含义 |
| --- | --- |
| `prompt_tokens` | 未缓存的输入 token |
| `cache_read_tokens` | 从缓存提供的输入 token（享受折扣） |
| `cache_write_tokens` | 本次请求写入缓存的输入 token |
| `completion_tokens` | 输出 token |
| `total_tokens` | 以上四项之和 |

## 计费

缓存输入比新输入更便宜。费率相对于模型的输入价格：

| 提供商 | 缓存读取 | 缓存写入 |
| --- | --- | --- |
| Claude / Opus | 0.1× 输入 | 1.25× 输入 |
| GPT-4 系列 | 0.5× 输入 | 按输入费率计费 |
| GPT-5 系列 | 0.1× 输入 | 按输入费率计费 |

填充缓存的首次请求需为这些 token 支付写入费率；之后命中缓存的请求则支付较低的读取费率。缓存的存活时间很短，因此节省来自于在短时间内连续发送相似的提示。

<Warning>
  缓存费用可在 **Settings → Credits** 中查看，并按模型或单个请求分别显示。
</Warning>

<Info>
  对于大多数 Anthropic 模型，系统提示必须至少有 **4096 tokens** 才能激活缓存。缓存条目在闲置 **5 分钟**后过期。
</Info>

## 常见陷阱

- **Claude 请求中没有 `cache_control`** → 没有缓存，每一轮都按全价计费。这是成本突然上涨最常见的原因。
- **系统提示以纯字符串发送** → 没有可附加标记的地方。
- **前缀太小** → 低于最小可缓存大小，因此不会创建条目。
- **缓存前缀在轮次之间发生变化**（例如系统提示开头的时间戳） → 缓存无法被复用。请保持被标记的前缀逐字节稳定。
- **在 `/v1/responses` 上标记 `instructions` 字段** → 它是纯字符串，无法携带标记；请改为将稳定前缀放在 `system`/`developer` 输入消息块中。
- **为自动缓存模型添加 `cache_control`** → 会被忽略或拒绝；让它自行缓存即可。
- **超过 4 个标记** → 只有前 4 个会生效。
