你的应用决定采样内容、评分方式和更新时机。Fastino 执行交互式模型操作。
原生客户端通过 `job_id` 寻址任务。Tinker `TrainingClient` 代表同一个任务。

## 控制循环

<Steps>
  <Step title="创建交互式任务">
    原生客户端使用 `base_model`，或使用 `from_checkpoint` 和 `load_optimizer`，调用
    [`POST /v1/training/jobs/create-model`](/cn/api-reference/training-jobs/interactive/create)。
    Tinker 客户端调用 `create_lora_training_client(...)`。原生客户端不发送 `seq_id`
    或心跳。
  </Step>
  <Step title="为采样创建权重检查点">
    调用 `save_weights_for_sampler(name, ttl_seconds=24 * 60 * 60)`，然后使用返回的检查点路径创建采样客户端。
    这会将 rollout 策略绑定到同一个任务的明确工件。
  </Step>
  <Step title="收集 rollout 组">
    为每个提示词采样多个候选响应。你的应用负责提示词构建、响应渲染和分组。
  </Step>
  <Step title="计算奖励和优势值">
    为每个响应评分，然后将奖励转换为所选且已记录的训练操作所需的优势值。
  </Step>
  <Step title="构建训练 datum">
    按 SDK 预期的形式组合模型输入、采样响应 token、采样元数据和 token 级训练信号。
  </Step>
  <Step title="更新同一个任务">
    通过现有 `TrainingClient` 提交受支持的前向/反向传播工作，然后执行优化器步骤。
  </Step>
  <Step title="保存恢复边界">
    在开始下一次迭代前，保存状态检查点，并将其标识符与应用步骤及数据集游标一起持久化。
  </Step>
</Steps>

## 对象模型

| 对象 | 作用 |
| --- | --- |
| `ServiceClient` | 查询功能并创建 SDK 客户端 |
| `TrainingClient` | 代表一个 Fastino 交互式任务并提交其模型操作 |
| `SamplingClient` | 从已解析的检查点采样 |
| `RestClient` | 列出或获取交互式运行并管理其检查点；使用 `/v1/training/jobs` 读取两种任务 |
| Future | 跟踪提交给任务的一项操作 |

SDK 模型 ID 就是规范的 Fastino 任务 ID。Future 和采样客户端不会创建独立运行。

要将确定性评分转换为组相对优势值，请参阅
[使用可验证奖励进行训练](/cn/training/verifiable-rewards)。

## 构建对齐的 datum

对于重要性采样式循环，提示词是上下文，采样到的补全是动作。确保 token 数组与所选模型
使用的 SDK 和渲染器对齐：

- 包含提示词和补全 token 的模型输入
- 与模型输入对齐的目标 token
- 与生成 token 对齐的采样对数概率
- 应用于补全位置的优势值

<Warning>
  提示词渲染、token 化、datum 构建和奖励执行均由客户端负责。在运行更大的工作负载前，
  请根据[经过测试的 SDK](/cn/training/migrate-from-tinker)和已记录的操作契约验证它们的形式。Capabilities
  仅报告已启用的模型及其上下文长度。
</Warning>

## 保持依赖工作有序

将前向/反向传播阶段视为完成之前，请先解析其 future；在为更新后的状态创建检查点之前，
请先解析优化器 future。没有应用级协调时，不要让独立控制器修改同一个任务。

原生 JSON 客户端调用
[`forward-backward`](/cn/api-reference/training-jobs/interactive/forward-backward)
和 [`optim-step`](/cn/api-reference/training-jobs/interactive/optim-step)。每个排队响应
都包含 `future_id`。轮询
[`get-operation`](/cn/api-reference/training-jobs/interactive/get-operation)，直到状态为
`completed`、`failed` 或 `cancelled`。一次 `wait=true` 请求可能在操作完成前返回。

Tinker 客户端跟踪受支持调用返回的每个 future，并逐个解析。两种接口都只有 sample
操作可以取消。不支持通过 `retrieve_futures` 批量检索。

## 恢复循环

持久化规范任务 ID、应用步骤、数据集游标以及相关的 future 或检查点标识符。
这样，重启后的控制器无需重放更新即可确定哪些工作已完成。

有关恢复顺序和检查点类型，请参阅[检查点与恢复](/cn/training/checkpoints)。

一个控制器在一个任务的生命周期内更新该任务。原生客户端可以从检查点创建任务，
Tinker 客户端可以从已保存状态创建任务。两条路径都会从来源检查点启动新的交互式
任务。请将两个任务 ID 记录为应用负责的沿袭关系。
