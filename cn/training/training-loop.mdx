你的应用决定采样内容、评分方式和更新时机。Fastino 执行交互式模型操作。
原生客户端通过 `job_id` 寻址任务。Tinker `TrainingClient` 代表同一个任务。

## 控制循环

<Steps>
  <Step title="创建交互式任务">
    原生客户端使用 `base_model`，或使用 `from_checkpoint` 和 `load_optimizer`，调用
    [`POST /v1/training/jobs/create-model`](/cn/api-reference/training-jobs/interactive/create-model)。
    Tinker 客户端调用 `create_lora_training_client(...)`。原生客户端不发送 `seq_id`
    或心跳。
  </Step>
  <Step title="保存用于采样的权重">
    使用名称调用 `POST /v1/training/jobs/{job_id}/save-weights-for-sampler`。
    从该检查点采样，使每个 rollout 都对应同一任务中的明确产物。
  </Step>
  <Step title="收集 rollout 组">
    使用 `POST /v1/training/jobs/{job_id}/sample` 并指定该检查点，
    为每个提示采样多个候选响应。提示构建、分词和分组由你的应用负责。
  </Step>
  <Step title="计算奖励和优势">
    为每个响应评分，然后将奖励转换为损失函数所需的优势。
  </Step>
  <Step title="构建训练 datum">
    将提示和响应 token 与逐位置的目标、权重、对数概率或优势组合起来。
  </Step>
  <Step title="更新同一个任务">
    发送 `POST /v1/training/jobs/{job_id}/forward-backward`，然后发送
    `POST /v1/training/jobs/{job_id}/optim-step`。
  </Step>
  <Step title="保存恢复边界">
    在开始下一次迭代之前，使用 `POST /v1/training/jobs/{job_id}/save-weights` 保存状态，并将其路径与应用步骤和数据集游标一起持久化。
  </Step>
</Steps>

## 路由

| 步骤 | 路由 |
| --- | --- |
| `ServiceClient` | 查询功能并创建 SDK 客户端 |
| `TrainingClient` | 代表一个 Fastino 交互式任务并提交其模型操作 |
| `SamplingClient` | 从已解析的检查点采样 |
| `RestClient` | 列出或获取交互式运行并管理其检查点；使用 `/v1/training/jobs` 读取两种任务 |
| Future | 跟踪提交给任务的一项操作 |

要将确定性评分转换为组相对优势，请参阅[使用可验证奖励训练](/cn/training/verifiable-rewards)。

## 构建对齐的 datum

datum 包含 N 个输入 token，以及 `loss_fn_inputs` 中各含 N 个值的张量。请使用基础模型的
Hugging Face tokenizer（`transformers.AutoTokenizer.from_pretrained(base_model)`）分词，并用同一个
tokenizer 解码采样结果。

| 损失函数 | 必需输入 |
| --- | --- |
| `cross_entropy` | `target_tokens`；可选 `weights`（默认处处为 `1`） |
| `importance_sampling`、`ppo`、`cispo`、`dro` | `target_tokens`、`logprobs` 和 `advantages` |

对于“提示 + 补全”：

- `model_input` 是除最后一个以外的所有 token。
- `target_tokens` 是除第一个以外的所有 token。
- `weights` 在提示位置为 `0`，在补全位置为 `1`。
- `logprobs` 是 sampler 对补全 token 给出的对数概率，提示位置为 `0`。
- `advantages` 在补全位置为该补全的优势，提示位置为 `0`。

<Warning>
  提示词渲染、token 化、datum 构建和奖励执行均由客户端负责。在运行更大的工作负载前，
  请根据[经过测试的 SDK](/cn/training/migrate-from-tinker)和已记录的操作契约验证它们的形式。Capabilities
  仅报告已启用的模型及其上下文长度。
</Warning>

仅支持上面的内置损失函数。在你自己的代码中编写的损失函数无法在任务上运行。

## 保持依赖工作有序

任务按接收顺序运行 operation，因此可以在 forward-backward 之后立即排队优化器步骤。
在将该步骤视为完成之前，请先读取 forward-backward 的结果。保存更新后的状态之前，请等待优化器步骤完成。

原生 JSON 客户端调用
[`forward-backward`](/cn/api-reference/training-jobs/interactive/forward-backward)
和 [`optim-step`](/cn/api-reference/training-jobs/interactive/optim-step)。每个排队响应
都包含 `future_id`。轮询
[`get-future`](/cn/api-reference/training-jobs/interactive/get-future)，直到状态为
`completed`、`failed` 或 `cancelled`。一次 `wait=true` 请求可能在 future 完成前返回。

Tinker 客户端跟踪受支持调用返回的每个 future，并逐个解析。两种接口都只有 sample
future 可以取消。不支持通过 `retrieve_futures` 批量检索。

## 恢复循环

持久化任务 ID、应用步骤、数据集游标和最新检查点路径。这样重启后的控制器就能判断哪些工作已完成，而无需重放更新。

关于恢复顺序和检查点类型，请参阅[检查点与恢复](/cn/training/checkpoints)。

一个控制器在一个任务的生命周期内更新该任务。原生客户端可以从检查点创建任务，
Tinker 客户端可以从已保存状态创建任务。两条路径都会从来源检查点启动新的交互式
任务。请将两个任务 ID 记录为应用负责的沿袭关系。
