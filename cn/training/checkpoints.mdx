状态检查点保护服务端训练状态。完整的恢复记录还会保护由用户负责、用于告诉控制器下一步操作的状态。

## 要保存的内容

| 记录 | 包含内容 | 存储方 |
| --- | --- | --- |
| 状态检查点 | SDK 检查点所表示的训练权重和优化器状态 | Fastino |
| 循环记录 | 来源任务 ID、检查点路径、步骤、数据集游标、配置和恢复沿袭 | 你的应用 |

SDK 训练客户端代表一个 Fastino 交互式任务。从
`training_client.get_info().model_id` 读取其规范 ID。

## 1. 保存状态和循环进度

通过 SDK 保存状态，然后持久化返回的检查点及继续运行所需的客户端字段：

```python
import json
from pathlib import Path


source_job_id = training_client.get_info().model_id
state = training_client.save_state(f"step-{step:06d}").result()
record = {
    "source_job_id": source_job_id,
    "state_path": state.path,
    "model": model_name,
    "dataset_revision": dataset_revision,
    "optimizer": optimizer_config,
    "step": step,
    "dataset_cursor": dataset_cursor,
    "reward_version": reward_version,
}

with Path(log_path).open("a", encoding="utf-8") as checkpoint_log:
    checkpoint_log.write(json.dumps(record, sort_keys=True) + "\n")
```

使用唯一的检查点名称，使每条循环记录都能标识明确的恢复边界。不要假设未记录的检查点生命周期。

## 2. 读取最新的完整记录

进程可能在写入最后一行时停止。反向扫描并跳过格式错误的尾部：

```python
def get_last_checkpoint(log_path: str) -> dict[str, object] | None:
    path = Path(log_path)
    if not path.exists():
        return None

    for line in reversed(path.read_text(encoding="utf-8").splitlines()):
        try:
            record = json.loads(line)
        except json.JSONDecodeError:
            continue
        if isinstance(record, dict) and isinstance(record.get("state_path"), str):
            return record
    return None
```

## 3. 加载前验证

将记录与来源检查点以及请求的继续运行进行比较：

- 检查点路径中编码的来源任务 ID
- 基础模型和可训练配置
- 数据集修订版和游标
- 奖励实现修订版
- 优化器配置
- 渲染器和 tokenizer 假设

如果这些字段冲突，请停止并要求明确决策。不要悄然将检查点与其他实验组合。

然后使用 SDK 支持的状态加载流程：

```python
training_client = (
    service_client.create_training_client_from_state_with_optimizer(
        str(resume["state_path"])
    )
)
resumed_job_id = training_client.get_info().model_id
```

此工厂方法先创建新的交互式任务，再将来源检查点的权重和优化器状态加载到新任务中。
恢复后的任务 ID 通常与来源任务 ID 不同。将 `source_job_id`、`state_path` 和
`resumed_job_id` 记录为应用负责的沿袭关系。不要因为两个任务 ID 不同而拒绝恢复，
也不要直接构造 SDK 的 HTTP 请求。

## 4. 使边界可恢复

按以下顺序操作：

1. 解析前向/反向传播和优化器 future。
2. 保存状态检查点。
3. 持久化包含其标识符的循环记录。
4. 将应用步骤标记为完成。
5. 开始下一步。

如果进程在保存检查点后、持久化循环记录前退出，请继续将上一条完整记录作为可信恢复点。
不要在记录持久保存前将步骤标记为完成。

## 5. 区分检查点类型

```python
state = training_client.save_state("step-000100").result()
sampler = training_client.save_weights_for_sampler(
    "step-000100",
    ttl_seconds=24 * 60 * 60,
).result()
```

使用状态检查点恢复训练。使用采样器检查点进行 rollout 或评估。不要将采样器检查点用作优化器状态恢复点。

`ttl_seconds` 默认为 `None`，因此省略 TTL 会创建不会自动过期的检查点。存活的
检查点会计入检查点存储。若要自动清理，请传入 `3_600` 到 `315_360_000`
秒（1 小时到 10 年）之间的值，包括端点值。

公开的训练 API 可以列出检查点。它可以下载交互式检查点。公开路由和 SDK 方法
`get_checkpoint_archive_url` 都需要权重下载权限。请参阅[从 Tinker 迁移](/cn/training/migrate-from-tinker)。SDK 还支持检查点删除、发布、保留期和存储用量方法。
这些是 SDK 操作，而不是公开的训练 API 路由。请勿构造等效的 SDK HTTP 请求，也不要假设未记录的保留期限。

## 6. 验证继续运行

扩大恢复后的工作负载之前：

1. 加载所选状态检查点。
2. 从 `training_client.get_info().model_id` 读取新 ID，将其持久化为
   `resumed_job_id`，并通过 `GET /v1/training/jobs/{resumed_job_id}` 确认。
3. 运行小型留出评估。
4. 提交一次受支持的训练更新。
5. 使用新名称保存新的状态检查点。
6. 持久化下一条循环记录。

所有交互式模型操作均使用 SDK。

## 诊断恢复错误

| 症状 | 检查项 |
| --- | --- |
| Future 失败 | 记录任务 ID 和操作结果。不要推进依赖的应用状态 |
| 无法加载检查点 | 验证其任务、检查点类型和客户端负责的恢复记录 |
| 来源检查点被拒绝 | 确认其来源任务、检查点类型和持久化的 `state_path`；不要要求新任务 ID 等于来源 ID |
| 恢复后的任务查找失败 | 确认 ID 来自恢复后客户端的 `get_info().model_id`，且已通过同一 Fastino 团队的身份验证 |
