RL API 将学习程序与模型计算分离。你的进程决定采样内容、评分方式和更新时机。Fastino
负责执行采样、前向和反向传播、优化器步骤及检查点操作。

## 控制循环

<Steps>
  <Step title="创建训练客户端">
    选择受支持的基础模型和 LoRA rank。客户端代表一次有序的训练运行，并拥有自己的权重、优化器状态和操作序列。
  </Step>
  <Step title="为采样创建当前策略的快照">
    调用 `save_weights_and_get_sampling_client()`。Rollout
    应来自你即将改进的策略，而不是无关或过时的权重。
  </Step>
  <Step title="收集 rollout 组">
    多次发送同一个提示词，或在一次调用中请求多个样本。同一问题的一组候选结果可供奖励函数进行比较。
  </Step>
  <Step title="计算奖励和优势值">
    为每个响应评分，然后将奖励转换为优势值。在 GRPO 风格的循环中，用每个响应的奖励减去该组的平均奖励。
  </Step>
  <Step title="构建训练 datum">
    组合提示词 token、采样响应 token、采样对数概率和 token 级优势值。提示词 token 的优势值通常设为零。
  </Step>
  <Step title="更新策略">
    使用 `forward_backward(...,
    loss_fn="importance_sampling")` 提交 datum，然后调用 `optim_step(...)`。
  </Step>
  <Step title="创建检查点并重复">
    在合适的边界保存持久状态，根据更新后的权重创建新的采样客户端，然后开始下一次迭代。
  </Step>
</Steps>

## 客户端对象模型

| 对象 | 职责 | 典型生命周期 |
| --- | --- | --- |
| `ServiceClient` | 打开会话、报告功能、创建训练和采样客户端，并提供 REST 客户端 | 一次逻辑应用运行 |
| `TrainingClient` | 拥有一次有序的 LoRA 训练运行及其优化器状态 | 一个正在训练的策略 |
| `SamplingClient` | 从基础模型或已保存权重进行采样或计算对数概率 | 一个策略快照或可复用检查点 |
| `RestClient` | 列出运行和检查点、管理可见性和保留策略，并报告存储用量 | 管理操作 |
| Future | 跟踪一个已提交的操作并返回其结果 | 一个操作 |

关闭 `ServiceClient` 会结束会话并释放其活跃的训练运行，但不会删除检查点。

## 分组奖励为何有效

假设针对一个提示词的四个响应获得以下奖励：

```text
[1.0, 0.0, 1.0, 0.0]
```

平均奖励为 `0.5`，因此组相对优势值为：

```text
[0.5, -0.5, 0.5, -0.5]
```

正值会强化评分高于组平均值的响应中的 token。负值会降低低于平均值的响应出现的概率。

如果每个响应获得相同奖励，中心化后的每个优势值都为零。该组不包含相对学习信号，可以跳过。

## datum 中应包含什么

对于常见的重要性采样循环，每个 datum 包含：

- 提示词及其后的采样补全
- 与模型输入对齐的目标 token
- 采样期间记录的对数概率
- 应用于补全 token 的优势值

提示词前缀是上下文，而不是策略选择的动作。将其优势值设为零，并将响应优势值应用于生成的 token 位置。

<Warning>
  Token 数组的长度必须符合 renderer 和 SDK 的要求。请复用与所选基础模型对应的
  renderer。使用其他模型的 formatter 可能生成错误的停止序列或 token 对齐。
</Warning>

## 有序且幂等的更新

训练运行是一个有序状态机。SDK 会为前向和反向传播、优化器步骤、保存及加载等操作分配序列 ID。

如果使用相同的运行、序列 ID 和请求正文重试请求，RL API 会返回原始操作，而不会重复应用。使用同一序列
ID 但传入不同正文会被拒绝。这能在客户端因网络中断而重试时保护优化器状态。

除非独立进程共享同一个排序机制，否则不要从多个独立进程为同一个训练客户端提交操作。

## 实时状态与持久状态

训练权重、待处理梯度和优化器状态属于实时状态。RL API
可以尝试在空闲缩容或基础设施中断后重建运行。自动恢复会从重放基础开始，并重放已记录的
`forward_backward` 和 `optim_step` 变更。它不会重放每个 API
操作；当某项变更的结果未知，或所需的重放数据不再可用时，恢复可能会失败。

显式检查点是由你掌控的恢复边界：

- `save_state(name)` 存储训练权重和优化器状态。
- `save_weights_for_sampler(name)` 存储用于采样的权重。
- `create_training_client_from_state_with_optimizer(path)` 使用已保存的权重和优化器状态启动新的运行。
- `create_training_client_from_state(path)` 使用已保存的权重和全新的优化器启动新的运行。
- `load_state(path)` 将兼容的检查点恢复到现有运行中。

在长时间的外部工作之前、进行高风险代码更改之前，以及达到可能需要比较或恢复的里程碑时保存状态。

## 成本边界

采样按输入 token、缓存输入 token 和输出 token 计量。前向和前向-反向操作按训练 token
计量。检查点存储按时间计量。

创建模型客户端、执行优化器步骤以及保存或加载检查点本身不会增加 token
用量。相关用量仍由实际处理的 token 和存储的字节数决定。

## 可靠的生产模式

1. 启动时查询服务器功能。
2. 固定应用已测试的 SDK 版本。
3. 保持 rollout 生成并发，但训练更新必须有序。
4. 将检查点路径与应用步骤一同记录。
5. 获取 future 结果时使用有界重试。
6. 在 `finally` 块中关闭服务客户端。
7. 仅保留所需的检查点。

有关具体的 datum 构建方式和确定性评分器，请继续阅读[可验证奖励实战示例](/cn/cookbooks/rl-verifiable-rewards)。
