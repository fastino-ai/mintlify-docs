在使用 GLiNER 2.5 Decide 的分类触发生产操作之前，请先使用应用中的已标注示例对其进行评估。

## 了解阈值行为

`cls_threshold` 仅适用于 `multi_label: true` 的任务：

```json
{
  "task": "topics",
  "labels": ["billing", "technical", "account", "security"],
  "multi_label": true,
  "cls_threshold": 0.5
}
```

- 提高阈值会返回更少的标签，通常更偏向精确率。
- 降低阈值会返回更多的标签，通常更偏向召回率。
- 单标签任务始终返回得分最高的标签；`cls_threshold` 不会改变其选择。
- `cls_threshold` 是推理设置，不影响训练。

## 构建评估集

使用能够代表生产流量的示例，包括：

- 每个标签的常见输入
- 罕见但重要的标签
- 接近类别边界的模糊输入
- 应该获得多个标签的输入
- 在所选阈值下不应获得任何多标签结果的输入
- 应用可能遇到的域外或格式错误输入

将评估数据与微调数据分开。

## 衡量应用所需的行为

对于单标签任务，请检查整体准确率和每个标签的错误。混淆矩阵有助于发现模型经常混淆的标签。

对于多标签任务，请衡量整体和每个标签的精确率、召回率和 F1。还应检查：

- 会触发错误操作的假阳性
- 会跳过必要操作的假阴性
- 每个输入选择的标签数量
- 空选择的频率
- 接近阈值的结果

## 选择阈值

1. 运行评估集，并保留每个选中的标签和置信度。
2. 测试多个候选阈值。
3. 比较精确率、召回率和业务影响。
4. 当不同任务的错误成本不同时，为每个任务选择阈值。
5. 更改标签、数据或模型后重新评估。

不要假定 `0.5` 普遍适用。对于高影响操作，请使用保守的自动化阈值，并保留复核或后备路径。

## 何时进行微调

先从运行时定义的标签开始，并评估基础模型。当代表性评估表明更改 schema 和调整阈值仍无法达到你的领域所需质量时，再进行微调。

## 1. 确认训练目标

查询[基础模型目录](/cn/api-reference/training/base-models)，并确认所选分类模型支持你计划使用的训练类型。

## 2. 准备分类数据

每行存储一个 JSON 对象。单标签示例使用 `label`：

```jsonl
{"text":"The setup was straightforward.","label":"positive"}
{"text":"The application crashes during sign in.","label":"negative"}
```

多标签示例使用 `labels`：

```jsonl
{"text":"The app crashes on login and I need help urgently.","labels":["technical_issue","login_problem","urgent"]}
```

使用与你的推理 schema 分类体系一致的稳定标签名称。为每个标签加入代表性示例，并保留独立的评估集。

## 3. 启动并监控训练

使用准备好的数据集和可训练的分类基础模型创建训练作业。只选择该模型训练方案支持的训练参数。

<Card title="训练作业" icon="activity" href="/cn/training">
  提交作业、监控其状态、检查指标和检查点，并获取生成的产物。
</Card>

## 4. 评估训练结果

在同一个留出集上比较训练后的模型与基础模型：

- 单标签任务的整体准确率和每个标签的准确率
- 多标签任务的精确率、召回率和 F1
- 罕见和高影响标签上的错误
- 生产阈值附近的行为
- 延迟和运维要求

不要只根据训练损失选择检查点。请评估应用实际要使用的分类行为。

## 5. 使用训练后的模型

所选检查点可部署后，通过受支持的推理端点使用其模型标识符，并保持应用所需的相同分类 schema。由于微调后置信度行为可能发生变化，请重新验证阈值。
