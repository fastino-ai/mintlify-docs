**Choice** 问题让 GLiDE 从调用方定义的固定集合（最多 255 个命名选项）中选出一个选项。响应包含所选选项、一个置信度值，以及你定义的所有选项上的完整概率分布。

当答案是若干无序类别中的一个时，请使用 Choice：应由哪个团队处理某张工单、某个产品属于哪个类别、某段代码片段使用的是哪种语言。

## 请求

<ParamField body="type" type="string" required>
  始终为 `"choice"`。
</ParamField>

<ParamField body="instructions" type="string" required>
  以自然语言描述的待评估问题。
</ParamField>

<ParamField body="criteria" type="object" required>
  将最多 255 个选项键映射到描述字符串的对象，例如 `{"billing": "Payment or charge disputes", "returns": "Refund or return requests"}`。选项名称及其描述都会发送给模型，因此请编写能够区分相似选项的描述。
</ParamField>

<CodeGroup>

```bash cURL
curl -s https://api.fastino.ai/v1/systemone \
  -H "X-API-Key: $FASTINO_API_KEY" \
  -H "Content-Type: application/json" \
  -d '{
    "model": "fastino/glide",
    "state": "Refund request: the receipt is attached, the purchase was 10 days ago, and refunds are allowed within 30 days.",
    "questions": {
      "department": {
        "type": "choice",
        "instructions": "Which team should handle this request?",
        "criteria": {
          "billing": "Payment or charge disputes",
          "returns": "Refund or return requests",
          "shipping": "Delivery or shipping issues"
        }
      }
    }
  }'
```

</CodeGroup>

## 答案对象

`answers` 中对应的条目如下：

```json
{
  "department": {
    "type": "choice",
    "choice": "returns",
    "confidence": 0.9983415574354015,
    "probabilities": {
      "billing": 0.000576420510560337,
      "returns": 0.9989179779459618,
      "shipping": 0.0005056015434779647
    }
  }
}
```

- `choice`：概率最高的选项。
- `probabilities`：你定义的所有选项上的完整分布；键与你的 `criteria` 键一致，总和约为 1。
- `confidence`：`top1 − top2`，即最佳与次佳选项之间的概率差，从 `0`（两个选项持平）到 `1`（某个选项占据几乎全部概率质量）。关于如何据此采取行动，请参阅[置信度](/cn/concepts/decision-models#置信度)。

## 使用结果

```python
answer = response["answers"]["department"]

queue_map = {"billing": "billing-team", "returns": "returns-desk", "shipping": "logistics"}
target_queue = queue_map[answer["choice"]]

if answer["confidence"] < 0.5:
    notify("routing uncertain - runner-up may also apply")
```

## 在一次调用中提出所需的全部问题

请在单个请求中针对同一个 `state` 评估多个 Choice 问题，而不是每个问题发送一个请求。这些问题会被独立回答，因此增加一个问题会消耗更多 token，但几乎不会影响延迟。例如，支持分诊调用可以一次性提出 `department`、`urgency` 和 `tone`，而无需三次往返；你的代码可以先根据 `department` 采取行动，在需要时再使用其余结果。完整示例请参阅[组合多个问题](/cn/concepts/decision-models#组合多个问题)。

请向模型提供真实选项的完整列表，而不是精简后的候选列表：一个 Choice 问题最多接受 255 个选项，而每个选项只消耗少量 token。当输入可能无法覆盖所有情况时，请添加 `other` 或 `none of the above` 选项，让 GLiDE 有地方安放概率质量，而不是被迫将其错误地匹配到某个命名选项上。
